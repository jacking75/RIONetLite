3부 · C12

완료를 반영하고 읽기와 쓰기 구간을 분리한다

다음 수신을 먼저 게시해도 안전하려면 커널의 쓰기 범위와 콜백의 읽기 범위가 겹치지 않아야 한다.

컨텍스트와 세대부터 확인한다

워커는 CQ에서 꺼낸 결과의 RequestContext를 보고 세션과 I/O 방향을 찾는다. null 컨텍스트, 잘못된 소유 관계, 오래된 세대와 손상된 CQ는 각각의 오류 경로다. 유효하지 않은 완료를 현재 세션의 정상 수신으로 합치지 않는다. native status 오류가 있으면 해당 요청 참조를 실패로 정리하고 연결 종료를 요청한다.

정상 status라도 transferred가 0이면 수신에서는 peer FIN 경로다. RecvFailed로 수신 참조를 정리하고 BeginPeerClose로 새 애플리케이션 송신을 차단한 뒤 지연 종료 관리자에 넣는다. 이미 접수된 송신을 기다리는 동작은 C16에서 다룬다. 같은 0을 송신의 정상 빈 메시지로 해석하지 않는다.

빈 구간으로 게시한다

PostRecv는 연결·네트워크 허용 상태와 writable 크기를 확인한다. 빈 공간이 0이면 RECV_BUFFER_FULL을 반환하고, 요청 길이는 max_receive_chunk_bytes와 writable 중 작은 값으로 정한다. 요청 컨텍스트에 UID, 등록 ID, 쓰기 위치와 길이를 넣고 outstanding을 증가시킨다. RIOReceive 게시가 실패하면 컨텍스트와 참조를 롤백한다.

RecvCompletion은 완료 크기를 컨텍스트와 링의 범위 안에서 검사한다. 실제 도착한 크기만 링의 used와 쓰기 위치에 반영한다. 다음 수신을 게시할 때 아직 오지 않은 데이터를 이미 쓴 것으로 계산하면 콜백이 쓰레기 데이터를 보게 되므로 게시 길이와 완료 길이를 나누어 유지한다.

완료와 소비를 서로 다른 동작으로 실행한다

실험에서 3바이트를 완료한 뒤 보면 콜백은 used=3의 범위를 읽고, 다음 수신은 빈 공간에서 4바이트를 기다린다. 소비량을 2로 반환하면 한 바이트가 꼬리로 남는다. 다음 완료가 4바이트면 미소비 범위는 5가 된다. 이 수치는 “이번 수신 5바이트”가 아니라 이전 꼬리와 새 수신의 합이다.

완료 길이를 게시 길이보다 크게 주거나 소비량을 readable보다 크게 주면 오류다. 범위를 clamp해 조용히 성공시키지 않는다. 잘못된 입력을 발견한 위치와 세션 ID를 기록해 연결을 닫는 것이 문제를 숨기고 계속 쓰는 것보다 추적하기 쉽다.

선게시 뒤 콜백을 호출하고 소비량을 반영한다

완료를 정상 반영하면 여유가 있는지 확인해 다음 수신을 콜백보다 먼저 게시한다. 빈 범위만 게시하므로 커널과 콜백이 같은 바이트를 동시에 수정하지 않는다. InvokeReceiveCallback은 읽기 가능한 span을 브리지로 전달하고 반환된 소비량만큼 읽기 위치를 옮긴다.

선게시 때 버퍼가 full이었다면 콜백이 공간을 만든 뒤 다시 게시를 시도한다. 콜백이 데이터를 소비하지 않아 계속 full이면 연결을 overload 경로로 닫을 수 있다. 길이 헤더가 아직 덜 왔다는 정상적인 소비량 0과, 완성 가능한 입력도 영구히 소비하지 않는 애플리케이션 오류를 구분한다.

공개 핸들러의 과대 소비는 먼저 Server::Impl::RejectReceiveCallback이 검사해 로그와 프로토콜 종료 요청으로 바꾼다. 내부 ConsumeRecvBuffer도 별도로 readable 범위를 검사한다. 이중 방어가 있다고 잘못된 소비량을 정상 반환해도 되는 것은 아니다.

닫힘 뒤의 지연 완료는 데이터 콜백을 만들지 않는다

소켓을 닫은 직후에도 커널의 취소·완료 결과가 남을 수 있다. 현재 세션이 더 이상 연결 상태가 아니면 수신 요청 참조만 정리하고 OnData를 호출하지 않는다. OnClosed 뒤에 Player가 제거된 게임 로직에 새 데이터가 들어가는 일을 피해야 한다.

세대가 다른 완료는 상태가 닫혔다는 검사와도 다른 조건이다. UID 검사를 먼저 수행하며 오래된 완료를 새 연결의 요청으로 retire하지 않는다. 안전한 슬롯 재사용이 이 수명 조건을 전제로 하므로 index만 보고 후처리하지 않는다.

EventHandler의 span과 소비량을 지킨다

EventHandler는 OnConnected, OnData, OnClosed 세 callback을 제공한다. 같은 세션의 연결과 수신, 종료 순서를 지키지만 전체 서버의 모든 callback이 한 스레드에서 직렬화된다는 뜻은 아니다. 서로 다른 세션과 logger 호출은 병행될 수 있다.

OnData의 span은 callback이 반환할 때까지만 유효하다. pointer를 Player에 보관하거나 DB task에 캡처하면 이후 링이 재사용될 때 다른 바이트를 읽을 수 있다. 비동기 작업에는 직접 소유하는 벡터나 queue slot을 전달한다.

OnData의 반환값은 앞부분 중 소비한 byte 수다. 0은 입력을 버린다는 뜻이 아니라 이번에는 처리하지 않았다는 뜻이다. available보다 큰 값을 반환하면 범위 계약 위반으로 종료한다. 미완성 prefix를 남기는 방식에서는 부분 소비가 정상적이다.

callback에서 자신의 Server::Start나 Stop을 호출하면 kInvalidState로 거절한다. Send와 RequestClose는 허용되지만 callback에서 객체를 파괴하지 않는다. Stop이 callback을 실행한 워커를 join하는 구조이므로 소유 스레드에 종료 요청을 넘긴다.

EventHandler의 span과 소비량을 지킨다: 적용한다

수신 callback에서 12바이트 완성 패킷과 3바이트 꼬리를 보았다. 12를 반환하면 꼬리는 남고 15를 반환하면 사라진다. adapter를 사용한 경우는 15 모두를 자체 slot으로 복사하고 worker의 입력 버퍼에서 꼬리를 관리한다.

OnData 예외와 과소비는 protocol close를 요청한다. OnConnected와 OnClosed 예외는 로그로 격리하는 경로이므로 같은 실패 정책이라고 단정하지 않는다. callback 내부의 긴 대기나 무한 loop는 강제로 중단할 수 없으며 noexcept 표기로 실행 시간이 제한되지 않는다.

실습에서 관찰할 값

  • span의 주소가 callback 밖으로 새지 않는지 본다.
  • 소비량이 available 이내인지 검사한다.
  • 느린 처리와 Stop을 owner로 전달한다.

생각하고 확인한다

queue가 찼을 때 0을 반환하면 소비자가 비운 뒤 자동으로 다시 callback이 오는가.

해설 펼치기

그 보장은 없다. 다음 수신 완료 같은 호출 계기가 필요할 수 있다. 단순히 0을 반환하는 방식은 흐름 제어 계약이 아니며 정지나 입력 축적을 만들 수 있다. 현재 adapter의 framed TCP 정책은 포화 시 연결을 종료한다.

CQ worker는 식별과 상태부터 검사한다

I/O worker는 자신의 CQ에서 batch 결과를 꺼낸다. 결과 buffer는 thread를 만들기 전에 확보해 실행 중 allocation 예외를 줄인다. CQ 생성이나 thread 생성 일부 실패 시 이미 생긴 자원과 thread를 rollback한다.

결과의 RequestContext는 먼저 null인지 확인하고 owner worker와 generation을 검사한다. null context를 session index 조회 전에 역참조하면 나중 방어 함수가 있어도 소용없다. RIO_CORRUPT_CQ는 일반 결과 개수가 아니라 별도의 치명적 상태다.

status 오류는 방향별 outstanding를 정리하고 close 경로로 이어진다. transferred=0의 수신은 peer FIN으로 해석하며 남은 수락 송신을 기다릴 수 있다. 송신과 수신의 같은 0을 같은 game payload로 처리하지 않는다.

수신 성공은 등록 링의 write를 반영하고 가능하면 다음 수신을 먼저 게시한 뒤 callback을 실행한다. 커널이 쓰는 writable 구간과 callback이 읽는 used 구간은 겹치지 않아야 한다. 이미 닫힌 세션의 지연 수신 완료는 데이터 callback 없이 수명만 정리한다.

CQ worker는 식별과 상태부터 검사한다: 적용한다

null context, owner mismatch, stale generation, 과대한 transferred, corrupt CQ를 fake로 주입한다. 이 입력은 일반 소켓 왕복으로 우연히 만들기 어려우므로 결정적인 단위 테스트가 적합하다. 실제 정상·오류 완료는 integration에서 함께 확인한다.

한 세션의 callback이 길어지면 같은 worker의 다른 완료도 늦어진다. batch를 크게 만들면 처리량이 달라질 수 있지만 game work를 callback에 넣어도 괜찮다는 근거는 되지 않는다.

실습에서 관찰할 값

  • null 검사가 최초 역참조보다 앞인지 본다.
  • stale 완료가 새 연결에 callback을 만들지 않는지 본다.
  • corrupt CQ가 Stop 성공으로 숨겨지지 않는지 본다.

생각하고 확인한다

실제 completion buffer를 worker loop 안에서 매번 할당하면 어떤 비용과 위험이 생기는가.

해설 펼치기

반복 allocation과 해제 비용이 추가되고 메모리 부족이 thread 내부에서 발생한다. 실행 전 확보하면 Start에서 실패를 보고하고 rollback할 수 있어 오류 경계가 명확해진다.

RIONetLite/impl/tcp_session.h

TcpSession은 세션 identity, socket/RQ와 recv context, 수신 링과 sender를 묶는다. 수신·송신 완료와 close가 모두 같은 연결 자원을 다루지만 각 경로의 동기화와 상태가 다르다.

OnConnect는 소켓 옵션을 확인한 뒤 generation 상태를 활성화한다. connect pending flag는 accept의 마지막 접근까지 recycle을 미룬다. last_activity는 수신 완료에서 갱신한다.

Disconnect는 close 승자와 socket_closed CAS, close notification을 연결한다. buffer Dispose와 socket close는 같은 작업이 아니며 outstanding는 늦게 오는 완료로 배출될 수 있다.

이 파일에서 추적할 연결

  • session_lifecycle.h의 CAS 전이를 읽는다.
  • accepter의 CompleteConnectCallback 위치를 본다.
  • sender의 BeginClose와 outstanding를 연결한다.

독해 포인트
