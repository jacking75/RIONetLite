같은 연결의 순서와 다른 연결의 동시성을 나눈다

하나의 콜백은 짧게 끝내고, 그 밖의 스레드가 동시에 무엇을 할 수 있는지 확인한다.

중급큰 그림에서의 위치: P02 누가 어떤 스레드에서 일하는가

쉽게 말하면 어떤 콜백이 어느 스레드에서 불리는지 다룬다. 같은 세션의 이벤트는 순서가 지켜지지만 다른 세션의 콜백은 동시에 실행될 수 있다. 콜백 안에서 무언가를 기다리면 같은 워커의 다른 플레이어까지 느려지는 이유도 설명한다.

처음 읽는다면 어느 스레드가 호출하는가와 기다리는 작업을 콜백에 넣지 않는다 두 절이 핵심이다.

어느 스레드가 호출하는가?

OnConnected는 accept 경로에서 실행된다. 연결 준비가 끝나기 전에 다른 워커가 슬롯을 재사용하지 않도록 connect callback pending 보호가 있다. 첫 수신은 연결 콜백 뒤에 게시되고, accept가 마지막 접근을 끝낸 뒤 pending 플래그를 해제한다. OnClosed가 아직 끝나지 않은 연결 콜백을 앞질러 Player 상태를 지우는 경로를 막는 이유다.

OnData는 세션의 소유 I/O 워커가 완료를 처리한 뒤 실행한다. 정상 활성 연결의 OnClosed도 그 소유 I/O 워커가 지연 종료 처리를 확정한 뒤 브리지를 통해 실행한다. OnConnected의 accept 스레드와 OnData·OnClosed의 워커는 서로 다르다. Logger는 accept·I/O·생명주기 경로에서도 호출될 수 있다. 모든 콜백이 전역 단일 스레드라고 가정하지 않으며 애플리케이션 공유 컨테이너는 세션 간 동시 접근을 고려한다.

두 세션을 교차 실행해 본다

실험은 콜백 하나를 시작부터 반환까지 묶는다. A의 OnData와 B의 OnData 순서를 바꾸는 것은 가능하지만 A의 OnClosed 뒤 A의 OnData를 새로 전달하는 것은 차단한다. 이 보장은 원격 애플리케이션의 업무 처리 순서를 자동 직렬화한다는 뜻이 아니다. 별도 게임 큐에 넣은 작업도 같은 세션의 이벤트 순서를 보존해야 한다.

기다리는 작업을 콜백에 넣지 않는다

DB 조회, 파일 저장, 네트워크 재시도나 다른 워커의 응답을 기다리는 작업은 I/O 워커의 진행을 멈춘다. 완료 처리가 늦어지면 송신 링이 차고 종료도 지연될 수 있다. 워커 수만 늘리기 전에 콜백 시간과 큐 대기 시간을 따로 측정한다.

QueuedEventAdapter를 사용할 때는 콜백 span의 내용을 복사해 유효 기간을 끊는다. 복사 비용은 있지만 게임 처리의 스레드와 수명이 분명해진다. 무조건 포인터만 전달해 복사를 줄이는 접근은 완료 전에 재사용되는 링을 나중에 읽는 오류로 이어질 수 있다. 잠금 없는 큐라는 이름도 payload 소유권이나 종료 순서를 대신하지 않는다.

예외를 격리해도 잘못된 일을 완료한 것은 아니다

브리지는 핸들러의 표준 예외와 알 수 없는 예외를 격리한다. OnConnected·OnClosed의 예외는 로그를 남기고 콜백 경계에서 잡는다. OnData의 예외와 제공 범위를 넘는 소비량은 RejectReceiveCallback을 통해 프로토콜 종료를 요청한다. 모든 콜백 예외에 같은 자동 종료 정책이 적용되는 것은 아니다. 프로세스가 살아 있다는 사실이 그 패킷의 처리가 성공했다는 뜻도 아니다. 오류 로그의 operation과 세션 ID로 해당 작업을 추적한다.

같은 서버의 이벤트나 로거 콜백에서 Start·Stop 같은 생명주기 진입을 시도하면 거절하는 보호가 있다. Stop을 직접 호출해 자기 스레드를 join하게 만드는 대신 제어 스레드에 종료 플래그를 전달한다. 로거의 IsEnabled도 이 재진입 경계에 포함된다.

스레드와 콜백

accept 스레드는 OnConnected를 호출하고 I/O 워커는 자신의 세션 OnData/OnClosed를 처리한다. 같은 세션의 OnConnected가 끝난 뒤 다른 callback을 전달하며 수신과 종료 순서를 보존한다. 다른 세션과 Logger는 동시 실행될 수 있어 handler/logger의 공유 상태는 사용자가 동기화한다.

Send·RequestClose·Stop·Metrics는 여러 애플리케이션 스레드에서 호출할 수 있다. Stop은 실행 상태를 닫고 이미 진입한 transport 호출자를 배출한다. 객체 이동·파괴는 application 호출자 종료 후 수행한다. event/logger callback 안에서 같은 서버의 Start/Stop은 kInvalidState다. 종료가 필요하면 atomic flag나 control queue로 주 스레드에 알린다. callback에서 다른 스레드를 만들고 그 스레드의 Stop을 기다려도 join 교착이므로 기다리지 않는다.

callback에서 DB·파일·게임 로직을 수행하거나 span을 저장하지 않는다. QueuedEventAdapter가 owned raw bytes로 넘기고 게임 워커가 처리한다. adapter는 유계 저장소와 짧은 mutex를 사용한다. capacity 확보 실패 시 생산자를 무한 대기시키지는 않지만 mutex 경합 대기는 존재한다.

OnData 예외는 protocol close다. OnConnected/OnClosed와 Logger.Log 예외는 격리·기록 또는 무시한다. Logger.IsEnabled는 noexcept 계약을 지킨다. 커널은 별도의 비중첩 링 구간에 다음 수신을 게시하므로 callback span을 반환 전까지만 읽는다. 함수별 조건은 API 계약에 있다.

이벤트와 로그의 borrowed view

include/rionetlite/event_handler.h

SessionId는 슬롯 index와 generation을 함께 표현한다. EventHandler의 세 함수가 네트워크에서 애플리케이션으로 들어오는 공개 경계다. 같은 연결의 순서 계약과 전체 서버의 동시 callback 가능성을 분리한다.

OnData는 span의 소유권을 넘기지 않고 callback 동안 빌려 준다. 반환값은 처리한 앞부분 크기다. logger의 string_view도 호출 동안만 유효하므로 비동기 저장 시 복사가 필요하다.

Logger는 문자열 방식과 구조화 LogEvent 방식을 제공한다. 기본 LogEvent overload가 문자열 overload로 전달하므로 기존 간단한 sink도 동작한다. IsEnabled는 noexcept 계약이다.

이 파일에서 추적할 연결

  • Server::Impl의 CallbackScope와 exception 격리를 본다.
  • adapter가 span을 복사하는 위치를 찾는다.
  • 비동기 logger를 추가할 때 owned string을 사용한다.
