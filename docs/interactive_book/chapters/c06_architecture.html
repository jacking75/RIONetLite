공개 API에서 소유 워커까지 연결한다

클래스 이름을 모두 외우기보다 애플리케이션 경계, transport 경계와 실행 주체를 따라간다.

공개 객체는 내부 transport의 수명을 묶는다

include/rionetlite/는 애플리케이션이 포함할 공개 헤더다. src/server.cpp의 Server::Impl은 설정·상태·지표·핸들러 브리지를 소유한다. 내부 transport는 전환 중인 RIONetLite/impl/의 세션 관리자, accept, I/O 워커, 송신기와 지연 종료 관리자로 이루어져 있다. 공개 Server가 내부의 모든 클래스와 같은 타입은 아니다.

Echo 애플리케이션은 OnData 콜백 안에서 디코딩하고 Send한다. Chat 경로를 선택하면 복사 큐와 게임 워커 이후 경계를 비교할 수 있다.

그림의 텍스트 순서
  1. 애플리케이션이 공개 API로 Send와 종료 요청을 전달한다.
  2. Server 브리지가 상태·인자·지표와 핸들러 경계를 관리한다.
  3. 내부 transport가 세션과 링을 소유하고 소유 워커의 RQ/CQ로 연결한다.
  4. Winsock/RIO의 완료를 I/O 워커가 처리해 브리지와 EventHandler로 되돌린다.
  5. Echo는 콜백에서 응답하고 Chat은 복사 큐를 거쳐 별도 로직 shard에서 처리한다.

내부 이름이 남아 있다는 이유로 예제에서 내부 헤더를 직접 포함하면 수명과 오류 변환을 우회하기 쉽다. Echo와 Chat은 가능한 한 공개 헤더를 사용한다. 내부 구조를 바꾸더라도 이 사용 계약과 예제의 검증을 함께 유지해야 한다.

스레드와 클래스의 경계를 겹쳐 그리지 않는다

accept 스레드는 연결을 받고 슬롯을 준비한 뒤 OnConnected를 호출한다. 각 I/O 워커는 자기 CQ와 세션 파티션을 처리한다. 같은 워커에 여러 세션이 속하므로 한 콜백이 오래 멈추면 그 워커의 다른 세션도 영향을 받는다. Chat의 로직 shard는 이 I/O 워커와 별도의 애플리케이션 스레드다.

요청 큐와 세션을 만든 워커 배정은 연결 수명 동안 유지된다. 모든 세션을 여러 워커가 동시에 임의로 소유하는 구조라고 설명하지 않는다. 다만 Send는 애플리케이션의 여러 스레드에서 들어올 수 있어 송신 링과 종료 진입을 별도로 보호한다.

Echo와 Chat은 콜백 이후 경로가 다르다

Echo는 OnData → Decode → Send를 짧은 콜백 안에서 실행한다. Chat은 QueuedEventAdapter가 raw chunk를 복사하고 로직 shard가 TryPop한 뒤 Player 입력을 해석한다. Chat의 룸·로그인 상태는 그 로직 shard가 소유한다. Echo 경로에 존재하지 않는 게임 큐를 설명 그림에 끼워 넣지 않는다.

Chat의 방송은 한 shard의 PlayerMap만 순회하지 않는다. 모든 shard의 유계 inbox에 같은 room 메시지를 넣고 각 shard가 자기 플레이어에게 보낸다. 모든 목적지의 공간을 함께 검사하므로 포화 시 일부 shard에만 방송을 넣는 결과를 피한다. 이 구조의 잠금과 메모리 비용은 C19에서 다룬다.

가짜 API를 넣는 접점도 구조의 일부다

RioApi와 SocketApi는 운영체제 호출을 좁은 인터페이스로 분리한다. 실제 구현과 fake 구현을 같은 transport에 주입하면 초기화의 N번째 실패, CQ 손상과 게시 오류를 반복할 수 있다. 운영 코드와 다른 완전히 별도의 테스트용 네트워크 스택만 검사하는 것보다 실제 분기에 가까운 증거를 얻는다.

그렇더라도 실제 accept·completion·소켓 취소는 통합 검사가 필요하다. 테스트가 최소 OS 의존성을 갖는다는 말은 모든 테스트가 OS 없이 실행된다는 뜻이 아니다. Win32 자원 테스트와 실제 RIO 통합 테스트의 경계를 결과표에 남긴다.

구조를 바꿀 때 소유권과 종료를 먼저 추적한다

버퍼 풀이나 워커 수를 바꾸기 전에 누가 생성하고, 누가 게시하고, 누가 마지막 완료를 처리하고, 누가 해제하는지 연결한다. Send 처리량이 개선되어도 지연 완료가 이전 세션의 자원을 건드리면 안전한 변경이 아니다. 성능과 세션 정합성, 종료의 실패 경로를 함께 검증한다.

구조와 설계

flowchart LR
  Client --> Accept[Accept thread]
  Accept --> RQ[RIO request queue]
  RQ --> IO[Owner I/O worker]
  IO --> Handler[EventHandler]
  Handler --> Adapter[QueuedEventAdapter]
  Adapter --> Logic[Sharded game workers]
  Logic -->|SessionId + owned bytes| Send[Bounded send ring]
  Send --> RQ

주 스레드가 Winsock, CQ와 세션 풀을 만든다. 각 세션은 한 I/O worker에 고정되고 index+generation이 수명을 식별한다. 세션 슬롯은 worker 파티션에 걸쳐 라운드로빈으로 대여하므로 기동 직후 부하가 한 worker에 몰리지 않는다. RIO 등록 버퍼는 완료가 끝날 때까지 주소와 등록 ID가 유지된다. 네트워크 callback에서 DB, 파일 I/O, room 처리를 실행하는 설계는 잘못이며 ChatServer처럼 유계 adapter로 넘기는 방식이 올바르다.

세션당 in-flight RIO 요청은 수신 1개와 송신 1개다. 송신은 애플리케이션이 쌓은 바이트를 double-mapped 링에 모으고, 진행 중인 요청이 완료되면 그때까지 쌓인 전체 구간을 하나의 RIO_BUF로 다시 게시한다. 따라서 완료 이벤트 수가 패킷 수가 아니라 burst 수에 비례하고 CQ 용량이 세션당 2개로 고정된다. 수신은 완료를 반영한 직후 콜백보다 먼저 다음 요청을 게시해 콜백 구간에도 수신이 진행되게 한다.

라이브러리의 책임을 나눈다

게임 서버는 접속을 받아 바이트를 이동하는 계층과 게임 세계를 바꾸는 계층으로 나뉜다. RIONetLite는 전자를 맡는다. 소켓, 등록 버퍼와 완료 처리를 안전하게 연결하지만 로그인 계정, 아이템 거래나 DB 저장을 구현하지 않는다. Echo와 Chat은 그 경계에서 애플리케이션을 작성하는 예제다.

신규 공개 API는 include/rionetlite 아래에 있다. src는 공개 호출을 구현하고 RIONetLite/impl은 전환 중인 RIO transport를 담는다. 파일 이름에 기존 구현이 보이더라도 새 게임 서버가 해당 내부 타입을 직접 사용하면 수명 규칙과 교체 비용까지 떠안게 된다.

Server는 move-only 객체다. Create에서 설정 검증과 자원 준비가 성공하면 Initialized가 되고 Start에서 accept와 I/O 워커를 시작한다. Stop으로 끝난 객체를 다시 Start하는 계약은 없다. 재기동은 새 Server를 만들어 진행한다.

핵심 설계 질문은 누가 데이터를 소유하고 언제 해제할 수 있는가다. TCP 바이트는 커널에서 등록 버퍼로 들어오고, callback의 span은 잠시 빌려 준다. 게임 작업이 이후까지 데이터를 쓰려면 별도 저장소에 복사한다. 빠른 네트워크 처리보다 이 계약을 먼저 이해해야 한다.

라이브러리의 책임을 나눈다: 적용한다

채팅 서비스를 만든다고 가정한다. 네트워크 callback에서는 연결 식별자와 수신 바이트를 유계 큐로 넘긴다. 게임 워커가 패킷을 해석하고 룸의 플레이어에게 Send한다. DB 조회는 다시 별도 작업으로 보내고 완료를 해당 플레이어의 워커에 돌려준다.

개발 초기에 전역 Server 포인터 하나로 모든 것을 연결하면 종료 시 누가 먼저 사라지는지 불분명해진다. handler와 logger를 먼저 만들고 마지막에 파괴하며 Server를 명시적으로 Stop한다. 객체 배치도 계약의 일부다.

  • handler와 logger가 Server보다 오래 사는지 확인한다.
  • Create, Start, Stop 실패를 구분해 출력한다.

저장소를 길 찾기 지도처럼 읽는다

공개 헤더부터 테스트까지 경로를 연결하면 파일 수에 압도되지 않는다. include/rionetlite/server.h는 애플리케이션이 보는 계약이고 src/server.cpp는 공개 상태, 오류, 지표를 관리한다. legacy_server_net.cpp는 공개 래퍼에서 기존 transport로 이어지는 호환 계층이다.

RIONetLite/impl/server_net.h는 초기화, 워커 시작과 종료를 조립한다. accepter는 새 소켓을 세션에 붙이고 io_worker는 CQ 결과를 처리한다. tcp_session은 연결 하나의 수신·송신 자원과 세션 상태를 묶는다. sender와 ring buffer는 바이트 저장과 게시를 담당한다.

src/detail은 운영체제 자원의 RAII와 검증 가능한 작은 알고리즘을 담는다. session_partition과 session_lifecycle은 테스트에서 독립적으로 상태를 확인하기 쉽다. socket_api와 rio_api의 추상화는 실제 Windows 호출과 실패를 주입하는 fake 구현 사이의 접점이다.

samples/echo_server는 최소 직접 callback 사용을, chat_server는 게임 워커로 넘기는 구조를 보여 준다. tests/unit은 작은 범위·경쟁 계약을 확인하고 tests/integration은 실제 소켓과 RIO를 통과한다. 도구의 성공 출력만 보지 않고 어떤 실행 파일과 환경이 쓰였는지 확인한다.

저장소를 길 찾기 지도처럼 읽는다: 적용한다

문제 보고가 “close 뒤에도 데이터가 온다”라면 게임 룸 코드부터 수정하지 않는다. CQ worker가 세션 상태를 검사하는 위치와 callback 뒤 close 처리, adapter의 event sequence, game worker의 generation 검증을 차례로 본다.

소스 독해편에서 같은 경로를 찾아 줄 번호를 맞춘다. 단일 함수만 떼어 보고 안전하다고 결론 내리지 않는다. 호출자가 유지하는 잠금과 피호출자가 기대하는 수명을 연결해야 경쟁 조건이 드러난다.

실습에서 관찰할 값

  • 각 파일의 사용자 호출자와 내부 호출자를 구분한다.
  • 함수 입력이 raw pointer인지 소유 객체인지 표시한다.
  • 성공뿐 아니라 반환 false와 exception 경로도 따라간다.

생각하고 확인한다

테스트 fake가 성공한다고 실제 RIO가 성공했다고 말할 수 있는가.

해설 펼치기

없다. fake는 특정 분기와 수명 규칙을 결정적으로 검사한다. 실제 provider와 Windows 자원, 소켓 종료의 동작은 integration 실행으로 별도 확인한다. 둘 다 필요하며 서로의 증거를 대신하지 않는다.
