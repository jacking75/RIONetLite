애플리케이션 메시지를 유계 송신 링에 넣는다

수락하지 않은 메시지를 알아야 재시도와 종료를 올바르게 선택할 수 있다. 수락한 메시지 수와 실제 RIO 요청 수는 같지 않다.

중급큰 그림에서의 위치: P02 ④ 송신

쉽게 말하면 Send를 부르면 바이트가 세션의 송신 링에 복사되고, 진행 중인 송신이 없을 때만 RIO 송신이 게시된다. 링에 자리가 없으면 메시지 전체를 거절(kWouldBlock)하며, 그때 다시 보낼지 끊을지는 앱이 정한다.

처음 읽는다면 메시지 전체가 들어갈 공간을 먼저 확인한다 절과 마지막 절의 앱 정책이 핵심이다.

헤더와 본문을 함께 받지만 자동으로 만들지는 않는다

한 span Send는 같은 내부 함수에 빈 두 번째 span을 넘긴다. 두 span Send는 앱이 이미 만든 헤더와 본문을 한 메시지로 이어 복사한다. 헤더를 자동 생성하거나 길이를 고쳐 주지 않는다. 전체 길이·버전·타입을 애플리케이션이 프로토콜에 맞게 만들어야 한다.

Echo의 헤더는 4바이트이고 Chat의 헤더는 8바이트다. 두 span 오버로드를 쓴다는 이유로 이 두 프로토콜이 호환되지는 않는다. 이미 헤더가 들어 있는 전체 packet을 첫 span으로 주면서 같은 헤더를 다시 더하면 중복 헤더가 된다. C13과 C19의 wire 예를 기준으로 바이트를 확인한다.

// 애플리케이션의 4바이트 길이 헤더 예다. total=4+3=7이다.
const std::array header{std::byte{0}, std::byte{0}, std::byte{0}, std::byte{7}};
const std::array payload{std::byte{'r'}, std::byte{'i'}, std::byte{'o'}};
const auto result = server.Send(session, header, payload);
// 결과를 검사한다. kQueued는 상대 프로그램의 처리 완료가 아니다.

메시지 전체가 들어갈 공간을 먼저 확인한다

먼저 결론 · 서버가 Running인지 먼저 확인하고 두 span의 합을 넓은 정수로 계산한다. 빈 송신이나 메시지 상한 초과는 링을 수정하기 전에 거절한다.

Send 접수와 잠금 밖 RIO 게시를 나눈다의 순서는 이어지는 본문과 실제 코드에서 확인한다.

공개 API는 running 상태, 넓은 정수로 계산한 크기 합계와 단일 메시지 한도를 검사한다. 내부 PostSendScatter는 송신 lock 아래 게시 허용·활성 UID·전체 writable 크기를 확인한다. 전체가 들어갈 때만 header와 payload를 순서대로 쓴다. 공간 부족에서 헤더만 먼저 쓰고 본문을 나중에 기다리는 부분 수락을 하지 않는다.

송신 링의 used에는 현재 커널이 참조하는 구간도 포함된다. 게시 직후에 그 구간을 비웠다고 계산하면 후속 Send가 진행 중인 데이터를 덮어쓸 수 있다. 읽기 위치와 used를 줄이는 것은 정상 완료를 처리한 시점이다. 반환값 kWouldBlock은 이 유계 공간에 들어가지 못한 메시지에 해당한다.

진행 중인 요청 뒤에 쌓고 완료 때 병합한다

처음 메시지가 들어왔고 진행 요청이 없으면 현재 링의 미소비 전체 구간으로 게시를 준비한다. 이미 요청이 있으면 새 메시지는 링 뒤에 남고 추가 RIOSend를 만들지 않는다. 완료가 오면 실제 완료 바이트만 소비한 뒤 남은 바이트를 다시 한 요청으로 게시한다.

예를 들어 2바이트를 게시한 뒤 3바이트를 추가하면 첫 RIO_BUF는 길이 2다. 그 완료 뒤 새 RIO_BUF는 대기한 길이 3이다. 완료 전에 더 들어온 여러 메시지는 한 번에 병합될 수 있다. FIFO 바이트 순서는 유지되며 애플리케이션 패킷 헤더의 경계도 그대로 남는다.

상태 잠금과 syscall 수명을 분리한다

PreparePostLocked는 컨텍스트, 등록 버퍼 outstanding, in_flight와 posts_in_flight를 갱신한다. 실제 RIO Send는 lock 밖에서 실행한다. 오래 걸릴 수 있는 syscall을 상태 lock 안에서 붙잡지 않으면서도 BeginClose가 RQ를 너무 일찍 지우지 않게 한다.

게시가 실패하면 준비한 참조를 롤백하고 상위에 오류를 반환한다. 게시 함수가 반환한 이후에도 커널 미완료 참조는 남을 수 있으므로 posts_in_flight와 Outstanding을 같다고 보지 않는다. 부분 완료와 재게시 실패의 자세한 상태표는 C15를 따른다.

거절된 메시지에만 앱 정책을 적용한다

게임 서버는 중요 메시지, 반복 가능한 상태 갱신과 일회성 요청의 정책을 구분할 수 있다. kWouldBlock에서 유계 재시도 큐를 쓰거나 최신 상태로 합치거나 연결을 overload 종료할 수 있다. 이 선택은 앱의 메시지 의미에 달려 있다. 무한 큐로 옮겨 API의 유계를 우회하면 지연과 메모리 사용만 다른 곳으로 밀어낸다.

이미 kQueued인 메시지를 “응답이 아직 안 왔다”는 이유만으로 다시 Send하면 중복될 수 있다. 애플리케이션 ACK·요청 ID와 재전송 규칙이 필요하다. kStaleSession에서는 이전 연결의 작업을 버리며 새 연결에 인덱스만 맞춰 다시 보내지 않는다. kClosing과 kUnavailable도 성공으로 소비하지 않는다.

헤더와 본문이 실제 연속 바이트로 게시되는지, 한 세션의 진행 요청이 하나인지, full일 때 기존 바이트를 덮어쓰지 않는지와 종료 경쟁을 각각 확인한다. 메시지를 많이 보낸 사실만으로 큐 포화와 종료 검증을 생략하지 않는다.

송신 배압 단위

세션당 in-flight RIO 송신 요청은 1개로 고정된다. 애플리케이션이 보낸 바이트는 세션 송신 링에 쌓이고, 진행 중인 요청이 완료되면 그때까지 쌓인 전체 구간이 하나의 RIO_BUF로 다시 게시된다. 따라서 배압은 요청 슬롯 수가 아니라 send_buffer_bytes에 남은 바이트로 판정하며, 링에 들어가지 못한 메시지만 kWouldBlock이 된다. 소형 패킷이 많은 게임 트래픽에서 완료 이벤트 수가 패킷 수가 아니라 burst 수에 비례하고, RIO completion queue 용량도 세션당 2개로 줄어든다.

SendResult를 게임 정책으로 바꾼다

Send는 데이터를 반환 전에 내부 링으로 복사한다. 한 span 또는 header와 payload 두 span을 받아 하나의 수락 단위로 처리한다. 두 span을 쓰면 애플리케이션이 합친 임시 벡터를 만들지 않아도 된다. 네트워크 zero-copy를 보장한다는 뜻은 아니다.

kQueued는 수락 성공, kWouldBlock은 링 잔여 용량 부족, kStaleSession은 재사용된 세션 식별자, kClosing은 종료 중, kMessageTooLarge는 empty 또는 최대 초과, kUnavailable은 다른 송신 불가다. 실패별로 게임에서 재시도·폐기·종료 정책을 정한다.

메시지 일부만 수락하는 API가 아니다. header와 payload 전체가 링에 들어가야 한다. 무조건 즉시 재시도 loop를 돌리면 같은 워커의 송신 완료를 막아 용량이 비워지지 않을 수 있다. 재시도는 별도 유계 대기 정책과 deadline이 필요하다.

중요한 거래 응답과 최신 위치 갱신은 같은 배압 정책을 쓰지 않을 수 있다. 위치 갱신은 새 값으로 대체할 수 있지만 거래 결과는 request id와 재조회 경로가 필요하다. 라이브러리의 결과를 게임 의미에 맞게 번역하는 것은 애플리케이션의 책임이다.

SendResult를 게임 정책으로 바꾼다: 적용한다

느린 클라이언트가 읽지 않아 송신 링이 찬다. Chat 예제는 kWouldBlock이나 kUnavailable에서 overloaded close를 요청한다. 이 정책은 예제의 단순성과 메모리 상한을 유지하지만 모든 게임의 정책으로 고정할 필요는 없다.

게임 worker가 이미 지난 generation으로 Send하면 새 사용자에게 전달되지 않아야 한다. kStaleSession은 오래된 task를 버리거나 request 결과를 무시할 계기다. 단순 index map의 존재 여부만 확인하면 이 보호를 우회하게 된다.

실습에서 관찰할 값

  • kQueued와 실제 완료 바이트 지표를 구분한다.
  • 재시도 저장소도 유계인지 확인한다.
  • empty와 maximum 초과를 명시적으로 검사한다.

생각하고 확인한다

Send 호출 횟수와 RIO 송신 요청 개수가 같은가.

해설 펼치기

같지 않다. 이미 in-flight 요청이 있으면 새 바이트를 링에 쌓고 완료 시 하나의 요청으로 묶을 수 있다. 공개 send_operations는 수락된 호출 수이며 실제 provider 요청 수로 해석하면 안 된다.
