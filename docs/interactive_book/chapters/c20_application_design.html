게임 작업의 소유권과 포화를 설계한다

지도에서의 위치는 이 장의 쉽게 말하면 상자에서 설명한다.

콜백을 별도 스레드로 옮긴 뒤에도 지연된 작업, 오래된 연결, 중복 요청과 종료의 책임은 남는다.

중급큰 그림에서의 위치: P02 내가 맡는 일

쉽게 말하면 실제 게임 서버로 키울 때 생기는 설계 문제를 다룬다. DB 응답이 오기 전에 플레이어가 나갈 수 있고, 큐마다 가득 찼을 때의 정책이 필요하며, 종료할 때 게임 작업까지 비워야 한다.

처음 읽는다면 DB 응답이 돌아오기 전에 세션이 바뀔 수 있다 절과 L16 실험을 본다.

네트워크 이벤트와 게임 명령을 구분한다

QueuedEventAdapter의 Data는 raw TCP chunk다. 게임 패킷 하나와 같은 단위가 아니다. 현재 Chat은 게임 워커에서 이를 Player 입력에 붙여 프레이밍한다. 다른 애플리케이션이 I/O 콜백에서 짧은 디코딩을 끝내고 완성된 메시지를 큐에 넣는 설계를 선택할 수도 있지만, 그 경로는 현재 Chat 구현과 구분한 제안이다.

어느 쪽이든 소유하는 payload와 전체 SessionId를 작업에 넣는다. borrowed span과 포인터만 넘기면 네트워크 링이 재사용된 뒤 내용을 읽게 된다. 메시지 소유권을 복사·이동으로 명확히 하고, 누가 소비·폐기·정리하는지 정한다. 여기서 다루는 DB·업무 큐와 월드 처리는 확장 설계이며 이 저장소에 이미 구현된 기능이 아니다.

DB 응답이 돌아오기 전에 세션이 바뀔 수 있다

게임 워커가 DB 작업을 요청할 때 SessionId와 업무 요청 ID를 복사한다. DB 워커는 PlayerMap을 직접 수정하지 않고 결과 메시지를 원래 게임 shard로 돌려준다. 소유 워커는 현재 Player의 전체 ID와 상태를 확인한 뒤 결과를 적용한다. 새 연결에 이전 플레이어의 결과를 적용한 다음 Send에서 stale을 발견하는 것으로는 이미 바뀐 게임 상태를 되돌릴 수 없다.

// 확장 설계의 의사 코드다. 현재 Chat의 구현 코드가 아니다.
on_database_result(result):
  player = shard.players.find(result.session.index)
  if player is absent or player.id != result.session:
    discard(result)
    return
  if request_is_expired_or_already_applied(result.request_id):
    discard(result)
    return
  apply_result_on_owner_thread(player, result)
  handle_send_result(server.Send(player.id, encoded_response))

세대 검사는 연결 식별을 해결하지만 업무 중복을 모두 해결하지 않는다. 같은 연결에서 동일 구매 요청이 두 번 오거나 재접속 후 재전송될 수 있다. 요청 ID, 처리 결과의 보존 기간과 idempotency 정책은 업무 프로토콜과 저장소가 책임진다. kQueued는 이 업무의 영속 저장 완료 확인이 아니다.

한 틱에서 먼저 처리하고 새 작업을 받는다

먼저 예측해 보기 · 매 틱 유입이 처리량보다 크다. 큐만 키우면 해결되는가?

지속되면 다시 포화하므로 유입·처리·거절 정책을 함께 정한다 — L16에서 큐 크기와 틱당 유입을 바꿔 본다.

기본 조건은 용량 8, 유입 3, 처리 상한 1이다. 한 틱은 기존 대기 작업을 최대 1개 처리한 뒤 새 작업을 넣는다. 5틱 뒤 대기 8, 거절 3, 누적 처리 4가 된다. 순서를 반대로 하면 첫 틱의 처리량도 달라지므로 틱의 규칙을 먼저 명시한다.

용량을 늘리면 일시적인 burst를 더 흡수할 수 있지만 유입이 장기 처리량보다 크면 다시 포화된다. 처리 상한을 5로 바꾸면서 새 유입도 5로 두면 이미 가득 찬 큐가 완전히 비워지지 않는다. backlog를 줄이려면 처리량에 여유를 두거나 유입을 제한해야 한다. 숫자는 가상 작업 수이며 실제 서버의 QPS 측정이 아니다.

각 큐의 정책과 예산을 별도로 정한다

저장소포화 시 선택빠뜨리기 쉬운 조건
세션 송신 링kWouldBlock 뒤 유계 재시도·갱신 합치기·종료수락한 메시지를 다시 넣어 중복시키지 않는다.
raw 이벤트 큐framed TCP에서는 disconnectraw chunk 폐기는 프레이밍을 깨뜨릴 수 있다.

대기 항목 수뿐 아니라 payload 바이트, 실행 중 작업, 결과 큐와 재시도 보관량을 합산한다. “네트워크는 유계 큐다”라는 말만으로 프로세스 전체가 유계가 되는 것은 아니다. 빠진 큐가 메모리와 지연의 실제 상한을 결정할 수 있다.

현재 예제에서 더 큰 게임으로 넘어간다

Chat의 PlayerMap은 index로 찾은 뒤 ID 전체를 비교한다. 룸 방송은 모든 shard에 메시지를 복사한다. 상태 소유권이 분명한 입문 구조지만 룸마다 전용 actor, 여러 서버 간 이동, 영속 사용자 인증이나 관심 영역 필터링은 구현되어 있지 않다. 이런 기능을 추가할 때 현재 단일 프로세스의 원자적 fanout을 서버 간 원자성으로 확장했다고 주장하지 않는다.

예를 들어 room actor를 도입하면 세션 shard와 room actor 사이의 메시지 순서, 참가·퇴장 경쟁과 mailbox 포화를 새로 정의해야 한다. 분산 DB 결과를 붙이면 timeout과 중복 결과를 처리해야 한다. 새 설계가 유리한 이유뿐 아니라 메모리·잠금·재시도·장애 복구 비용도 함께 비교한다.

업무 큐까지 포함해 종료를 확장한다

transport 생산 중지 → close와 game input 배출 → 외부 작업 결과·broadcast 배출 → Player 정리 → 게임 워커 join을 애플리케이션의 실제 의존 관계에 맞게 정한다. DB 작업이 계속 새 결과를 만든다면 게임 input이 비었다고 끝낼 수 없다. 실행 중 작업 카운터와 중단·기한 정책을 설계한다.

이 확장의 테스트에는 오래된 ID 결과, 중복 요청, 큐 포화, 종료 중 결과 도착과 부분 fanout을 포함한다. 현재 라이브러리 테스트와 Chat E2E 통과는 아직 구현하지 않은 DB·room actor의 인수를 뜻하지 않는다. 새로운 기능을 추가할 때 코드, 설명용 모델과 실제 시나리오를 각각 검증한다.

배압과 유계 저장소

Send 링은 세션당 send_buffer_bytes다. 공간 부족이면 kWouldBlock이며 수락하지 않은 메시지는 호출자가 소유한다. 게임 워커에서 상한 있는 retry queue, rate limit 또는 kOverloaded close를 선택한다. callback 안의 무한 retry는 완료를 처리할 워커를 막는다.

adapter는 shard별 events_per_shard slot과 slot별 max_payload_bytes를 기동 시 확보한다. raw OnData는 조각으로 나누므로 큰 TCP coalesce를 큰 메시지로 오판하지 않는다. 조각 자체는 메시지가 아니므로 게임 워커에서 framing한다.

정책포화 동작
kDisconnect거절된 chunk가 생기면 CloseRequest를 호출하고 입력은 소비한다. framed TCP에 사용한다.
kRejectNewest거절된 raw chunk를 소비·폐기하는 손실 정책이다. 뒤 바이트의 framing을 깨뜨릴 수 있어 framed TCP에 사용하지 않는다.

close는 폐기하지 않는다. 링 포화 시 세션별 사전 확보 gate에 parked close를 저장하고 선행 이벤트를 소비한 뒤 전달한다. 해당 index의 새 generation connected는 이전 close가 전달될 때까지 거절한다. event_queue_depth는 링과 parked close를 모두 포함하므로 events capacity보다 클 수 있다. 이 보호가 애플리케이션 Player 상태를 자동 정리한다는 뜻은 아니다.

transport close 제어는 세션당 mailbox 하나와 worker당 최대 64개 batch다. 중복 close를 합치고 아직 outstanding인 세션은 다시 보류한다. Chat broadcast inbox도 shard당 1024개로 유계이며 모든 shard에 넣을 공간이 없으면 발신자를 overload close한다.

adapter.metrics의 depth/high_watermark/rejections와 Server.Metrics의 send_would_block을 따로 관찰한다. EstimatedMemoryBytes는 slot payload·gate·parked index 등의 추정이며 allocator·mutex·thread stack·kernel 비용은 process 계측으로 확인한다.

queue 포화 정책을 선택한다

유계 큐는 소비자가 느릴 때 저장량을 무한히 늘리지 않는다. 현재 adapter 정책은 kDisconnect와 kRejectNewest다. 전자는 실패한 chunk에서 close를 요청하고 입력을 소비한다. 후자는 수락하지 못한 raw chunk도 소비해 버리는 손실 정책이다.

TCP가 바이트를 순서대로 전달해도 애플리케이션이 중간 chunk를 버리면 프로토콜 스트림은 복구되지 않는다. 길이 prefix 일부가 사라지면 뒤 payload가 다음 길이처럼 읽힌다. 따라서 framed TCP 입력에는 kDisconnect를 사용한다.

kRejectNewest를 패킷 단위 최신값 교체로 오해하지 않는다. 현재 정책은 raw chunk 단위다. 게임의 위치 갱신을 합치려면 먼저 패킷을 안전하게 해석한 뒤 game command queue에서 객체별 최신값으로 대체하는 별도의 구조가 필요하다.

queue capacity는 burst와 처리 속도, 허용 지연으로 정한다. 크게만 늘리면 메모리와 대기 시간이 늘어난다. producer와 consumer의 장기 속도가 다르면 유한 capacity로 해결되지 않으므로 연결 제한이나 application 작업량 제한도 필요하다.

queue 포화 정책을 선택한다: 적용한다

소비자를 잠시 멈춰 큐를 채운 뒤 Data를 더 넣는다. kDisconnect는 close callback이 호출되는지, kRejectNewest는 rejected와 소비량이 증가하는지 확인한다. 손실 후 정상 framed stream을 이어서 처리한다고 가정하지 않는다.

송신 링 포화와 이벤트 큐 포화는 서로 다른 계층이다. 같은 overloaded reason을 쓰더라도 지표에서 어느 queue가 찼는지 분리해야 게임 처리 병목과 느린 클라이언트를 구별할 수 있다.

실습에서 관찰할 값

  • 포화 시 메모리 상한이 유지되는지 본다.
  • raw loss 정책을 패킷 drop 정책과 구분한다.
  • rejection 원인을 계층별로 기록한다.

게임 기능을 경계 안에서 확장한다

이 라이브러리를 게임 서버에 붙일 때 transport를 월드 처리 스레드처럼 쓰지 않는다. 이동, 전투와 거래는 game command로 바꾸고 Player 또는 room owner에게 전달한다. DB와 파일 작업은 별도 executor에 넘겨 결과를 같은 owner에 돌려준다.

새 protocol type을 추가하면 wire 문서, C++ helper, C# encoder/decoder와 fixture를 함께 바꾼다. version 변경과 unknown type 정책을 먼저 정한다. 필드 범위, 문자열 byte 길이와 phase 검사를 기존 패킷과 같은 기준으로 적용한다.

재접속, retry와 중복 요청은 TCP 순서만으로 해결되지 않는다. SessionId는 연결 정체성을 지키고 game request id는 같은 연결의 작업 의미를 지킨다. 거래 결과를 재시도할 때 중복 적용되지 않는 저장 계약은 네트워크 라이브러리 밖의 설계다.

TLS, 인증, IPv6, 여러 노드와 운영 보안은 현재 구현 기능으로 설명하지 않는다. 필요하다면 별도 설계·검증 단계로 추가한다. 공개 API 변경은 예제와 README, source atlas와 tests를 갱신해야 독자가 실제 코드를 따라갈 수 있다.

게임 기능을 경계 안에서 확장한다: 적용한다

실습 과제로 type 5 “상태 조회”를 설계한다. 먼저 input payload와 response, 허용 phase, 크기와 오류를 표로 정한다. 그다음 확정 fixture를 만들어 양 언어와 실제 server의 응답을 비교한다. 이 기능은 현재 코드에 구현되어 있지 않다.

두 번째 과제는 느린 DB 완료가 reconnect 후 돌아오는 상황이다. 옛 SessionId의 결과를 버리고 새 Player가 유지되는지 확인한다. 성공 시나리오만 만드는 것보다 취소와 stale 결과를 먼저 설계하면 경계가 명확해진다.

실습에서 관찰할 값

  • 새 type의 문서와 fixture를 같이 만든다.
  • 네트워크 callback에서 긴 작업을 하지 않는다.
  • 연결 세대와 게임 요청 의미를 따로 검증한다.

생각하고 확인한다

새 게임 기능의 구현 완료를 판단할 때 무엇을 확인해야 하는가.

입력과 상태 검사, 정상 결과, duplicate와 cancel, stale session, queue full, shutdown 중 작업과 실제 client 호환을 확인한다. 빌드 성공만으로 게임 의미와 비동기 수명이 맞는지 확정할 수 없다.
