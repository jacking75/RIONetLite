완료된 바이트만 소비하고 나머지를 다시 보낸다

지도에서의 위치는 이 장의 쉽게 말하면 상자에서 설명한다.

요청 하나가 끝났다는 사실과 메시지 전체의 송신이 끝났다는 사실을 분리한다. 카운터가 0이 된 순간에도 링에는 보내지 못한 바이트가 남을 수 있다.

심화큰 그림에서의 위치: P02 ④ 송신

쉽게 말하면 4바이트를 보내 달라고 했는데 2바이트만 보냈다는 완료가 오는 경우다. 보낸 2바이트만 링에서 지우고 나머지를 다시 보낸다. 처음부터 다시 보내면 중복되고, 전부 지우면 데이터가 사라진다.

처음 읽는다면 첫 절과 L11 실험만 보고, 나머지 절은 송신 코드를 고칠 때 읽는다.

4바이트를 게시했는데 완료는 2바이트다

송신 링의 현재 읽기 위치가 0이고 rio! 네 바이트를 요청에 연결했다고 가정한다. 등록 메모리는 이 요청이 참조하는 동안 유지되어야 한다. 완료 이벤트가 2바이트를 보고하면 앞의 ri만 완료된 것이다. 읽기 위치를 4로 옮기면 뒤의 o!를 보내지 않고 버리게 된다. 반대로 읽기 위치를 그대로 두고 네 바이트를 다시 보내면 이미 완료된 앞부분을 중복 전송한다.

현재 구현은 완료된 두 바이트만 링에서 소비하고 나머지를 새 요청으로 게시한다. 그 사이에 애플리케이션이 더 보낸 데이터가 있다면 나머지와 새 데이터를 함께 게시할 수 있다. 이번 실험은 새 메시지 추가를 생략한 가장 작은 사례다. 새 데이터와의 병합은 C14에서 다룬다.

먼저 예측해 보기 · 4바이트 요청에서 2바이트만 완료됐다. 무엇을 하는가?

2바이트를 소비하고 남은 구간을 재게시한다 — offset·remaining·outstanding을 함께 본다. L11에서 2+2 완료를 실행한다.

컨텍스트 정리와 링의 진행 위치를 나눈다

그림으로 보기 · 4바이트를 2+2로 완료한다에서 먼저 상태를 바꾸어 본다. 아래 코드와 표는 이 그림의 조건을 세부로 읽는다.

먼저 결론 · 이 송신의 컨텍스트인지와 완료 길이가 유효한지를 먼저 확인한다. 잘못된 완료를 링에서 소비한 것으로 만들지 않는다.

부분 송신 완료 뒤 남은 구간을 다시 게시한다의 순서는 이어지는 본문과 실제 코드에서 확인한다.

SendImmediately::Completed는 lock 안에서 전달받은 포인터가 자신의 send_context_인지 확인하고 CompleteSend(transferred)로 크기를 검사한다. 정상 크기라면 컨텍스트의 Offset과 Length를 일단 완료된 만큼 조정한다. 그 뒤 Retire로 이 요청을 idle 상태로 되돌리고 등록 버퍼의 outstanding 참조를 하나 줄인다.

진행 상태의 원본은 컨텍스트에 남겨 둔 이전 요청 길이가 아니라 송신 링의 읽기 위치와 미소비 바이트다. 완료 크기만큼 IncremantReadPos를 호출한 뒤 데이터가 남아 있고 게시를 허용하면 PreparePostLocked가 현재 링 전체의 미소비 범위로 새 컨텍스트를 만든다. 따라서 Retire 직후 Offset이 0으로 초기화되더라도 나머지를 처음부터 잘못 보내는 것은 아니다.

관찰 시점링 읽기 위치새로 게시한 길이등록 버퍼 outstanding
최초 4바이트 게시 뒤041
2바이트 완료와 재게시 뒤221
마지막 2바이트 완료 뒤400

실험은 완료 처리 함수 한 번의 결과를 보여 준다. 내부에서는 이전 요청을 retire하며 카운트가 0이 된 뒤 새 요청을 준비하며 다시 1이 된다. 화면의 1은 그 중간 순간이 없었다는 뜻이 아니다. 링이 wrap하면 물리 읽기 위치는 링 크기로 나머지를 취하고, double mapping이 경계를 넘는 연속 구간을 제공한다. 이번 실험의 offset은 작은 비순환 예에서의 소비 위치다.

세션당 요청 하나가 병합의 경계가 된다

현재 송신기는 한 세션의 진행 중인 RIO 송신을 한 개로 제한한다. 이미 요청이 있으면 PostSendScatter는 새 데이터를 링 뒤에 복사하고 바로 돌아간다. 완료 처리에서 그때까지 쌓인 범위를 한 요청으로 다시 게시한다. 애플리케이션의 여러 Send 호출과 RIO 게시 호출은 일대일 관계가 아니다.

예를 들어 aa를 먼저 게시하고, 완료 전에 bbb와 cccc를 추가하면 첫 게시 길이는 2이고 다음 게시 길이는 7이다. 해당 단위 테스트는 실제 fake RIO가 받은 RIO_BUF의 길이와 바이트를 확인한다. 병합으로 시스템 호출을 줄이는 이 구조가 애플리케이션 패킷의 길이 헤더를 바꾸는 것은 아니다. 스트림 안의 바이트 순서는 그대로다.

0바이트와 과대 완료를 성공으로 소비하지 않는다

RioIoContext::CompleteSend는 완료 크기가 0이거나 현재 Length보다 크면 false를 반환한다. 과대 완료를 읽기 위치에 더하면 미전송 데이터나 버퍼 경계를 넘어설 수 있다. 정상적인 부분 완료의 범위를 명확히 제한해야 한다.

실제 I/O 워커는 0바이트 완료를 앞의 전용 분기에서 처리한다. 수신의 0바이트는 peer FIN 경로이며, 송신의 0바이트는 SendFailed와 연결 종료 경로다. 실험의 0바이트 동작은 “송신 요청을 실패로 정리하고 바이트를 소비하지 않는다”는 결과를 모델링한다. 모든 실제 경로에서 Completed를 호출한다고 설명하지 않는다.

유효하지 않은 완료에서 FailUnlocked는 진행 요청의 참조를 정리하지만 링의 읽기 위치를 완료된 것처럼 옮기지 않는다. 그래서 outstanding은 0이고 remaining은 4인 상태가 가능하다. 이는 전송 성공도 아니고 모든 데이터가 상대에 도착했다는 증거도 아니다. 상위 워커는 오류를 연결 종료에 연결한다.

재게시가 실패해도 완료된 앞부분은 되돌리지 않는다

두 바이트 완료를 반영한 뒤 나머지 재게시가 실패할 수 있다. PreparePostLocked는 컨텍스트와 outstanding을 먼저 준비한다. lock 밖에서 실행하는 IssuePost의 RIO Send가 false를 반환하면 Failed가 이번 게시의 참조를 롤백하고 kSEND_IO_FAIL을 반환한다. 실패한 게시에 나중의 성공 완료를 만들어 카운트를 맞추지 않는다.

앞의 두 바이트 완료는 이미 사실이므로 링 읽기 위치는 2다. 나머지 두 바이트는 링에 남지만 진행 요청은 없다. 이 상태를 “다시 처음 네 바이트를 보내면 된다”고 처리하면 앞부분이 중복될 수 있다. 현재 라이브러리는 게시 실패를 상위 오류로 전달해 연결을 닫는다. 애플리케이션 재시도는 연결과 프로토콜의 요청 식별을 고려해 별도로 설계한다.

syscall 실행 수와 미완료 I/O 수는 다르다

posts_in_flight_는 lock 밖에서 RIO Send를 호출하는 동안 요청 큐의 수명을 보호한다. BeginClose는 lock 안에서 새 게시를 막은 뒤 이 카운트가 0이 될 때까지 기다린다. syscall이 반환되어 이 값이 0이 되어도 운영체제가 아직 등록 버퍼를 참조할 수 있다. 그 참조는 등록 버퍼의 outstanding()으로 따로 관리한다.

이 구분 없이 “Send 호출이 반환했으니 소켓과 버퍼를 모두 지워도 된다”라고 판단하면 완료 전 메모리를 해제할 수 있다. 반대로 모든 종류의 카운트를 하나로 합치면 누가 무엇을 기다리는지 알기 어려워진다. lock은 짧은 상태 변경을 보호하고, syscall 실행과 완료 회수는 각자의 조건으로 추적한다.

실험의 버퍼 해제 버튼은 이 단일 송신 참조만 검사한다. 실제 서버에서는 신규 게시 차단, 수신 요청, 요청 큐, 완료 큐와 워커의 수명을 모두 확인해야 한다. C17의 타임아웃 경로는 참조가 남으면 메모리와 CQ를 의도적으로 보존할 수 있다. 이를 정상적인 해제 성공으로 표시하지 않는다.

보낸 양과 접수한 양을 지표에서 구분한다

send_operations는 애플리케이션 Send 수락 횟수이며 RIOSend 횟수가 아니다. queued_send_bytes는 수락한 누적 바이트이지 현재 링 사용량이 아니다. sent_bytes는 성공 완료의 바이트 수이며 상대 애플리케이션 ACK가 아니다. 세 값을 같은 시점의 같은 단위로 취급하지 않는다.

수신 측이 느려 링이 차면 send_would_block이 늘 수 있다. 이미 수락한 메시지를 다시 Send하는 것으로 대응하면 중복이 생긴다. 수락하지 않은 메시지에만 애플리케이션의 유계 재시도 또는 종료 정책을 적용한다. 지표 조회는 여러 atomic의 eventually consistent snapshot이므로 순간 차이를 모두 버퍼 누수로 단정하지 않는다.

구간·참조·실패를 다른 검사로 확인한다

RepostsOnlyTheRemainderAfterPartialCompletion은 두 번째 RIO_BUF의 Offset이 원래 위치보다 2 크고 Length가 2인지 확인한다. TracksPostRollbackPartialAndFinalCompletion은 컨텍스트의 범위 검사와 retire를 확인한다. RollsBackOutstandingWhenPostFails는 fake RIO의 게시 실패 뒤 참조가 0인지 확인한다. 마지막 검사는 부분 완료 뒤의 실패만을 독립적으로 실행하는 테스트는 아니므로, JS의 재게시 실패 사례와 적용 범위를 구분한다.

bin\tests\x64\Debug\RIONetLite.UnitTests.exe --gtest_filter=SendQueueTest.*:IoContextTest.*:RioRequestTest.*
bin\tests\x64\Release\RIONetLite.UnitTests.exe --gtest_filter=SendQueueTest.*:IoContextTest.*:RioRequestTest.*
npm.cmd --prefix tools/book run test:models

정상 2+2뿐 아니라 0, 현재 길이보다 큰 완료, 재게시 실패, 완료 전 해제 시도도 확인한다. 이전 단계와 JSON 내보내기를 사용하면 같은 초기값과 동작을 다시 실행할 수 있다. 모델에서 맞는 숫자를 본 사실은 실제 운영체제의 드문 부분 완료를 강제로 발생시켰다는 증거가 아니다.

송신 링과 부분 완료를 이어 붙인다

SendImmediately는 세션당 한 in-flight 송신을 유지한다. 애플리케이션 Send는 spinlock 아래 generation, accepting flag와 링 용량을 확인하고 바이트를 복사한다. 이미 요청이 진행 중이면 새 요청을 만들지 않고 기존 완료가 이어서 게시하도록 둔다.

PreparePostLocked는 현재 used 구간을 context에 기록하고 outstanding와 posts_in_flight를 증가시킨다. 실제 RIOSend syscall은 잠금 밖에서 실행한다. 짧은 잠금 범위를 유지하면서 posts_in_flight가 RQ를 사용하는 게시 동작의 수명을 보호한다.

Completed는 context 정체성과 transferred 범위를 확인한 뒤 실제 전송량만 read 위치를 옮긴다. 요청한 전체 길이보다 작으면 남은 바이트를 다시 게시한다. 부분 완료를 무조건 오류로 닫거나 원래 길이 전체를 소비하면 바이트가 누락된다.

BeginClose는 accepting_posts를 끄고 이미 시작한 syscall 게시가 끝날 때까지 기다린다. in-flight 완료와 syscall 실행 중이라는 두 개념은 다르다. 전자는 등록 버퍼 수명, 후자는 request queue 접근 수명과 관계가 있다.

송신 링과 부분 완료를 이어 붙인다: 적용한다

100바이트 요청이 37바이트 완료되면 링에는 앞부분을 뺀 63바이트가 남는다. 그동안 다른 Send로 20바이트가 쌓였다면 다음 요청은 남은 83바이트를 포함할 수 있다. 순서는 원래 바이트 순서다.

header와 payload를 동시에 보내는 두-span API를 여러 스레드에서 호출한다. 전체 수락을 같은 lock으로 보호해 header A와 payload B가 섞이지 않는지 확인한다. 클라이언트의 TCP 분할과 송신 메시지 원자 수락을 혼동하지 않는다.

실습에서 관찰할 값

  • 완료량이 posted length 이내인지 본다.
  • 남은 바이트가 재게시되는지 본다.
  • BeginClose와 IssuePost 수명 카운트를 연결한다.

생각하고 확인한다

링에 쌓인 byte 수와 outstanding 요청 수가 왜 다른가.
