수락한 양과 완료한 양을 따로 관찰한다

누적 카운터·현재 gauge·시간 합계는 서로 다른 단위다. 한 숫자보다 요청 문맥과 변화 추세를 함께 읽는다.

중급큰 그림에서의 위치: P02 운영과 문제 해결

쉽게 말하면 로그와 지표로 서버 안을 들여다보는 방법이다. “Send가 받아 준 양”과 “실제로 보낸 양”처럼 비슷해 보이지만 단위와 시점이 다른 숫자를 구분한다.

처음 읽는다면 연결·바이트·연산의 단위를 나눈다 표를 먼저 본다.

로그 문맥과 문자열 수명을 보존한다

LogEvent는 timestamp_unix_ns, level, component, worker, SessionId, operation, ErrorCode, native_error와 message를 전달한다. 실패한 expected의 category·code·native_code·field·message와 이 로그를 함께 저장하면 설정 오류, bind 실패와 게시 오류를 구분하기 쉽다.

component·operation·message는 string_view다. Log 호출이 끝난 뒤 포인터만 비동기 큐에 저장하지 않는다. 필요한 문자열을 복사해 로깅 워커로 넘긴다. accept·I/O·생명주기에서 동시에 호출될 수 있으므로 sink의 공유 버퍼도 보호한다. 파일 I/O를 네트워크 콜백에 붙이지 않는다.

Log 예외는 브리지가 격리한다. IsEnabled는 noexcept이므로 그 안에서 예외를 던지는 구현을 만들지 않는다. wall-clock timestamp는 사건의 문맥을 찾는 값이지 게임 이벤트의 엄격한 전역 순서를 증명하는 번호가 아니다. 작업 식별과 adapter sequence도 함께 본다.

연결·바이트·연산의 단위를 나눈다

지표단위와 의미잘못된 해석
accepted_connections / closed_connections서버 인스턴스의 누적 통지 수현재 연결 수가 아니다.
active_connections현재 활성 연결 gauge매 snapshot에서 accepted-closed와 엄격히 동시에 읽힌 값은 아니다.
rejected_connectionsaccept·슬롯/setup 거절 기록공개 OnRejectedConnection 핸들러가 있다는 뜻이 아니다.
received_bytes / receive_operations브리지의 수신 처리에 기록한 새 바이트와 호출 수미소비 꼬리를 매번 새 수신량으로 더하지 않는다.
queued_send_bytes / send_operationskQueued로 수락한 누적 바이트와 Send 호출 수현재 송신 링 사용량이나 RIO 게시 수가 아니다.
sent_bytes정상 status의 송신 완료 바이트상대 애플리케이션 ACK가 아니다.
send_would_block / stale_operations / protocol_errors배압·오래된 ID·프로토콜 오류의 누적 기록서로 같은 원인의 카운터가 아니다.
close_peer / close_application / close_error원인별 누적 닫힘. 서버 정지는 application에 포함모든 CloseReason이 독립 카운터는 아니다.
corrupt_completion_queuesCQ 손상 관찰정상 처리량 표에 숨길 수 없다.

received_bytes는 정상 브리지 경로에서 이전 미소비 크기를 빼고 새 바이트를 계산한다. OnData 예외처럼 조기 반환하는 분기는 계측 경로도 달라질 수 있다. 모든 커널 완료 바이트를 예외와 무관하게 무조건 합산한 packet capture라고 설명하지 않는다. 이상을 조사할 때 실제 로그와 workload 결과도 함께 본다.

adapter snapshot은 별도로 읽는다

event_queue_depth는 링과 parked close를 합친 현재 저장량이다. high_watermark는 최고 저장량, rejections와 dequeued는 누적 거절·소비 수다. wait_total_nanoseconds와 wait_max_nanoseconds는 큐 대기 시간이다. 데이터 slot의 대기는 enqueued_at, parked close의 대기는 parked_at을 기준으로 기록한다.

Server::Metrics는 QueuedEventAdapter::metrics를 자동 합치지 않는다. Server snapshot의 event_queue 계열은 0이고 adapter를 별도 조회해야 한다. Server의 enable_metrics=false로 adapter 계측까지 꺼졌다고 판단하지 않는다. 큐 depth가 slot 용량보다 큰 경우도 parked close 때문에 가능하다.

TryPop의 kDestinationTooSmall은 이벤트를 제거하지 않으므로 dequeue 수가 늘지 않는다. 게임 워커의 실행 중 작업은 dequeue 후에도 남을 수 있다. shutdown에서 depth 0과 “아무 작업도 실행 중이지 않다”를 구분한다.

시간 계측과 비활성 옵션을 구분한다

callback_count, callback_total_nanoseconds와 callback_max_nanoseconds로 기록된 콜백의 평균·최댓값을 본다. 현재 구현은 steady_clock을 사용한다. OnData 예외의 조기 반환 등 기록 경로가 다르므로 이 count를 모든 콜백 진입의 완전한 감사 로그로 쓰지 않는다. 평균은 total/count이며 count 0에서 나누지 않는다.

enable_metrics=false면 Server::Metrics는 0 snapshot을 반환한다. enable_callback_timing=false는 콜백의 clock 계측을 생략하며 다른 서버 카운터를 끄지 않는다. Echo의 --observability off는 Logger와 Server metrics를 끄는 예제 옵션이다. 관측을 켠 실행과 끈 실행을 성능 비교에서 섞지 않는다.

한 번의 항등식보다 추세와 근거를 본다

스냅샷은 여러 atomic을 차례로 합치므로 동시에 고정된 전역 상태가 아니다. 순간 queued-sent 차이가 곧 메모리 누수라는 결론은 성립하지 않는다. 입력률, 처리률, outstanding, 큐 깊이와 종료 여부를 시간에 따라 기록한다. 종료가 송신을 취소하면 수락한 누적 바이트가 완료 바이트보다 큰 채 끝날 수도 있다.

callback 시간과 큐 대기가 함께 늘면 애플리케이션 처리 지연을 조사한다. 배압이 늘지만 callback은 짧다면 느린 상대 수신이나 send 링 예산도 확인한다. CPU가 높다는 증상 하나로 polling, 무한 재시도와 실제 업무 부하 중 하나를 바로 원인으로 고르지 않는다.

로그와 지표

Logger.Log(LogEvent)는 timestamp(ns), level, component, worker, SessionId, operation, library/native error를 전달한다. callback/accept/lifecycle 등에서 동시 호출할 수 있다. string_view는 Log 동안만 유효하므로 비동기 logger queue에 저장하려면 복사한다. Log 예외는 격리한다. IsEnabled는 noexcept이고 짧게 반환한다. 파일 I/O는 별도 logging worker로 넘긴다.

지표의미
accepted/closed_connections누적 연결·종료 수다.
active_connections현재 활성 연결 gauge다.
received_bytes수신 완료로 들어온 누적 바이트다.
queued_send_byteskQueued로 수락한 누적 바이트다. 대기 queue gauge가 아니다.
sent_bytes성공한 RIO send completion의 누적 바이트다. 상대 ACK가 아니다.
send_operations수락한 Send 호출 수다. RIO 게시·완료 수와 다르다.
send_would_block/stale_operations/protocol_errors배압·오래된 ID·protocol 실패 누적이다.
callback_*count·total/max ns다. total/count로 평균을 구한다.
adapter event_queue_depth링과 parked close를 포함한 현재 gauge다.
adapter high_watermark/rejections/dequeued/wait_*최고 저장량·거절·소비 수와 total/max 대기 ns다.

Server.Metrics와 adapter.metrics는 별도 snapshot이다. Server의 event_queue 필드는 0이고 adapter가 제공한다. 여러 atomic을 합친 eventually consistent 조회이므로 순간 항등식으로 오류를 판정하지 않는다.

enable_metrics=false는 Server 지표를 0으로 반환한다. enable_callback_timing=false는 callback_*만 생략한다. adapter 계측은 별도로 유지된다. Echo --observability off는 Server metrics와 Logger를 끈다.

오류 조사 시 Error.code/native_code/field/message와 LogEvent.operation을 같이 남긴다. 예를 들어 bind_failed와 native 10048은 사용 중인 포트다. native 0은 플랫폼 원인이 제공되지 않은 오류일 수 있다. 문제 해결을 따른다. 성능 비교는 검증 안내의 동일 장비·설정·correctness 조건을 따른다.

지표는 수락과 완료를 따로 센다

queued_send_bytes는 kQueued로 수락한 누적 byte 수다. 이름에 queued가 들어 있어도 현재 대기량 gauge가 아니다. sent_bytes는 성공한 RIO send completion byte 수이며 peer의 application acknowledgement는 아니다.

send_operations는 공개 Send 수락 호출 수다. 링 coalescing으로 여러 호출을 한 요청으로 게시할 수 있으므로 RIO syscall 수나 CQ result 수와 다르다. received_bytes는 미소비 꼬리를 다시 전달할 때 중복으로 세지 않도록 pending byte를 고려한다.

Server::Metrics는 worker별 atomic을 합친 eventually consistent snapshot이다. 조회 중 callback이 진행되면 accepted, active, closed가 서로 다른 순간의 값일 수 있다. 순간 항등식 한 번만으로 정합성 오류를 확정하지 않는다.

adapter.metrics는 event queue depth, high watermark, rejection, dequeue와 wait timing을 별도로 제공한다. Server snapshot의 event queue 필드는 0이다. enable_metrics=false는 Server 지표를 0으로 만들고 callback timing은 별도 선택이며 adapter 계측과 구분한다.

지표는 수락과 완료를 따로 센다: 적용한다

100바이트를 수락한 뒤 종료로 일부 output이 취소되면 queued_send_bytes가 sent_bytes보다 클 수 있다. 이 차이만으로 송신 링이 그만큼 현재 남아 있다고 계산하지 않는다. 현재 링 대기량을 알고 싶다면 별도의 gauge 계약을 설계해야 한다.

callback 평균은 total_nanoseconds/count로 계산한다. max는 관찰 최대이며 percentile이 아니다. queue wait도 평균·최대만으로 긴 꼬리를 완전히 설명하지 못하므로 운영에서 histogram이 필요하면 추가 계측 경로를 설계한다.

  • Server와 adapter snapshot을 함께 관찰한다.
  • 수락·완료·application ACK를 구분한다.

로그의 native 오류와 수명을 보존한다

LogEvent에는 timestamp, severity, component, worker, SessionId, operation과 library/native error가 들어 있다. “send failed”만 남기는 것보다 어느 세대의 어느 작업이 어떤 Windows 오류였는지 알 수 있어야 지연된 완료를 구별할 수 있다.

LogEvent의 string_view는 Log 호출 동안만 유효하다. 비동기 logger가 이벤트를 큐에 넣으려면 component, operation과 message를 복사한다. span과 마찬가지로 보기 객체는 소유권이 아니다.

Logger는 lifecycle, accept와 I/O callback 경로에서 동시 호출될 수 있다. 파일에 바로 쓰는 logger는 callback 시간을 늘리므로 별도 logging worker와 유계 큐를 고려한다. logger 큐가 full일 때의 정책도 정의해야 관측이 새 병목이 되지 않는다.

native 10048과 BindFailed 조합은 사용 중인 포트의 단서다. native 0은 플랫폼 오류가 제공되지 않았을 수도 있다. code, field, operation과 환경을 같이 본다. 추측한 재시작만 반복하지 않고 작은 입력으로 원인을 재현한다.

로그의 native 오류와 수명을 보존한다: 적용한다

포트를 점유한 상태에서 둘째 Create를 실행해 code와 native_code를 확인한다. 그 후 포트를 바꾸면 성공하는지 비교한다. 이 과정은 thread 수나 buffer 크기를 임의로 바꾸는 것보다 원인 계층을 좁히기 쉽다.

비동기 sink 실습에서는 LogEvent를 그대로 저장하지 말고 소유 문자열 record로 바꾼다. 종료 시 logging queue를 네트워크 자원보다 언제 배출할지 정한다. 마지막 stop error를 기록할 logger가 먼저 사라지면 진단이 빠진다.

실습에서 관찰할 값

  • 오류 지점의 native 값을 즉시 저장한다.
  • 비동기 로그가 view를 복사하는지 본다.
  • logger 수명이 Server보다 긴지 확인한다.

생각하고 확인한다

계측 snapshot 정의

include/rionetlite/metrics.h

이 헤더는 transport와 adapter가 사용하는 지표 타입을 정의한다. 같은 struct를 쓰지만 실제 생산자가 다르다. Server에서 queue 값이 항상 0인 이유는 adapter 계측이 별도 객체에 있기 때문이다.

누적 값과 현재 상태 값을 구분한다. accepted와 sent는 누적 counter이고 active와 event_queue_depth는 gauge다. queued_send_bytes는 이름과 달리 현재 대기 byte가 아니다.

정확한 원자 snapshot이 아니라 eventually consistent 합산이다. 값의 단위와 의미를 운영 dashboard 이름에 유지해야 잘못된 경보와 성능 해석을 줄일 수 있다.

이 파일에서 추적할 연결

  • Server::Metrics의 worker 합산을 읽는다.
  • adapter.metrics의 gate depth를 확인한다.
  • observability 문서의 counter/gauge 표와 비교한다.

독해 포인트

sent_bytes는 성공 RIO 완료, queued_send_bytes는 공개 수락의 누적 byte다. 차이를 현재 queue gauge나 상대 ACK로 해석하지 않는다.

depth에는 ring뿐 아니라 parked close도 들어간다. wait total/max는 ns이고 average를 계산할 때 dequeued count와 사용 범위를 확인한다.

연결해서 읽기: Server::Metrics의 worker 합산을 읽는다.
