공개 API의 경계를 지킨다

지도에서의 위치는 이 장의 쉽게 말하면 상자에서 설명한다.

애플리케이션은 소켓과 CQ를 직접 소유하지 않는다. 대신 핸들러 수명, 호출 시점, 데이터 범위와 비동기 반환값의 의미를 지켜야 한다.

중급큰 그림에서의 위치: P02 공개 API 세 가지

쉽게 말하면 P02에서 본 ServerConfig·EventHandler·Server의 사용 규칙을 정확히 정리한다. 객체를 만드는 순서, 핸들러가 살아 있어야 하는 기간, Send의 성공이 “보냈다”가 아니라 “맡았다”라는 뜻인 이유, Stop을 콜백 안에서 부르면 안 되는 이유를 다룬다.

처음 읽는다면 각 절의 첫 문단만 읽고 넘어가도 된다. 반환값 전체 목록은 필요할 때 A01에서 찾는다.

Create와 Start의 실패를 분리한다

그림으로 보기 · 단계 버튼으로 요청과 상태가 바뀌는 순서를 확인한다. 다음 코드 설명은 이 그림의 해당 단계를 구체적으로 읽는다.

먼저 예측해 보기 · Start 이전의 Send가 거절됐다. 무엇이 정상인가?

Running 상태에서만 송신을 접수한다 — 공개 Send의 상태 검사와 kClosing 반환을 확인한다.

Server::Create는 설정을 검증하고 내부 구현과 세션 자원을 초기화한다. 성공한 객체의 공개 상태는 kInitialized다. 생성 성공은 아직 accept와 I/O 워커가 실행된다는 뜻이 아니다. Start는 initialized 상태에서만 시작하며 내부 워커를 시작하기 전에 kRunning을 공개한다. 시작 중 콜백이나 동시 조회에서 이 상태를 볼 수 있다. 중간 실패는 진입자를 배출하고 rollback한 뒤 kStopped가 되므로 새 객체로 재시도한다.

공개 상태 enum에는 kCreated, kInitialized, kRunning, kStopping, kStopped가 있다. 이것은 세션의 Free·Active·Quarantined 상태와 다른 객체의 상태다. 라이브러리의 생성 과정에서 쓰는 내부 Created와 사용자가 받는 initialized 객체를 혼동하지 않는다. 정지한 객체를 다시 Start하는 재시작 계약은 제공하지 않으므로 새 서버를 만든다.

설정 오류는 std::expected의 Error로 반환한다. 설정 범위가 통과해도 실제 메모리나 플랫폼 자원 확보는 실패할 수 있다. bad_alloc 등 생성 과정 예외를 잡아 자원 오류로 바꾸는 경로가 있으므로 모든 실패를 “잘못된 port”로 단정하지 않는다. category, code, native_code, field와 message를 함께 보존한다.

Server는 이동만 되고 핸들러는 빌려 쓴다

Server는 복사할 수 없고 이동할 수 있는 타입이다. 내부 구현은 unique_ptr로 소유한다. 그러나 EventHandler&와 선택적인 Logger*는 외부 객체를 참조한다. 둘은 Server의 마지막 사용과 소멸이 끝날 때까지 유효해야 한다. 스택에서 선언 순서를 바꾸어 핸들러가 먼저 파괴되면 콜백이 이미 사라진 객체를 부를 수 있다.

여러 애플리케이션 스레드가 Send를 호출할 수 있다는 계약이 서버 객체의 이동이나 파괴까지 안전하게 만든다는 뜻은 아니다. 이동·파괴 전에 모든 애플리케이션 호출자를 끝낸다. 예제에서 주 스레드가 Stop하고 게임 워커를 정리한 뒤 객체를 파괴하는 순서에는 이 이유가 있다.

OnData의 span은 콜백이 반환할 때까지만 유효하다. 로거의 string_view도 Log 호출 동안만 유효하다. 다른 스레드에서 나중에 사용할 데이터와 문자열은 유효한 동안 복사한다. span이나 string_view를 컨테이너에 넣었다고 데이터 소유권이 생기지 않는다.

두 Send 오버로드는 내부 복사 계약이다

한 span을 받는 Send와 header·payload를 따로 받는 Send가 있다. 둘 다 반환 전에 내용을 내부 송신 링으로 복사한다. 두 span은 애플리케이션이 합치는 용도의 임시 vector를 만들지 않아도 되게 한다. 커널까지 zero-copy로 전송하거나 호출자의 두 span을 RIO 완료까지 계속 참조한다는 뜻은 아니다.

송신 크기 합계를 넓은 정수로 계산하고, 합계 0과 메시지 최대값 초과를 거절한다. 현재 서버가 running이 아니면 kClosing이다. 세션은 index와 generation으로 검증하며 링 공간이 부족하면 메시지 전체를 받지 않고 kWouldBlock을 반환한다. 즉시 결과의 모든 enum과 대응표는 A01에서 찾는다.

성공한 kQueued는 복사·접수의 성공이다. 상대방의 처리 완료는 별도 프로토콜로 확인한다. 같은 메시지를 수락했는지 모른 채 재시도하면 중복을 만들 수 있으므로 재시도 큐에는 반환값과 요청 식별을 함께 기록한다. 콜백 안의 무한 재시도는 완료를 처리할 워커를 막는다.

RequestClose는 요청이며 Stop은 소유 스레드의 작업이다

RequestClose는 세션 종료를 비동기로 요청한다. false는 서버가 running이 아니거나 유효하지 않은 세션 등 요청이 받아들여지지 않은 경우다. true여도 호출 반환 시점에 OnClosed가 이미 실행됐다는 뜻은 아니다. 세대가 일치해도 실제 활성 상태나 종료 경쟁 때문에 처리가 달라질 수 있다.

공개 CloseReason 전체가 RequestClose의 인자로 그대로 전달되는 것은 아니다. 현재 구현은 ProtocolError, Overloaded와 IdleTimeout을 명시적으로 내부 사유로 변환하고 나머지는 애플리케이션 요청으로 처리한다. PeerClosed 같은 네트워크 관찰 이유를 인자로 넣어 원격 FIN이 발생한 것처럼 만들지 않는다.

Stop은 graceful 또는 immediate로 서버 transport를 정리한다. 같은 서버의 이벤트·로거 콜백에서 호출하면 kInvalidState다. 이 경계는 콜백이 자신을 기다리는 join을 시작하지 않게 한다. 콜백은 플래그나 제어 메시지로 소유 스레드에 종료 의사를 전달한다. 동시·반복 Stop은 같은 종료 결과를 공유하며 첫 종료 소유자의 모드를 따른다.

스냅샷과 로그는 관찰용이다

state()는 생명주기 상태를 lock-free로 조회한다. Metrics()는 여러 워커의 atomic 카운터를 합친 eventually consistent snapshot이다. 조회 직후 상태가 바뀔 수 있으므로 state가 Running인 것을 보고 별도 검증 없이 내부 포인터를 사용하는 근거로 삼지 않는다. Send와 RequestClose의 반환값을 확인한다.

로거는 accept·I/O·생명주기 경로에서 동시에 호출될 수 있다. 로그 예외는 브리지가 격리하지만 느린 파일 I/O까지 대신 처리해 주지는 않는다. 로그 sink는 짧게 복사해 로깅 워커로 넘기는 구조를 선택할 수 있다. IsEnabled는 noexcept이므로 예외를 던지는 구현을 만들지 않는다.

Create와 Start의 실패를 분리한다

Create는 expected<Server, Error>를 반환한다. 성공하면 객체가 존재할 뿐 아니라 설정 검증, Winsock/RIO 준비, listen socket bind와 세션 풀 자원 확보가 끝난 Initialized 상태다. port 0으로 자동 포트를 받는 API가 아니므로 1..65535를 지정한다.

Start는 Initialized에서 accept와 I/O 워커를 시작한다. 내부적으로 Running 상태가 시작 진행 중에도 보일 수 있으므로 state snapshot을 readiness 프로토콜로 쓰지 않는다. Start 결과가 성공했는지 직접 확인한 뒤 외부 준비 상태를 알린다.

중간 실패는 생성한 CQ, 이벤트와 이미 실행한 스레드를 정리한다. Start 실패 후 객체는 Stopped가 되므로 같은 객체에 Start를 다시 호출하지 않는다. 자원이나 설정 문제를 해결하고 새 Create를 수행하는 것이 계약이다.

Error는 category, code, native_code, field와 message를 담는다. 포트 bind 실패에서는 WSAEADDRINUSE 같은 native 오류가 필요하다. native 오류는 실패 바로 뒤에 보관해야 후속 destructor나 다른 Windows 호출이 덮어쓰지 않는다.

Create와 Start의 실패를 분리한다: 적용한다

첫 서버가 port 32452를 사용 중인 상태에서 둘째 서버를 Create하면 bind가 실패한다. 이 실패는 워커 실행 전에 나온다. 포트를 바꿔 성공한 경우와 비교하고 Error의 category와 native_code를 관찰한다.

handler는 Create 이전에 만들고 서버에 부착할 포인터는 Start 이전에 연결한다. 초기 callback이 시작된 뒤 attach를 하면 첫 접속 이벤트에서 아직 준비되지 않은 애플리케이션 상태를 볼 수 있다.

실습에서 관찰할 값

  • Create 성공 상태가 Initialized인지 확인한다.
  • bind 실패의 native_code를 기록한다.
  • Start 실패 후 새 객체를 만드는지 확인한다.

아니다. state는 순간 관측이며 다른 스레드가 Stop으로 바꿀 수 있다. Send는 실제 진입 후 상태와 세션, 링 용량을 다시 확인하고 결과를 반환한다. 다음 행동은 snapshot이 아닌 API 결과로 결정한다.

Server 공개 계약

include/rionetlite/server.h

애플리케이션이 가장 먼저 읽을 헤더다. 소유 객체는 Server이고 실제 자원은 private Impl에 숨긴다. copy는 금지하고 move만 허용한다. handler와 logger는 borrowed reference이므로 서버보다 오래 살아야 한다.

Create는 expected 값에 성공 객체 또는 Error를 담고 Start/Stop은 expected<void, Error>를 반환한다. Send는 즉시 수락 결과, RequestClose는 비동기 요청 승자 여부를 반환한다. 결과 타입의 차이가 작업 의미의 차이다.

선언에 붙은 주석을 함수 이름보다 먼저 읽는다. thread-safe Send가 객체 파괴까지 안전하게 만든다는 의미는 아니다. callback에서의 lifecycle 호출과 quiescent destruction 조건을 찾는다.

이 파일에서 추적할 연결

  • src/server.cpp의 실제 상태 검사와 비교한다.
  • event_handler.h의 borrowed span 수명을 읽는다.
  • shutdown_coordinator.h의 종료 승자를 찾는다.

공개 Server와 transport의 연결

src/server.cpp

이 파일은 공개 계약을 실행한다. 설정을 legacy NetConfig로 바꾸고 callback·logger 예외를 격리하며 worker별 지표와 lifecycle 상태를 관리한다. transport 그 자체와 game 로직을 여기서 구현하지 않는다.

긴 파일은 네 구간으로 읽는다. CallbackScope와 변환 helper, WorkerMetrics와 Impl callback, Create/Start/Stop, Send/RequestClose/Metrics다. 잠금은 lifecycle ownership과 transport caller barrier로 역할이 다르다.

같은 코드가 thread-safe와 borrowed lifetime을 함께 다룬다. handler/logger pointer를 보호하는 것은 caller 객체 수명 계약이며 Send gate는 pool dispose와 이미 진입한 transport 호출 사이의 경쟁을 막는 것이다.

이 파일에서 추적할 연결

  • server.h의 thread/lifetime 주석과 비교한다.
  • server_net.h End의 실제 자원 순서를 읽는다.
  • integration의 동시 Send/Stop과 logger 재진입을 본다.

독해 포인트

shared transport API gate와 lifecycle mutex의 역할이 다르다. Stop은 신규 진입을 막고 기존 caller를 배출한 뒤 gate를 놓고 join한다.

public reason 중 protocol/overload/idle을 legacy로 명시 변환한다. false는 stale/closing/비실행일 수 있어 완료 성공 의미가 아니다.

연결해서 읽기: integration의 동시 Send/Stop과 logger 재진입을 본다.
