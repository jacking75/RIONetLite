주 스레드가 Winsock, CQ와 세션 풀을 만든다. 각 세션은 한 I/O worker에 고정되고 index+generation이 수명을 식별한다. 세션 슬롯은 worker 파티션에 걸쳐 라운드로빈으로 대여하므로 기동 직후 부하가 한 worker에 몰리지 않는다. RIO 등록 버퍼는 완료가 끝날 때까지 주소와 등록 ID가 유지된다. 네트워크 callback에서 DB, 파일 I/O, room 처리를 실행하는 설계는 잘못이며 ChatServer처럼 유계 adapter로 넘기는 방식이 올바르다.

accept thread는 연결을 배정하고 I/O worker는 소유 세션의 완료를 처리한다. OnData와 OnClosed는 해당 세션의 순서를 보존한다. Send, RequestClose, Stop, Metrics는 여러 애플리케이션 스레드에서 호출할 수 있다. handler와 logger 구현의 자체 공유 상태는 사용자가 동기화해야 한다.

콜백에서 대기하거나 동일 서버의 종료를 장시간 막는 것은 잘못이다. QueuedEventAdapter를 사용해 session.index % shard_count로 전달하고 소비자가 소유 payload를 처리하는 것이 올바르다. 콜백 span을 저장하면 안 되며 반환 전에 복사해야 한다.

콜백에서 벗어난 예외는 worker를 죽이지 않는다. OnData에서 예외가 나오면 해당 세션을 kProtocolError로 닫고 소비 바이트를 0으로 처리하며, OnConnected와 OnClosed의 예외는 오류 로그만 남기고 무시한다. 다만 예외에 의존해 제어 흐름을 만드는 것은 잘못이며, handler는 자체적으로 예외를 처리해야 한다.

worker는 완료를 처리하기 전에 다음 수신을 먼저 게시한다. 커널이 쓰는 구간과 콜백이 읽는 구간은 세션 수신 링에서 겹치지 않으므로, 콜백이 도는 동안에도 같은 세션의 수신이 진행된다.

TCP는 메시지 경계를 보존하지 않는다. LengthPrefixedDecoder는 big-endian 32비트 전체 길이를 읽고 header 미만이면 기다리며, 최소 길이 미만 또는 설정 최대값 초과를 protocol error로 반환한다. raw pointer를 정수로 cast하거나 한 recv가 한 packet이라고 가정하는 코드는 잘못이다.

콜백은 완성된 모든 packet을 처리한 뒤 실제 소비 바이트 수를 반환한다. 반환값이 readable보다 크거나 0을 반복해 버퍼를 채우면 서버가 계약 위반 또는 과부하로 연결을 닫는다.

모든 큐는 유계다. Send의 kWouldBlock은 재시도 가능한 포화를, kMessageTooLarge는 계약 위반을, kStaleSession과 kClosing은 재시도하면 안 되는 수명 종료를 뜻한다. 반환값을 무시하거나 무제한 보조 큐를 두는 것은 잘못이다.

송신 배압의 단위는 in-flight 요청 수가 아니라 send_buffer_bytes다. 세션당 RIO 송신 요청은 항상 1개이고, 진행 중인 요청이 완료되면 그 사이에 쌓인 바이트 전체를 하나의 요청으로 묶어 다시 게시한다. 따라서 소형 패킷 burst는 완료 이벤트를 늘리지 않고 링에 합쳐지며, 링에 들어가지 못한 메시지만 kWouldBlock이 된다. 버스트 크기를 링 크기로 나눠 send_buffer_bytes를 정하고, send_would_block 카운터로 검증하는 것이 올바르다.

QueuedEventAdapter는 Disconnect 또는 RejectNewest를 제공하며 네트워크 worker를 block하는 정책은 제공하지 않는다. 게임 서버는 중요도에 따라 접속 종료, 패킷 폐기 또는 상위 rate limit을 선택하고 queue depth/high-watermark/rejection을 관찰해야 한다.

종료 이벤트는 폐기 대상이 아니다. 큐가 가득 차 kClosed를 넣지 못하면 어댑터는 그 이벤트를 보류했다가 해당 세션의 남은 이벤트를 모두 소비한 뒤 순서를 지켜 전달하고, 그 전까지 같은 슬롯의 새 세대 kConnected를 받지 않는다. kData만 정책에 따라 거부된다.

정상 종료

sequenceDiagram
  participant App
  participant Server
  participant Accept
  participant Worker
  participant CQ
  App->>Server: Stop(kGraceful)
  Server->>Accept: 새 accept 차단 및 join
  Server->>Worker: 새 send/recv 차단, close 명령
  Worker->>CQ: 수락된 send와 취소 완료 drain
  CQ-->>Worker: outstanding = 0
  Worker-->>Server: join
  Server-->>App: CQ/buffer/Winsock 해제 완료

graceful은 timeout까지 수락된 send를 drain하고 immediate는 새 게시를 막고 취소 완료만 drain한다. Stop은 동시 호출해도 같은 종료를 기다린다. callback이나 등록 버퍼보다 CQ를 먼저 없애는 순서는 잘못이다.

worker가 timeout 안에 drain하지 못하면 소켓을 먼저 모두 닫아 커널이 미완료 요청을 취소하게 하고, 취소 완료를 종료 스레드에서 짧게 다시 drain한다. 그래도 outstanding이 남으면 등록 버퍼, 이중 매핑과 CQ를 해제하지 않고 소유권만 포기해 의도적으로 누수시킨다. 커널이 참조할 수 있는 메모리를 회수하는 것보다 누수가 안전하기 때문이다. 이 경우 Stop은 kShutdownTimedOut과 함께 remaining_outstanding을 보고하므로, 이 값이 0이 아닌 종료는 정상으로 취급하면 안 된다.

peer가 FIN 직후 사라져 미완료 송신이 완료되지 않으면 세션이 drain 상태로 남는다. peer_close_drain_timeout_ms를 넘기면 abortive close로 강등해 슬롯을 회수한다.

송신 배압 단위

세션당 in-flight RIO 송신 요청은 1개로 고정된다. 애플리케이션이 보낸 바이트는 세션 송신 링에 쌓이고, 진행 중인 요청이 완료되면 그때까지 쌓인 전체 구간이 하나의 RIO_BUF로 다시 게시된다. 따라서 배압은 요청 슬롯 수가 아니라 send_buffer_bytes에 남은 바이트로 판정하며, 링에 들어가지 못한 메시지만 kWouldBlock이 된다. 소형 패킷이 많은 게임 트래픽에서 완료 이벤트 수가 패킷 수가 아니라 burst 수에 비례하고, RIO completion queue 용량도 세션당 2개로 줄어든다.

관측성

Logger::Log(LogEvent)는 timestamp, severity, component, worker, SessionId, operation, library/native error를 연결한다. 비활성 로그는 IsEnabled로 hot-path 문자열 생성을 피한다. 라이브러리는 프로세스 전역 exception filter를 바꾸지 않는다.

Metrics()는 연결, recv/send bytes와 operation, would-block, stale, protocol error, close reason, CQ corrupt, callback 시간과 adapter queue 지표를 snapshot한다. 평균 callback 대기는 total/count로 계산하며 max와 high-watermark를 함께 확인한다. 서로 다른 Server의 logger와 counter는 공유되지 않는다.

ServerConfig::enable_metrics=false이면 hot-path atomic counter와 callback 시간 측정을 생략하고 Metrics()는 0 snapshot을 반환한다. counter는 유지하면서 콜백 시간 측정만 끄려면 enable_callback_timing=false를 쓴다. 이 경우 콜백당 QueryPerformanceCounter 2회가 사라지고 callback_count/callback_total_nanoseconds/callback_max_nanoseconds만 0이 된다. EchoServer의 --observability off는 metrics와 logger를 함께 끈다.

send_operations는 애플리케이션의 Send 호출 수이고 실제 RIO 송신 요청 수는 아니다. 송신이 링에서 합쳐지므로 완료 이벤트는 이보다 적을 수 있다. 배압을 볼 때는 send_would_block을 본다.

2026-08-27 Release, adaptive/64, 32연결, 128-byte payload, 2초×5회 비교에서 모든 오류·누락은 0이었다. 중앙값은 off 37,205 packets/s·P99 1,804µs·서버 CPU 4.688%, on 40,668 packets/s·P99 1,495µs·서버 CPU 4.882%였다. 짧은 측정의 표준편차가 각각 3,112/4,904 packets/s여서 유의한 성능 악화는 관찰되지 않았으며, 수치는 고정 장비 장시간 결과를 대신하지 않는다.

문제 해결

- RIO unavailable: x64 Windows와 RIO 지원 Winsock provider인지 확인한다.

- bind failed: 동일 port 프로세스를 종료하거나 다른 --port를 쓴다. 테스트는 OS 배정 port를 사용한다.

- vcpkg restore 실패: Visual Studio 2026의 vcpkg 구성요소와 루트 vcpkg.json baseline을 확인한다.

- page alignment 오류: recv/send buffer를 GetSystemInfo page size 배수로 둔다.

- 높은 CPU: notification 또는 adaptive로 바꾸고 spin을 낮춘다.

- kWouldBlock: 배압 단위는 send_buffer_bytes다. 확대 전에 소비 속도, rate limit과 high-watermark를 조사한다.

- shutdown timeout: logger의 session/outstanding/native error와 dump를 보존한다. remaining_outstanding이 0이 아니면 등록 버퍼와 CQ를 의도적으로 누수시킨 상태이므로 프로세스를 재사용하지 않는다.

- 세션 슬롯 고갈: 죽은 클라이언트가 슬롯을 점유하는지 확인하고 keepalive_time_ms와 idle_timeout_ms를 설정한다.

- accept 거부 급증: OnRejectedConnection의 native error를 본다. 핸들 고갈이면 accept 스레드가 백오프하므로 CPU 대신 거부 카운터가 오른다.

임의 Sleep으로 타이밍을 숨기지 말고 seed, 설정, JSON과 resource CSV를 함께 남기는 것이 올바르다. ASan x64와 Application Verifier/PageHeap의 정확한 구성, 해제 명령과 판정 기준은 메모리 안전성 검사를 따른다.

벤치마킹

Release를 빌드한 뒤 tools\run-benchmark.ps1 -Profile suite -Runs 5 -DurationSeconds 10 -Connections 32를 실행한다. suite는 latency 32/128 B, throughput 1/4/16 KiB, fan-in, burst, slow consumer와 churn을 실행한다. matrix는 -WaitModes, -BatchSizes, -ObservabilityModes, -AffinityModes의 조합을 비교한다. 결과는 benchmarks/results/<date>-<commit>/에 raw JSON, summary.csv, 중앙값·표준편차·서버 CPU·컨텍스트 스위치·자원 최고치를 담은 aggregate.csv, 환경 JSON과 요약으로 저장된다.

Latency(32/128 B), throughput(1/4/16 KiB), fan-in, burst, slow consumer, churn을 분리한다. worker wait mode, batch, affinity, mimalloc을 한 번에 하나만 변경한다. P99, packets/bytes, CPU와 resource 추세를 함께 보고 data/connection error가 있는 실행은 무효다. 큰 ETW/WPA trace는 CI artifact에만 둔다.

LoadClient JSON의 data_errors, dropped_packets, timeouts가 모두 0인 결과만 사용한다. 정상 응답 시나리오는 측정 종료 뒤 최대 5초 동안 진행 중 왕복을 drain하므로 종료 경계의 미수신 패킷도 성공으로 숨기지 않는다.

고정 장비의 승인된 aggregate.csv를 기준선으로 보관한 뒤 -BaselineCsv <path>를 지정하면 같은 case/wait/batch/observability를 비교한다. 기준 디렉터리에는 approval.json과 environment.json이 함께 있어야 하며 현재 컴퓨터명, CPU, 논리 코어 수와 측정 조건이 모두 일치해야 실행된다. 0.2.x 기준은 benchmarks/baselines/heungbae-1-vs2026/다. 0.3.0의 송신 경로 변경으로 이 기준선과는 직접 비교하지 않는다. 기본 실패 조건은 처리량 중앙값 5% 초과 하락 또는 P99 중앙값 10% 초과 증가이며 regression.csv를 남긴다.

하네스는 각 측정 중 \Thread(EchoServer*)\Context Switches/sec를 1초마다 표본화한다. summary.csv에는 실행별 평균·최댓값·표본 수, aggregate.csv에는 중앙값을 기록하므로 관리자 권한이 없는 장비에서도 wait mode 비교가 가능하다. -CaptureEtw는 추가로 WPR CPU file-mode trace를 cpu-context-switches.etl로 저장하며, 스레드별 스케줄링 원인 분석용이다. WPR 시스템 성능 프로파일 정책이 허용된 관리자 또는 CI 계정이 필요하다. 2026-08-27 로컬 실행에서는 정책 오류 0xc5585011로 ETW trace 시작이 거부됐지만 성능 카운터 계측은 정상 동작했다.

ChatServer

ChatServer의 네트워크 callback은 QueuedEventAdapter에 connect/data/close만 넣고 즉시 반환한다. shard worker가 자신의 session과 room 상태를 소유하며 login → lobby → room 전이, heartbeat/idle timeout, room broadcast를 처리한다.

packet은 protocol version과 big-endian 길이를 명시적으로 검증한다. malformed 입력과 event/send queue 포화는 close 정책으로 이어진다. 종료는 network accept/drain → adapter drain → logic worker join 순서다. 공유 room을 callback에서 직접 잠그거나 payload span을 저장하는 구현은 잘못이다.

응답과 room broadcast는 8바이트 헤더를 스택에 만들고 payload span을 그대로 넘기는 Send(session, header, payload)를 사용한다. 패킷마다 임시 벡터를 할당해 헤더와 본문을 이어붙이는 구현은 broadcast 대상 수만큼 할당을 반복하므로 잘못이다.

bin\x64\Debug\ChatServer.exe --port 32453 --logic-workers 4 --max-sessions 1024 --idle-seconds 30

무엇을 확인했고 무엇이 남았는가

책 작성에 앞서 0.3.0 preview 수정 코드에서 x64 Debug/Release 빌드와 테스트를 실행했다. Debug는 단위 63개, 실제 RIO 통합 25개를 통과했다. Release는 단위 62개 통과, Debug 할당 후크용 1개 제외, RIO 통합 25개 통과다. 두 구성의 빌드 경고와 오류는 0개였다. 이 숫자는 2026년 10월 9일 로컬 수정본의 증거다.

Chat은 1/2/4 로직 샤드에서 공통 fixture 8개, 각 구성의 broadcast 21회 수신과 malformed 5개 종료를 확인했다. 종료 시 active_players, queued_events, pending_broadcasts가 모두 0이었다. GUI 버튼을 사람이 조작한 검증은 수행하지 않았으므로 headless 프로토콜 검증과 구분한다.

8개 실제 RIO ASan 시나리오는 오류 0, exit 0이었다. 600초 안정성 측정은 전체 경로 warmup 이후 20회 iteration, 원시 표본 77개와 유휴 표본 20개를 얻었다. 같은 유휴 상태에서 handle 165→165, thread 21→21, private bytes 4,210,688→4,210,688이며 correctness 오류 0, server exit 0이었다. 이것은 장기 운영이나 처리량 목표 인증이 아니다.

ZIP에 들어 있는 소스 스냅샷으로 정적 라이브러리를 새로 만들고 ZIP만 꺼낸 consumer를 빌드·실행했다. 개발 PC에서의 검증이며 새 PC 설치, 다른 Windows/Server 조합, 일반 독자의 학습 성공, 실제 게임 운영 부하는 아직 별도 검증이 필요하다.

이 책의 browser/인쇄 검증은 HTML의 기능과 조판을 확인한다. 라이브러리의 네트워크 테스트를 대체하지 않는다. 실습 결과를 기록할 때 반드시 코드 버전, 도구 체인, 설정과 실행 환경을 함께 남긴다.
