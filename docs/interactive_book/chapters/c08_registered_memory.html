커널이 참조하는 메모리를 먼저 지우지 않는다

등록 ID와 주소, 게시된 구간, 마지막 완료가 하나의 수명으로 연결되어야 한다.

심화큰 그림에서의 위치: P02 ④ 수신 링·송신 링

쉽게 말하면 커널에 등록한 메모리는 요청이 끝날 때까지 옮기거나 지우면 안 된다는 규칙을 구현 수준에서 본다. 수신과 송신의 참조를 따로 세고, 새 요청을 막고 참조가 모두 0이 된 뒤에야 해제한다.

처음 읽는다면 L04 실험에서 “완료 전 해제”가 막히는 모습만 확인하고 넘어가도 된다.

등록된 범위의 주소를 유지한다

RIORegisterBuffer는 메모리 범위를 등록하고 ID를 돌려준다. 요청은 그 ID와 Offset·Length를 참조한다. vector가 커지며 내부 주소를 바꾸거나 소유 객체를 잘못 이동해 등록된 주소가 달라지면 커널은 예전 주소를 사용할 수 있다. 등록 뒤의 주소 안정성은 단순한 C++ 포인터 유효성보다 긴 비동기 수명 문제다.

이 구현은 세션별 DoubleMappedBuffer와 RegisteredRioBuffer를 RAII 타입으로 소유한다. RIO_BUF와 요청 컨텍스트도 요청이 끝나기 전에 옮기거나 재사용하지 않는다. 등록 ID를 저장했다는 사실만으로 원래 매핑의 수명이 늘어나지 않는다.

송신과 수신 참조를 따로 끝낸다

실험에서 송신을 완료해도 수신 참조가 남으면 해제는 차단된다. 참조가 0이 되어도 신규 게시가 열려 있으면 다른 호출이 다시 참조를 만들 수 있다. 먼저 게시를 차단하고, 모든 참조를 정리하고, 등록을 해제한 뒤 저장소를 해제한다. CQ와 RQ의 의존 관계는 서버 종료 단계에서 추가로 확인한다.

소유권 이동은 항상 메모리 바이트 복사와 같지 않다. RAII 객체의 move가 주소가 유지되는 매핑 소유권만 넘길 수도 있다. 그러나 진행 중인 객체를 애플리케이션 호출과 경쟁하며 옮기는 것은 다른 동기화 문제다. 공개 Server의 이동에는 모든 호출자를 끝내라는 별도 계약이 있다.

이중 매핑의 중간 실패를 되돌린다

DoubleMappedBuffer::Create는 Windows page 크기 배수와 범위 overflow를 확인한다. 연속 가상 주소 placeholder를 확보하고 두 범위를 나눈 뒤 backing mapping과 두 view를 만든다. 두 번째 view 생성이 실패할 때 첫 view까지 정리하는 경로가 필요하다. 마지막 성공 줄만 보면 중간 자원 누수를 찾기 어렵다.

오류를 반환하기 전에 GetLastError 값을 저장한다. 자원 해제 호출이 그 값을 덮어쓸 수 있기 때문이다. 로컬 UniqueHandle은 backing mapping 핸들을 관리하고 성공한 view 소유권은 반환 객체가 관리한다. 실패한 자원을 확보한 것처럼 해제하지 않고, 성공한 단계만 역순으로 되돌린다.

의도적 보존은 정상 해제가 아니다

종료 타임아웃 뒤에도 커널 참조가 남으면 즉시 모든 객체를 지우는 것이 가장 위험할 수 있다. 현재 실패 복구는 소켓을 abort하고 추가 완료를 회수한 뒤, 그래도 참조가 남으면 등록 메모리·매핑·CQ 등의 소유권을 의도적으로 포기할 수 있다. use-after-free를 막는 마지막 실패 경로다.

이 상태는 메모리가 잘 회수되었다는 뜻이 아니다. 남은 참조 수, 활성 연결, 손상 CQ와 종료 오류를 기록하고 정상 서비스 상태로 계속 재사용하지 않는다. 테스트나 문서에서 “크래시하지 않았다”만으로 누수 없는 종료라고 판정하지 않는다. C17과 C24에서 정상 회수와 실패 시 보존을 나누어 검증한다.

RAII는 해제 순서까지 설계한다

RAII는 자원의 소유권을 객체 수명과 묶는 방식이다. UniqueSocket은 closesocket, UniqueHandle은 CloseHandle, WinsockRuntime은 WSACleanup을 담당한다. copy를 금지하고 move에서 원래 객체를 빈 상태로 바꾸므로 같은 자원을 두 객체가 해제하지 않는다.

자동 destructor가 있다고 아무 때나 파괴해도 되는 것은 아니다. 등록 버퍼는 outstanding가 0이어야 deregister할 수 있다. CQ는 이를 사용하는 워커와 요청이 정리된 뒤 닫아야 한다. notification event는 CQ가 계속 참조할 수 있어 CQ 뒤에 해제한다.

Reset은 현재 소유 자원을 해제하고 빈 상태로 만든다. Release는 handle이나 등록의 소유권을 놓는다. 정상 경로의 Release는 새 소유자에게 넘기기 위한 것이지만 실패 drain 경로는 커널 참조가 남아 있어 의도적으로 회수하지 않기 위한 것이다. 같은 이름이라도 목적을 읽는다.

멤버의 선언 순서도 destructor 순서에 영향을 준다. 명시적 Stop과 Dispose에서 의존 관계를 확인하는 이유는 서로 다른 객체의 자동 소멸만으로 복잡한 I/O 종료를 증명하기 어렵기 때문이다. 단위 테스트는 move와 rollback, outstanding 거절을 따로 검사한다.

RAII는 해제 순서까지 설계한다: 적용한다

CreateRequestQueue가 실패하면 이미 받은 accepted socket은 RAII로 닫힌다. 반면 BeginRequest 후 RIOReceive가 성공한 경우에는 buffer destructor를 바로 호출할 수 없다. 같은 “실패”라도 게시 전과 게시 후의 정리 조건이 다르다.

작은 실습에서는 fake RIO로 outstanding 하나가 있는 Reset이 false인지 확인한다. 완료를 반영한 뒤에는 성공해야 한다. 정상 경로에서 이 false를 무시하는 코드가 있으면 종료 순서부터 다시 검사한다.
