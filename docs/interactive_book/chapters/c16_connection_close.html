소켓을 닫은 뒤에도 완료는 남을 수 있다

종료 이유의 선택, 소켓 종료, 애플리케이션 통지와 슬롯 재사용을 한 순간으로 합치지 않는다.

종료 요청과 네트워크 관찰을 구분한다

애플리케이션은 전체 SessionId로 RequestClose를 호출한다. 내부 ForcedClose는 풀의 할당·재사용과 같은 lock 아래 세대를 검사하고 종료 전이를 시도한다. 성공하면 소유 I/O 워커의 지연 종료 mailbox에 작업을 보낸다. 반환 true는 그 요청을 받아들였다는 뜻이지 이미 OnClosed가 실행됐다는 뜻이 아니다.

수신 오류, 송신 오류, 원격 FIN, idle 만료와 서버 정지는 서로 다른 종료 원인이다. 로그의 operation·native 오류와 공개 CloseReason을 함께 확인한다. 원격 FIN은 수신 방향이 끝났다는 관찰이며 접수한 송신을 기다릴 수 있다. 애플리케이션이 PeerClosed를 RequestClose에 넣는 것으로 실제 FIN을 재현하지는 못한다.

종료 통지와 참조 회수를 따로 실행한다

실험에서 일반 요청이나 오류 종료를 선택한 뒤 닫힘을 통지해도 미완료 참조가 남을 수 있다. 소켓을 닫으면 취소 완료가 나중에 도착할 수 있기 때문이다. 참조가 남은 슬롯은 quarantine에 두고 새 연결에 바로 주지 않는다. 닫힌 뒤의 지연 수신은 OnData를 만들지 않고 요청 참조만 정리한다.

통지 횟수는 TryNotifyClose로 최대 한 번으로 제한한다. 중복 종료 요청이 와도 Player 제거를 반복하거나 active 연결 수를 여러 번 줄이지 않는다. 다만 아직 보류 중인 FIN은 이미 확정한 오류 종료와 같지 않으므로 아래 우선순위를 함께 읽는다.

peer FIN 뒤에는 접수한 송신을 기다린다

0바이트 수신 완료가 오면 수신 참조를 정리하고 새 애플리케이션 송신 접수를 막는다. 기존 송신기의 완료·재게시 경로는 이미 접수한 링 데이터를 처리할 수 있다. 지연 종료 관리자는 ReadyForPeerClose, 즉 SendOutstanding이 0인지 확인한다. 정상 완료가 모두 끝나면 send 방향을 shutdown하고 소켓을 닫는 경로로 진행한다.

peer_close_drain_timeout_ms는 이 대기의 상한이다. 제한 시간에 닿으면 보류 이유를 SEND_ERROR로 바꾸고 abortive close로 전환한다. “FIN을 받았으니 상대가 응답까지 다 읽었다”거나 “무조건 무기한 송신을 기다린다”라고 설명하지 않는다. 이 연결 기한은 서버 Stop의 공유 예산과 별개다.

중복을 합치고 FIN보다 명시적 종료를 우선한다

지연 종료 제어 저장소는 세션당 mailbox 하나와 워커별 ready 목록을 사전 확보한다. 같은 index의 중복 요청을 계속 동적 큐에 추가하지 않는다. 한 처리 회차는 현재 pending 수와 64 중 작은 값을 예산으로 사용하므로 아직 종료할 수 없는 세션을 다시 보류해도 무한 drain 루프로 바뀌지 않는다.

보류된 ZERO_COMPLETION, 즉 peer FIN은 같은 세대의 명시적·오류 종료로 대체될 수 있다. 반면 이미 명시적 이유가 들어 있으면 같은 세대의 뒤 요청을 덮어쓰지 않는다. 더 오래된 세대의 작업이 새 세대의 명령을 바꾸는 것도 거절한다. 따라서 “첫 요청이 모든 사유를 영원히 고정한다”는 단순 설명은 현재 코드와 맞지 않는다.

connect callback pending이 남으면 실제 닫힘을 그 뒤로 미룬다. 이 보호와 세대 검증, 소켓 닫기 CAS, 닫힘 통지 CAS는 서로 다른 경쟁을 막는다. 하나의 bool만 추가해 모두 해결했다고 가정하지 않는다.

idle과 keepalive는 다른 신호다

idle_timeout_ms가 켜져 있으면 I/O 워커는 약 1초 주기로 자기 파티션의 세션을 확인한다. 최근 성공 수신 활동 이후의 경과 시간이 기준이며 송신을 계속했다고 수신 idle이 자동으로 갱신되지는 않는다. 0이면 이 검사를 사용하지 않고, 1000ms보다 짧은 양수는 설정에서 거절한다.

keepalive_time_ms가 지정되면 소켓에 SIO_KEEPALIVE_VALS를 설정한다. 사라진 피어가 미완료 수신을 영구 점유하는 상황에서 오류 완료를 얻는 데 사용한다. 설정 실패도 접속 setup 실패로 기록한다. 이것은 애플리케이션 heartbeat나 게임의 로그인 idle 정책과 같은 기능이 아니며 각각 독립적으로 사용한다.

Chat의 --idle-seconds는 게임 프로토콜 처리의 activity 기준이다. 기본 ServerConfig의 네트워크 idle은 0이며 Chat의 30초 정책과 같은 값이 자동으로 복사되는 구조가 아니다. 바이트만 흘리는 연결과 완전한 게임 패킷을 보내는 연결을 구분하는 데 이 차이가 중요하다.

유계 close mailbox로 중복을 합친다

RequestClose는 애플리케이션 스레드에서 직접 OnClosed를 부르는 동기 함수가 아니다. 세션 close 전이의 승자가 owner worker에 command를 보내고 그 worker가 연결 종료와 callback 순서를 담당한다. true는 요청 전이 성공을 뜻한다.

close manager는 worker별로 세션 수만큼 entries, pending과 ready ring을 미리 확보한다. 세션 하나에 한 pending command만 둬 반복 close가 unbounded queue를 만들지 않게 한다. 지연된 옛 generation이 새 command를 덮지 못한다.

ProcessLazyedDisConnectSession은 시작 시 pending 수와 64 중 작은 값을 한 번의 처리 budget으로 삼는다. 아직 peer 송신 drain이 끝나지 않으면 command를 다시 넣어 다음 loop에서 처리한다. 같은 loop에서 무한 fetch-reinsert하지 않는다.

peer FIN의 deferred close보다 명시·오류 close가 우선할 수 있다. drain deadline이 지나면 send error 경로로 강등해 abortive 회수를 시도한다. 큐 이름의 legacy 철자가 남아 있어도 동작은 유계 mailbox이며 예전 PPL 무한 큐 설명을 그대로 적용하지 않는다.

유계 close mailbox로 중복을 합친다: 적용한다

한 세션에 100,000번 close command를 보낸 테스트에서도 저장된 slot 수가 한 개 수준인지 확인한다. 실제 close 요청은 이미 closing이면 false일 수 있지만 내부 command 중복 방어도 별도로 검사한다.

disconnect delegate가 아직 완료하지 못한다고 반환하는 fake를 사용한다. 한 Process 호출에서 같은 세션을 계속 처리하지 않아야 한다. 그래야 새 수신 완료와 다른 세션의 종료를 처리할 기회가 남는다.

실습에서 관찰할 값

  • 중복이 queue 크기를 늘리지 않는지 본다.
  • 예전 generation이 새 항목을 덮지 않는지 본다.
  • deferral이 한 loop를 무한 점유하지 않는지 본다.

생각하고 확인한다

bounded queue가 있는데도 처리 loop가 무한정 길어질 수 있는가.

해설 펼치기

가능하다. fetch한 항목을 즉시 reinsert하고 empty가 될 때까지 돌면 크기는 일정해도 끝나지 않는다. 현재 코드는 시작 시 budget을 고정해 시간 점유도 제한한다.

peer FIN과 idle timeout을 구분한다

peer가 송신 방향을 닫으면 수신 완료의 transferred 0으로 FIN을 관찰할 수 있다. 이는 이미 수락한 서버 송신을 곧바로 버려야 한다는 뜻은 아니다. BeginPeerClose는 새 application send를 막고 기존 outstanding 송신을 별도 drain deadline까지 기다린다.

peer_close_drain_timeout_ms는 연결별 FIN 이후 예산이며 서버 전체 graceful timeout과 다르다. 기다리는 송신이 끝나면 정상 peer close를 진행하고 deadline이 지나면 send error와 abortive close 경로로 회수한다.

idle_timeout_ms는 마지막 수신 활동을 기준으로 owner가 약 1초 주기로 검사한다. 1000ms를 지정해도 정확히 1000ms 순간에 닫는 정밀 timer가 아니다. 0이면 사용하지 않는다. 게임 Chat의 별도 packet 활동 timeout도 존재하므로 계층을 구분한다.

keepalive는 소켓 수준에서 사라진 peer를 감지하도록 설정한다. idle timeout과 목적·시간 척도가 같지 않다. WSAIoctl 설정이 실패하면 해당 새 세션 설정 실패를 보고하며 성공한 것처럼 계속 진행하지 않는다.

peer FIN과 idle timeout을 구분한다: 적용한다

half-close 클라이언트가 request를 보내고 SD_SEND 후 서버 응답을 읽는지 검사한다. 응답을 읽지 않는 경우에는 timeout 경로가 세션을 회수하는지 본다. 정상 remote FIN과 강제 reset을 같은 상황으로 취급하지 않는다.

idle 연결에서 close reason이 IdleTimeout인지 확인한다. application이 RequestClose에 IdleTimeout을 직접 지정해도 공개 reason이 보존되는지 테스트한다. native transport error와 application 지정 reason을 로그에서 구분한다.

실습에서 관찰할 값

  • half-close 후 응답을 받을 수 있는지 본다.
  • FIN drain deadline 후 slot이 회수되는지 본다.
  • IdleTimeout reason이 변형되지 않는지 본다.

생각하고 확인한다

heartbeat가 keepalive와 같은 기능인가.

해설 펼치기

heartbeat는 애플리케이션 protocol packet이고 keepalive는 TCP 소켓 감지 정책이다. heartbeat는 game 상태나 packet 활동을 유지할 수 있지만 두 정책의 timer와 실패 의미를 별도로 설계한다.
