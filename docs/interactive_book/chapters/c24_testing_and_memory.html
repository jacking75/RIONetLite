결정적인 실패 검사와 실제 RIO 증거를 연결한다

테스트 종류마다 확인할 수 있는 범위를 명확히 하고, 실행하지 않은 도구를 통과로 기록하지 않는다.

심화큰 그림에서의 위치: P02 운영과 문제 해결

쉽게 말하면 이 저장소의 테스트 종류(순수 로직, 가짜 RIO, Win32 자원, 실제 RIO 통합)가 각각 무엇을 증명하는지와 메모리 오류를 찾는 도구의 사용법을 다룬다.

처음 읽는다면 테스트 종류 구분 절만 읽고, 나머지는 라이브러리를 수정할 때 읽는다.

순수·fake·Win32·통합을 구분한다

단위 실행 파일에는 설정·상태·파티션·프레이밍·큐 같은 구조 검사, FakeRioApi/SocketApi를 주입한 실패 검사와 실제 Win32 자원 검사도 들어 있다. “단위”라는 폴더명만 보고 모두 OS 독립이라고 가정하지 않는다. 통합 실행 파일은 실제 Winsock/RIO 연결·분할·병합·종료·idle·keepalive와 handle 회수를 다룬다.

브라우저 모델 검사는 이 코드의 주요 조건을 작은 상태로 설명한다. 실제 커널 API나 스레드 메모리 순서를 전부 흉내 내지 않는다. 별도 Echo/Chat 프로세스 검사는 명령행·실제 클라이언트·게임 배출까지 확인한다. 네 가지 증거를 한 “테스트 통과” 숫자로 합치지 않는다.

bin\tests\x64\Debug\RIONetLite.UnitTests.exe
bin\tests\x64\Debug\RIONetLite.IntegrationTests.exe
bin\tests\x64\Release\RIONetLite.UnitTests.exe
bin\tests\x64\Release\RIONetLite.IntegrationTests.exe

N번째 실패와 비정상 완료를 고정한다

RioApi 접점은 등록·RQ/CQ·게시·완료를 fake로 제어할 수 있게 한다. SocketApi는 registered socket 생성, exclusive address 설정, bind와 listen의 실패를 제어한다. 횟수별 성공·실패를 고정하면 중간 초기화가 확보한 자원을 정확히 되돌리는지 확인할 수 있다.

생산 워커 루프에 fake 결과를 넣는 검사에는 null 컨텍스트, 손상 CQ, 스레드 시작 전 CQ 생성 실패와 중복 close의 유계 처리가 있다. 같은 이름의 별도 테스트용 알고리즘만 검사하는 것과 실제 워커의 분기를 검사하는 것을 구분한다. 랜덤 SendQueue 검사는 실패할 때 seed를 남겨 재현할 수 있게 한다.

등록 실패에서 확보한 자원만 정리한다

현재 TcpSession의 등록 순서는 send 다음 recv다. 두 세션을 순서대로 준비한다면 session0.send → session0.recv → session1.send → session1.recv가 된다. 세 번째 등록 실패에서는 앞서 성공한 session0의 recv와 send를 정리한다. 실패한 등록을 해제한 것으로 세거나 참조 카운트를 음수로 만들지 않는다.

이 실험의 “정리”는 임시 초기화 결과를 폐기하는 롤백 모델이다. 정상 서비스 종료에서 모든 세션을 전역적으로 역순 파괴한다는 주장은 아니다. 실제 SessionManager::Dispose는 세션별 자원 의존 관계를 지키며 순회한다. 소켓·CQ·매핑 placeholder의 실패 단계는 각각의 실제 자원 테스트도 확인해야 한다.

AddressSanitizer는 계측 바이너리로 실제 시나리오를 실행한다

Visual Studio의 C++ AddressSanitizer 구성 요소를 준비한다. 저장소 도구는 라이브러리와 EchoServer를 Debug·EnableASAN=true로 별도 경로에 빌드하고, Release LoadClient로 실제 RIO 시나리오 8개를 실행한다. 일반 Debug 빌드 성공만으로 ASan을 실행했다고 표시하지 않는다.

tools\build.ps1 -Configuration Release -Rebuild
tools\run-memory-safety.ps1 -Connections 16 -ScenarioSeconds 1 -Seed 1511506142

echo, split, coalesce, half-close, slow-read, abrupt-close, invalid-length와 no-read의 correctness 오류가 없어야 하며 서버 종료 코드와 sanitizer 보고를 함께 확인한다. 결과는 artifacts/memory-safety 아래에 남는다. 비계측 GoogleTest 라이브러리와 STL annotation ABI 차이가 있으므로 계측 실행 파일에 임의로 섞어 링크하지 않는다.

이번 책 집필에서는 ASan을 재실행하지 않았다. A04의 과거 실행 기록은 이번 실행 결과가 아니다. 실제로 새 검사를 돌릴 때는 도구·구성·바이너리·source 해시와 seed를 함께 남긴다.

Verifier와 PageHeap은 대상과 해제를 함께 지정한다

아래는 기존 검증 문서의 도구 사용 절차를 이관한 것이다. 설치된 도구의 도움말에서 옵션 형식을 확인하고, 관리자 환경에서 테스트 실행 파일에만 적용한다. 이번 판에서는 Application Verifier와 gflags를 실행하지 않았으며 통과로 기록하지 않는다. 생산 실행 파일이나 머신 전체에 무작정 켜지 않는다.

$unit = (Resolve-Path .\bin\tests\x64\Debug\RIONetLite.UnitTests.exe).Path
$integration = (Resolve-Path .\bin\tests\x64\Debug\RIONetLite.IntegrationTests.exe).Path
appverif.exe -enable Heaps Handles Locks Memory Threadpool Leak -for $unit $integration
try {
  & $unit
  & $integration
  appverif.exe -export log -for $unit -with to=.\artifacts\appverif-unit.xml
  appverif.exe -export log -for $integration -with to=.\artifacts\appverif-integration.xml
} finally {
  appverif.exe -disable '*' -for $unit $integration
}

full PageHeap을 좁게 적용하는 대안은 appverif.exe -enable Heaps -for $unit $integration -with Heaps.full=true다. Windows SDK Debugging Tools의 gflags를 쓰는 경우도 해제까지 한 절차로 수행한다.

gflags.exe /p /enable RIONetLite.UnitTests.exe /full
gflags.exe /p /enable RIONetLite.IntegrationTests.exe /full
try {
  & $unit
  & $integration
} finally {
  gflags.exe /p /disable RIONetLite.UnitTests.exe
  gflags.exe /p /disable RIONetLite.IntegrationTests.exe
}

도구가 설치되지 않았거나 실제 실행하지 않았다면 그 상태를 따로 적는다. 프로세스 exit 0뿐 아니라 verifier stop, heap corruption, sanitizer와 handle 오류가 없는지 검사한다. XML·stderr·PDB·seed·명령·관련 JSON을 같은 실행 자료로 보존하고 설정이 해제되었는지 확인한다.

같은 유휴 상태에서 자원을 비교한다

최초 RIO workload가 provider 자원을 준비한 뒤 handle이 늘어나는 것과 반복마다 누수되는 것은 다르다. 정상·오류 경로를 예열하고 같은 quiescent 시점의 handle·thread·private bytes를 비교한다. workload 중 최고치와 종료 뒤 안정값도 구분한다.

600초 stress나 ASan 통과가 모든 대상 OS·장기 운영·고부하 성능의 승인으로 확대되지 않는다. 공유 개발 PC에서 짧은 관찰을 운영 용량 판정으로 바꾸지 않는다. 이번 판에서 실행한 범위는 A05, 과거의 구체적 값과 미완료 항목은 A04로 분리한다.

결정적 테스트 경계

RioApi와 SocketApi를 주입해 N번째 초기화 호출 실패와 롤백을 소켓 없이 재현한다. logger는 Server 인스턴스마다 주입하며 서로 다른 두 logger의 격리를 통합 테스트로 검증한다.

세션 재사용은 generation과 outstanding 요청 수로 결정한다. idle 검사와 peer-close drain은 production deadline을 사용하므로 transport 전체가 clock 독립적인 것은 아니다. application event adapter 역시 내부 작업자나 예약 실행기를 만들지 않고 TryPop으로 소비자가 직접 구동한다. 핵심 상태 전이와 큐 순서는 결정적 단위 검사로, 실제 deadline·RIO 완료·종료 경합은 OS 통합 검사로 확인한다.

DoubleMappedBuffer의 실패를 되돌린다

DoubleMappedBuffer::Create는 2N 연속 가상 주소 placeholder를 예약하고 두 N 구간으로 나눈다. 하나의 file mapping 저장소를 두 placeholder에 연결한다. 같은 저장소가 이어진 두 주소에서 보이는 것이 링의 wrap 처리를 단순하게 만든다.

예약, 분할, mapping 생성, 첫 view, 둘째 view는 각각 실패할 수 있다. 함수는 어느 단계까지 성공했는지에 맞춰 placeholder와 view를 되돌린다. 첫 view 성공 후 둘째 view가 실패했을 때는 첫 view를 unmap하고 남은 placeholder도 해제해야 한다.

오류 코드는 rollback 전에 저장한다. VirtualFree, UnmapViewOfFile나 handle destructor가 다른 last error를 남길 수 있기 때문이다. 실패 원인과 정리 동작은 서로 다른 작업이며 사용자에게는 원래 실패를 전달한다.

Release는 view를 unmap하지 않고 객체의 pointer만 비운다. 이 동작은 outstanding I/O가 남은 치명적 종료에서 조기 해제를 피하기 위해 존재한다. 정상 stop에서 무조건 Release하면 자원을 누수시키므로 Reset과 목적을 혼동하지 않는다.

DoubleMappedBuffer의 실패를 되돌린다: 적용한다

원문에서 second_view==nullptr 분기를 찾아 어떤 자원이 이미 살아 있는지 그린다. first_view만 unmap하고 second placeholder를 잊으면 가상 주소 누수가 남는다. mapping handle은 UniqueHandle이 함수 종료 시 해제한다.

Windows page 크기에 맞지 않는 입력은 시스템 호출 전에 거절한다. 이는 환경 실패와 입력 실패를 구분하는 장치다. buffer 생성에 대한 native error는 library 설정 오류와 함께 비교해 진단한다.

실습에서 관찰할 값

  • 모든 실패 분기의 반환 전 회수를 확인한다.
  • GetLastError 보관이 rollback보다 먼저인지 본다.
  • 정상 Reset이 두 view를 모두 unmap하는지 본다.

단위와 실제 RIO 테스트를 연결한다

단위 테스트는 입력과 실패를 통제한다. fake RioApi로 게시 실패, 부분 완료, null context와 corrupt CQ를 만들 수 있다. 실제 worker loop를 사용하는 테스트와 단순 helper만 테스트하는 경우의 검증 범위를 구분한다.

통합 테스트는 실제 Winsock socket과 RIO provider를 사용한다. connect, data, close, stale id와 동시 Stop을 관찰한다. 이벤트 대기는 condition variable이나 제한된 deadline으로 제어하고 실패가 무한 hang이 되지 않게 한다.

경쟁 조건은 우연한 Sleep 한 번에 기대지 않는다. connect callback 진입 신호를 기다리고 close를 요청한 뒤 callback을 해제하는 방식은 원하는 interleaving을 명확히 만든다. 테스트가 무엇을 기다리고 어느 순서를 확인하는지 읽는다.

Release에서 제외된 Debug allocator hook 테스트는 “모든 테스트 통과”라고 묶지 않는다. 실행된 수, passed, skipped와 실패를 구분한다. ASan, 실제 두 PC와 운영 부하는 각각 추가 증거이므로 단위 테스트 숫자로 대체하지 않는다.

단위와 실제 RIO 테스트를 연결한다: 적용한다

새 실패를 고치면 먼저 이전 코드에서 실패하고 수정에서 통과하는 작은 재현을 만든다. 예를 들어 close 중복은 queue slot 상한과 delegate 호출 수를 검사하고 handle 회수는 반복 실제 create-stop으로 검사한다.

테스트는 구현을 그대로 재작성하는 것이 아니라 지켜야 할 외부 계약을 확인한다. ring helper의 내부 필드가 특정 이름이라는 검사보다 부분 송신 후 정확한 바이트 순서가 유지되는지가 중요하다.

실습에서 관찰할 값

  • fake와 실제 OS 검증 범위를 기록한다.
  • 순서 경쟁을 신호로 제어한다.
  • passed와 skipped를 구분한다.

생각하고 확인한다

fake CQ의 null context 검사가 실제 production loop를 통과해야 하는 이유는 무엇인가.

해설 펼치기

방어 helper 앞의 production loop가 먼저 역참조한다면 helper 테스트만으로는 crash를 놓친다. 실제 결과 dispatch 경로까지 테스트해야 최초 접근 순서를 확인할 수 있다.

$unit = (Resolve-Path .\bin\tests\x64\Debug\RIONetLite.UnitTests.exe).Path

appverif.exe -enable Heaps Handles Locks Memory Threadpool Leak -for $unit $integration
& $unit
& $integration
appverif.exe -export log -for $unit -with to=.\artifacts\appverif-unit.xml
appverif.exe -export log -for $integration -with to=.\artifacts\appverif-integration.xml
appverif.exe -disable '*' -for $unit $integration

Application Verifier의 full PageHeap만 좁게 적용하려면 다음 구성을 사용한다.

appverif.exe -enable Heaps -for $unit $integration -with Heaps.full=true

gflags.exe /p /enable RIONetLite.UnitTests.exe /full

& $integration
gflags.exe /p /disable RIONetLite.UnitTests.exe
