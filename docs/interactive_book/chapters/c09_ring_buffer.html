주소가 이어져도 용량은 늘지 않는다

지도에서의 위치는 이 장의 쉽게 말하면 상자에서 설명한다.

읽기 위치, 쓰기 위치와 미소비 크기를 따로 추적하면 full과 empty, wrap과 overwrite를 구분할 수 있다.

심화큰 그림에서의 위치: P02 ④ 수신 링·송신 링

쉽게 말하면 세션의 수신·송신 버퍼로 쓰는 원형 버퍼(링 버퍼)를 다룬다. 읽기 위치·쓰기 위치·사용량을 따로 기록하는 이유와, 같은 메모리를 두 번 이어 붙여 끝과 처음을 한 덩어리로 다루는 이중 매핑을 설명한다.

처음 읽는다면 L05 실험으로 작은 링을 채우고 비워 보는 것만으로 충분하다.

위치 두 개만으로 full과 empty를 구분하지 않는다

그림으로 보기 · 메모리·소유권·종료 순서를 실제 코드와 대조한다.

먼저 예측해 보기 · read와 write가 같다. 링이 비었다고 단정할 수 있는가?

used를 함께 확인한다 — used=0과 used=capacity가 같은 포인터 위치를 가질 수 있다. L05로 비교한다.

크기 8인 링에서 읽기 위치와 쓰기 위치가 모두 0이면 비어 있을 수도, 8바이트가 가득 찼을 수도 있다. RingBufferVA2는 used_bytes를 따로 관리한다. 쓰기 가능 크기는 capacity-used이고 읽기 가능 크기는 used다. 같은 위치라는 이유로 빈 버퍼로 초기화하면 아직 처리하지 않은 바이트를 덮어쓴다.

Write는 요청 크기가 남은 공간에 들어가는지 먼저 검사한다. 실패하면 nullptr 또는 false를 반환한다. 수신 완료는 커널이 이미 쓴 바이트의 크기를 Write(size)로 반영하고, 애플리케이션 송신은 Write(size, data)로 복사한다. 같은 이름이어도 어느 쪽이 메모리에 실제로 쓰는지 구분한다.

작은 링을 채우고 경계를 넘겨 본다

먼저 6바이트를 쓰고 5바이트를 소비하면 읽기 위치 5, 쓰기 위치 6, used 1이다. 다시 6바이트를 쓰면 쓰기 위치는 4가 되고 used는 7이다. 읽을 데이터의 가상 연속 범위는 [5,12)로 나타낼 수 있다. 이때 물리 저장소는 여전히 8바이트며 빈 공간은 1바이트다.

실험의 post는 읽기 구간을 요청에 연결한다. 해당 범위가 완료되기 전에는 consume으로 임의 이동하지 못하게 한다. 이 링 실험은 보호 구간을 눈으로 확인하기 위한 모델이며 송신기의 retire와 새 메시지 병합은 C14·C15에서 더 정확히 다룬다.

두 view가 같은 backing을 가리킨다

가상 주소 [0,8)과 [8,16)이 같은 실제 저장소를 가리킨다고 생각한다. 첫 view의 끝에서 두 번째 view의 처음으로 읽으면 저장소의 끝과 처음을 연속 주소처럼 다룰 수 있다. 따라서 wrap된 송신을 하나의 RIO_BUF로 표현할 수 있다. 읽기 위치가 5일 때 [5,12)는 첫 view의 5~7과 두 번째 view의 8~11이다.

RegisteredSpanSize는 링 크기의 두 배다. 이는 등록할 가상 주소 범위이며 물리 backing commit의 두 배 할당을 뜻하지 않는다. 메모리 예산에서 registered/reserved와 committed를 구분하는 이유다. 주소 범위가 두 배라고 용량 검사도 두 배로 허용하면 같은 backing의 미소비 바이트를 덮어쓴다.

읽기와 커널 쓰기가 겹치지 않아야 한다

수신 경로는 이번 완료를 반영한 뒤 빈 범위에 다음 수신을 게시한다. 콜백이 읽는 미소비 범위와 커널이 새로 쓰는 범위는 used와 writable로 나뉜다. 콜백이 올바른 소비량을 반환하면 읽기 위치만 이동한다. 다음 수신 완료가 오기 전부터 아직 받지 않은 바이트를 쓴 것으로 계산하지 않는다.

송신 경로는 lock으로 여러 애플리케이션 호출과 완료 처리를 조정한다. 링 타입 자체의 모든 메서드가 독립적으로 thread-safe인 것은 아니다. 내부 타입의 간단한 memcpy를 보고 외부 여러 스레드에서 아무 보호 없이 Write해도 된다고 추론하지 않는다. 동기화 책임은 호출하는 송신기와 소유 워커에 있다.

링 버퍼의 읽기와 쓰기를 계산한다

링 버퍼는 고정 크기 저장소에 read position, write position과 used bytes를 둔다. 쓰기는 writable = capacity-used 이내에서만 가능하고 읽기 위치는 실제 소비한 크기만큼 이동한다. 두 위치가 같아도 used가 0인지 capacity인지에 따라 empty와 full을 구분한다.

RingBufferVA2는 double-mapped 저장소를 사용한다. 논리 capacity가 N이면 가상 주소에는 2N span이 보인다. read가 끝부분에 있고 데이터가 앞부분으로 돌아가도 연속 주소로 전체 used 구간을 읽는다. 물리 저장소가 두 배로 늘어나는 방식은 아니다.

버퍼의 index를 N으로 접어 넣는 것과 RIO에 게시하는 길이를 구분한다. 모든 논리 읽기·쓰기 크기는 N 이내의 writable/used 규칙을 따르고 등록 구간은 2N이다. 두 번째 view가 있다고 2N 바이트를 저장할 수 있다고 해석하면 기존 바이트를 덮어쓴다.

이 클래스 자체가 모든 호출을 동기화하지 않는다. sender는 spinlock 아래 쓰기와 읽기 위치를 바꾸고 수신은 owner worker의 흐름을 따른다. 자료구조의 함수가 안전한지뿐 아니라 누가 어떤 잠금으로 부르는지를 함께 읽는다.

링 버퍼의 읽기와 쓰기를 계산한다: 적용한다

8칸 교육용 링에서 read=6, used=4이면 바이트는 6,7,0,1에 있다. 가상 주소에서는 첫 view의 6부터 둘째 view의 1까지 이어진다. 실제 구현은 page 배수 크기를 사용하므로 이 숫자는 계산을 이해하기 위한 모형이다.

다음 두 바이트를 쓸 때 used는 6이 되고 writable은 2가 된다. 3바이트 메시지를 수락하면 안 된다. 송신 요청이 진행 중인 구간을 덮어쓰지 않는 조건은 단순 위치 계산과 완료 시점 양쪽에서 지켜야 한다.

실습에서 관찰할 값

  • write 크기가 writable 이내인지 본다.
  • consume 크기가 used 이내인지 본다.
  • wrap 전후 바이트 내용이 동일한지 비교한다.

double-mapped 링 연산

RIONetLite/impl/ring_buffer.h

논리 ring capacity, used bytes와 read/write 위치를 관리한다. storage는 DoubleMappedBuffer가 소유하며 실제 등록 span은 논리 크기의 두 배다.

Write는 writable 검사 후 copy하거나 kernel write 크기를 반영한다. Read는 현재 used 구간의 연속 alias 주소를 반환한다. 호출자가 적절한 동기화와 lifetime을 유지해야 한다.

위치 wrap은 logical size에서 한 번 접는다. 허용 입력 크기가 capacity 이내라는 조건이 이 계산을 안전하게 만든다. 두 view가 있다고 저장 용량도 두 배가 되는 것은 아니다.

이 파일에서 추적할 연결

  • DoubleMappedBuffer::Create의 실제 backing을 읽는다.
  • sender lock 아래 호출되는지 확인한다.
  • 수신 PostRecv와 consume 구간을 비교한다.
