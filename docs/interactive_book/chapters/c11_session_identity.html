같은 슬롯의 다음 연결을 구분한다

인덱스는 저장 장소를 가리키고 세대는 연결의 수명을 가리킨다. 둘이 같다는 검사와 연결이 아직 활성이라는 검사도 별개다.

심화큰 그림에서의 위치: P02 ② 연결 · ⑤ 연결 종료

쉽게 말하면 끊긴 플레이어의 슬롯을 새 플레이어가 받았을 때, 늦게 도착한 옛 작업이 새 플레이어에게 가지 않게 하는 방법이다. SessionId의 index는 자리 번호, generation은 그 자리를 몇 번째로 쓰는 연결인지를 뜻한다.

처음 읽는다면 첫 절의 “DB 요청 뒤 끊기고 새 클라이언트가 같은 슬롯을 받는” 예만 이해해도 이 규칙을 지킬 수 있다.

게임 작업이 돌아왔을 때 연결이 바뀔 수 있다

인덱스 7의 클라이언트가 DB 요청을 보낸 뒤 끊기고 새 클라이언트가 같은 슬롯을 사용했다고 가정한다. 작업에 인덱스만 저장했다면 나중의 응답을 새 클라이언트에게 보낼 수 있다. SessionId는 32비트 index와 64비트 generation을 묶어 이 두 연결을 구분한다. 작업을 시작할 때 전체 ID를 복사하고 응답 시점에도 전체 ID로 Send 또는 RequestClose한다.

RIO 완료에도 세대가 들어 있다. 요청에 기록한 session_unique_Id와 현재 세션의 UID가 다르면 오래된 완료로 분리한다. 완료가 늦게 도착했다는 이유만으로 새 연결의 카운터나 버퍼 위치를 변경하지 않는다. 송신 오류 뒤 연결을 닫는 경로 역시 세대를 함께 전달해야 한다.

식별 일치가 Active를 뜻하지 않는다

SessionLifecycle::Matches는 index와 0이 아닌 generation이 일치하는지를 확인한다. 이 함수 자체는 현재 상태가 Active인지 검사하지 않는다. 종료 중이거나 Free가 된 슬롯도 새 예약 전까지는 같은 세대 값을 가질 수 있다. 작업의 권한을 판단할 때 식별과 상태를 서로 대신 사용하지 않는다.

상태의미주의점
Free새 연결 예약 가능이전 세대 숫자가 남아 있어도 활성 연결이 아니다.
Accepting슬롯 예약과 setup 진행접속 콜백 전 실패도 회수해야 한다.
Active연결 활성네트워크 허용·peer close의 송신 접수 플래그도 확인한다.
Draining첫 종료 전이 적용새 요청과 기존 완료의 처리를 구분한다.
Closing소켓 닫기와 통지 진행완료가 아직 남을 수 있다.
Quarantined새 연결로 덮어쓰지 않는 격리참조와 통지 조건 뒤 Free로 돌아간다.

이 표는 실제 enum의 이름이다. “연결됨→끊어짐”이라는 두 상태의 개념 그림으로 내부의 모든 단계가 구현됐다고 해석하지 않는다. peer FIN 대기 같은 별도 제어 플래그도 생명주기 상태와 완전히 같지 않다.

정리한 뒤 재사용하고 옛 작업을 전달한다

TryReserve는 Free에서 Accepting으로 전이하는 데 성공한 소유자만 세대를 증가시킨다. TryRecycle은 Quarantined 상태, 닫힘 통지, outstanding I/O와 pending_events가 모두 조건을 만족해야 성공한다. CAS로 첫 전이의 소유자를 정하므로 두 스레드가 같은 연결 종료를 각각 처음인 것처럼 적용하지 않는다.

실험의 pending_events는 SessionLifecycle 헬퍼 인자가 지원하는 조건을 관찰하기 위한 값이다. 현재 TcpSession::TryRecycle은 transport의 Outstanding과 pending_events=0을 넘긴다. 게임 큐가 빌린 이 슬롯의 재사용을 직접 막는 것은 아니며 QueuedEventAdapter가 자기 세대 gate와 parked close로 이벤트 순서를 별도로 보호한다. 두 계층의 수명을 하나의 카운터라고 설명하지 않는다.

64비트 값을 Number로 줄이지 않는다

JavaScript Number는 모든 uint64 정수를 정확하게 표현하지 못한다. 브라우저 모델은 세대를 10진 문자열로 저장하고 증가할 때 BigInt를 사용한다. JSON과 URL에도 문자열을 넣는다. 실험의 초기 세대를 18446744073709551615로 바꾸어 정상 정리 뒤 재사용하면 0을 건너뛰고 1이 된다.

C++ 헬퍼의 GenerationOverflowSkipsZero는 이 동작을 확인한다. 이것만으로 애플리케이션의 모든 generation 정렬·캐시 정책이 wrap까지 대응한다고 결론내리지는 않는다. 예를 들어 이벤트 gate의 새 세대 비교와 전체 연결 재사용 정책은 별도로 검토해야 한다. 오래된 작업을 영구 저장하는 애플리케이션은 재시작 경계와 ID 보존 기간도 설계한다.

단순히 세대 증가만 검사하면 오래된 close가 새 세션의 네트워크를 끄는 경쟁을 놓칠 수 있다. SessionManager::ForcedClose는 할당·재사용과 같은 lock 아래에서 전체 ID 검증과 종료 전이를 실행한다. Send는 송신 링 lock 안에서도 활성 세대를 검사해 검증과 쓰기 사이의 재사용을 막는다.

세션 수명

stateDiagram-v2
  [*] --> Free
  Free --> Allocated: generation 증가, 0 제외
  Allocated --> Active: accept/RQ 준비
  Active --> Closing: close 승자
  Closing --> Draining: outstanding 정리
  Draining --> Closed: close 통지
  Closed --> Free: transport recycle

index 7/generation 41이 닫힌 뒤 슬롯이 7/42로 재사용될 수 있다. 옛 게임 task에 index만 저장하면 새 사용자에게 송신·종료하게 된다. Send·RequestClose·I/O context·게임 이벤트에 전체 SessionId를 저장한다. uid 검사와 close 전이는 pool reserve/recycle과 같은 lock에서 보호한다.

transport 슬롯의 recycle은 outstanding와 close 통지를 기준으로 하며 게임 이벤트 소비까지 기다리지 않는다. adapter는 별도 gate에서 이전 generation의 parked close가 전달되기 전 새 connected를 거절한다. 이것은 transport와 application event의 서로 다른 수명이다. 게임 워커도 Player.id 전체를 확인해야 한다.

같은 세션의 OnConnected/OnClosed 순서를 보존하고 OnClosed 이후 OnData는 없다. accept는 첫 recv 게시까지 슬롯 보호를 유지한다. close 요청은 한 승자만 전이하며 제어 mailbox의 중복은 합친다. idle_timeout_ms는 마지막 수신 기준 약 1초마다 검사하므로 정확한 밀리초 타이머가 아니다. peer FIN drain도 deadline을 사용한다.

generation으로 오래된 작업을 거절한다

세션 풀은 같은 index를 여러 연결에 재사용한다. index 7의 사용자 A가 나간 뒤 사용자 B가 index 7을 받으면 A의 지연 DB 결과는 B의 작업이 아니다. SessionId는 index와 64비트 generation을 함께 담아 이 차이를 표현한다.

TryReserve가 Free에서 Accepting으로 바꾸는 데 성공하면 generation을 증가시킨다. 0은 유효 세대로 쓰지 않고 wrap이 발생하면 1로 바꾼다. index만 맞는지 확인하는 map이나 delayed task는 이 보호를 무효화하므로 전체 id를 저장한다.

SessionLifecycle의 상태는 Free, Accepting, Active, Draining, Closing, Quarantined다. close의 한 승자는 TryBeginClose의 compare-exchange로 정한다. close notification도 별도 원자 flag로 한 번만 허용한다.

generation이 맞더라도 사용 가능 상태를 보장하지 않는다. Matches는 정체성을 검사하고 Active와 accepting send flag는 행동 가능성을 검사한다. “맞는 연결인데 종료 중”과 “다른 세대”는 서로 다른 실패다.

generation으로 오래된 작업을 거절한다: 적용한다

DB 작업을 큐에 넣을 때 SessionId를 복사하고 결과가 돌아오면 owner worker에서 Player.id와 비교한다. 같은 index의 Player가 존재해도 generation이 다르면 결과를 버린다. 네트워크 Send의 세대 검사만 믿고 게임 상태를 먼저 바꾸면 충분하지 않다.

실습은 연결 A의 id를 보관하고 닫은 뒤 슬롯을 재사용한 B에 대해 A의 Send와 RequestClose를 시도한다. B가 계속 정상 왕복하고 A의 호출이 stale 또는 false로 끝나는지 확인한다.

실습에서 관찰할 값

  • 모든 지연 task에 전체 id를 넣는다.
  • close 승자가 한 명인지 확인한다.
  • recycle 전에 outstanding가 0인지 확인한다.

generation이 맞으면 Player의 방 상태도 예전과 같다고 볼 수 있는가.

해설 펼치기

없다. 같은 연결 안에서도 룸 이동이나 요청 취소가 발생한다. 세션 세대는 연결 정체성만 보호한다. 게임 작업에는 별도의 request id나 상태 버전을 추가해야 할 수 있다.

src/detail/session_lifecycle.h

이 helper는 OS 자원 없이 연결 상태와 generation, close notification을 관리한다. 실제 socket과 RIO outstanding는 TcpSession이 제공하고 recycle 판단에 숫자로 전달한다.

CAS가 close와 reserve의 승자를 정한다. Matches는 정체성만 검사하므로 active 여부와 분리한다. close_notified flag는 callback이 한 번만 발생할 조건을 만든다.

TryRecycle는 outstanding와 pending 이벤트, close notification을 검사한다. 현재 transport caller가 pending_events에 0을 넘긴다는 사실을 읽고 application event 소비까지 기다린다고 오해하지 않는다.

  • pool lock과 ForcedClose 관계를 읽는다.
