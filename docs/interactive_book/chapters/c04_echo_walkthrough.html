받은 패킷이 응답이 되기까지

지도에서의 위치는 이 장의 쉽게 말하면 상자에서 설명한다.

네트워크 호출의 성공, 패킷의 완성, 응답의 송신 완료는 서로 다른 순간이다. EchoServer 한 연결을 따라가며 그 사이에 누가 데이터를 소유하는지 확인한다.

입문큰 그림에서의 위치: P03 패킷 하나가 왕복하는 길

쉽게 말하면 P03의 순서도를 실험으로 한 단계씩 실행해 보는 장이다. 수신 완료, OnData, Send, 송신 완료가 서로 다른 순간이라는 것을 직접 확인한다.

처음 읽는다면 L01 실험의 “단계별 재생”을 먼저 눌러 본 뒤 본문을 읽는다.

수신 콜백 한 번이면 응답도 한 번인가?

클라이언트가 문자열 rio를 보냈다고 가정한다. 서버가 받은 범위는 문자열 세 글자만으로 이루어지지 않는다. Echo 예제는 먼저 전체 패킷 크기를 나타내는 4바이트 헤더를 읽는다. 클라이언트가 보내야 할 바이트는 00 00 00 07 72 69 6F다. 맨 앞의 7에는 헤더 자체도 포함된다.

TCP는 이 일곱 바이트를 2바이트, 3바이트, 2바이트로 나누어 전달할 수 있다. 반대로 두 패킷이 한 수신 완료에 함께 들어올 수도 있다. 따라서 OnData 횟수와 응답 횟수를 같다고 가정하면 안 된다. 이번 장에서는 이미 연결된 세션에서 패킷 하나가 모두 모인 경우의 왕복을 먼저 따라간다. 조각을 모아 읽는 과정은 C13의 수신 조각에서 다시 실험한다.

실행 전에 예측한다

EchoHandler가 Send에서 kQueued를 받았다. 이 순간 클라이언트가 응답을 읽었다고 말할 수 있는가? 아래 흐름을 따라가면서 송신 링에 데이터가 들어간 시점과 운영체제 완료가 도착한 시점을 구분해 본다.

서버보다 오래 살아야 하는 객체를 먼저 만든다

main은 설정, 로거, 핸들러를 만들고 Server::Create를 호출한다. 핸들러와 로거는 서버가 빌려 쓰는 객체다. 서버를 정지시키고 파괴할 때까지 유효해야 한다. Create가 성공한 뒤 handler.Attach(*server)로 응답에 사용할 서버 주소를 저장하고, 그 뒤 Start로 accept와 I/O 워커를 실행한다.

Attach는 라이브러리 API가 아니라 이 예제 핸들러의 보조 함수다. 생성 도중 아직 존재하지 않는 서버를 핸들러 생성자에 넘기는 대신 두 단계를 사용한다. 콜백이 시작될 수 있는 Start 이전에 연결하므로 정상 실행에서는 server_가 준비된 상태다. 핸들러의 null 검사는 이를 대신하는 동기화 수단이 아니다.

// 실제 예제의 초기화 순서를 설명하기 위한 의사 코드다.
ConsoleLogger logger;
EchoHandler handler(config.max_message_bytes, observability_enabled);
auto server = Server::Create(config, handler, logger_pointer);
if (!server) { /* 오류를 보고하고 종료한다. */ }
handler.Attach(*server);
auto started = server->Start();

Create와 Start는 각각 std::expected의 오류를 확인한다. 예제는 생성 실패에 종료 코드 3, 시작 실패에 4를 사용한다. 실행 안내에서 “서버가 실행된다”는 말은 생성 성공 메시지만으로 확인하지 않고 listen 상태와 실제 바이트 왕복까지 확인해야 한다.

요청·완료·콜백을 한 단계씩 연결한다

아래 실험은 하나의 연결에서 성공한 응답 경로를 펼친다. 세션의 수신 요청은 이미 연결 준비 과정에서 게시된다. 수신 완료에서는 먼저 컨텍스트의 세대와 상태, 완료 길이를 확인한다. 완료 바이트를 수신 링에 반영한 뒤, 빈 공간이 있으면 다음 수신을 현재 애플리케이션 콜백보다 먼저 게시한다. 다음 수신을 게시한다는 말은 아직 처리하지 않은 완료를 무시한다는 뜻이 아니다.

같은 세션의 현재 콜백은 소유 I/O 워커가 실행한다. 다른 세션의 워커와 커널 작업은 그동안 진행할 수 있다. 그림의 단계를 직렬로 제시한 것은 설명을 위한 선택이며, 모든 세션이 하나의 전역 순서로 실행된다는 뜻이 아니다. 단계 이동에 쓰는 0.9초 간격도 실제 RIO 지연 시간과 관계없다.

수신 완료에서 선게시한 다음 요청이 등록 버퍼를 계속 참조할 수 있다. 마지막 단계에서 응답 송신의 outstanding이 0이 되어도 수신 outstanding은 1로 남는다. 송신 종료와 서버 전체의 메모리 해제를 한 상태로 합치지 않는 이유다.

OnData는 처리한 범위의 크기를 반환한다

위 그림의 장면을 실제 코드로 내려가 읽는다. 줄 번호 옆 작은 숫자는 해당 단계가 시작하는 곳이다.

코드 따라가기의 단계는 아래 설명과 실제 코드 버튼으로도 확인할 수 있다.

수명과 복사 규칙은 이어지는 본문을 따른다.

수명과 복사 규칙은 이어지는 본문을 따른다.

EchoHandler::OnData는 받은 span을 LengthPrefixedDecoder::Decode에 넘긴다. 디코더는 완전한 패킷을 찾을 때마다 람다를 호출한다. 람다가 받는 packet에는 헤더와 본문이 모두 들어 있다. 예제는 이 범위 전체를 다시 보내므로 클라이언트가 같은 프레이밍 규칙으로 응답을 읽을 수 있다.

정상 경로의 반환값은 decoded.consumed_bytes다. 아직 패킷이 완성되지 않았다면 0을 반환할 수 있다. 그렇다고 다음 데이터를 기다리는 내부 무한 루프를 돌지 않는다. 이번 콜백이 끝나면 미소비 바이트가 수신 링에 남고, 다음 수신 완료 때 더 긴 범위로 다시 전달된다. 디코더 객체 자체에는 수신 조각을 축적하는 컨테이너가 없다.

콜백 span을 나중에 쓰려고 주소만 저장하면 안 된다. 반환 뒤에는 링의 읽기 위치가 이동하고 다른 데이터가 그 저장소를 사용할 수 있다. 현재 Echo처럼 콜백 안에서 바로 Send를 부르는 경우에는 송신 함수가 반환 전에 내부로 복사한다. 반면 DB나 게임 처리에 넘길 데이터는 C18의 소유하는 이벤트 큐로 옮겨야 한다.

Send의 반환값을 연결 정책으로 바꾼다

Send가 kQueued를 반환하면 내부 송신 경로가 바이트를 받아들인 것이다. RIO 요청은 이미 진행 중일 수도 있고, 기존 요청 뒤에서 기다릴 수도 있다. 상대 프로그램이 읽거나 처리했다는 확인은 포함하지 않는다. 게임에서 “보상 지급 응답을 처리했다” 같은 확인이 필요하면 별도의 요청 번호와 애플리케이션 응답을 설계한다.

반환값Echo에서의 처리사용자가 알아야 할 범위
kQueued다음 패킷 해석을 계속한다.데이터는 내부 소유다. 원래 span은 콜백 반환 뒤 보관하지 않는다.
kWouldBlock로깅이 켜져 있으면 결과를 남기고 kOverloaded 종료를 요청한다.메시지 전체를 받지 못한 배압이다. 콜백에서 성공할 때까지 반복하지 않는다.
kUnavailable마찬가지로 overload 종료를 요청한다.즉시 재시도하면 완료 처리를 막을 수 있다.
오래된 세션·종료 중·메시지 크기 오류 등현재 예제는 관측 기능이 켜져 있으면 거절 결과를 기록한다.모든 거절을 자동 재전송하거나 같은 종료 이유로 처리한다고 설명하지 않는다. 공개 반환값은 A01에서 구분한다.

예제의 종료 요청은 비동기다. 람다가 종료를 요청했다고 현재 Decode 반복이 즉시 중단되지는 않는다. 같은 span에 뒤 패킷이 있으면 그 람다도 실행될 수 있다. 마지막으로 RequestClose를 호출한 줄만 보고 콜백 내부의 모든 후속 실행이 사라진다고 가정하면 안 된다.

길이 헤더가 잘못되면 예제는 kProtocolError로 종료를 요청하고 data.size()를 반환한다. 닫을 연결의 이번 입력 전체를 소비하는 정책이다. 정상 상태에서 매번 data.size()를 반환하는 코드와 구분한다. 정상 입력에서 그렇게 반환하면 불완전한 꼬리를 버릴 수 있다.

실제 프로세스에서 바이트를 왕복시킨다

저장소 루트에서 다음 순서로 실행한다. 빌드 스크립트는 지정한 구성의 단위 테스트와 통합 테스트도 실행한다. EchoServer의 기본 포트는 32452다. 이미 다른 프로세스가 사용하면 서버와 클라이언트에 같은 새 포트를 지정한다.

tools\build.ps1 -Configuration Debug -Rebuild
tools\build.ps1 -Configuration Release -Rebuild
bin\x64\Release\EchoServer.exe --port 32452 --workers 2 --max-sessions 8 --duration 30

# 다른 터미널에서 짧은 실제 프로세스 검사를 재현한다.
python tools/book/verify_echo.py --configuration Release

마지막 검사는 별도의 loopback 포트를 골라 새 EchoServer를 실행하고, 2+3+2로 나눈 요청, 두 패킷의 병합 요청, 잘못된 길이 3의 종료를 확인한다. 검사가 실행한 서버는 stop 파일로 정상 종료하며 종료 코드 0을 요구한다. stdout과 stderr는 logs/book_echo/, 결과는 .artifacts/book/echo/에 남는다. 이것은 실제 Winsock/RIO 검사이며 위 브라우저 실험과 별개다.

콘솔에서 직접 띄운 서버는 quit 또는 Ctrl+C로 종료한다. 핸들러가 플래그를 바꾸면 주 스레드가 Stop(kGraceful)를 호출한다. Ctrl+C 처리 함수나 OnData에서 직접 서버 객체를 파괴하는 순서로 바꾸지 않는다. --duration 0은 시간 제한이 없다는 뜻이며, stop 파일을 지정하면 그 파일의 존재도 종료 조건으로 사용한다.

테스트가 무엇을 증명하는지 나눈다

PacketDecoderTest.WaitsForFragmentsAndDecodesCoalescedPackets는 길이 해석과 소비 범위를 OS 없이 확인한다. IntegrationSmokeTest.EchoesFragmentedAndCoalescedFrames는 실제 RIO 연결에서 분할과 병합 응답을 확인한다. 별도 실행 파일 검사는 예제의 명령행과 주 스레드 종료 경로까지 확인한다. 하나의 테스트 통과를 이 셋 모두의 통과로 바꾸지 않는다.

bin\tests\x64\Release\RIONetLite.UnitTests.exe --gtest_filter=PacketDecoderTest.*
bin\tests\x64\Release\RIONetLite.IntegrationTests.exe --gtest_filter=IntegrationSmokeTest.EchoesFragmentedAndCoalescedFrames

이번 판에서 재현한 실제 실행 결과와 제외한 메모리·긴 부하 검사는 A05 실행 기록에 따로 적었다. 소규모 loopback 성공을 운영 환경 처리량 승인으로 해석하지 않는다.

게임 처리로 확장할 때 바뀌는 경계

이 예제에는 별도 게임 로직 워커가 없다. Echo의 짧은 디코딩과 응답을 I/O 콜백에서 바로 처리하는 최소 사용 예제다. 여기에 동기 DB 조회, 파일 저장, 다른 스레드 응답 대기를 붙이면 같은 I/O 워커가 다른 연결의 완료도 처리하지 못한다. 단순한 함수 호출 한 줄을 추가해도 네트워크 지연이 여러 세션으로 퍼질 수 있다.

확장할 때는 payload를 소유하는 큐, 같은 세션의 순서, 세션 세대 검증, 포화 정책을 함께 설계한다. 큐에 넣는 순간 원래 span의 수명은 길어지지 않는다. 응답을 돌려줄 때는 저장한 SessionId 전체를 사용한다. C19의 ChatServer는 이 경계를 실제 로직 shard와 연결하는 예제다.

다음에는 C05에서 게시와 완료의 계약을 보거나, C13에서 같은 패킷을 수신 조각으로 나누어 본다.

Echo 코드 읽기

EchoServer 전체 코드가 빌드되는 한 파일 예제다. 복사한 부분 코드 대신 이 파일을 열고 첫 실행을 완료한다. README의 C++ 블록은 즉시 종료하는 package smoke 예제이므로 계속 대기하는 서버와 구별한다.

1. EchoHandler는 공개 EventHandler를 구현한다. LengthPrefixedDecoder의 maximum은 header를 포함한 전체 메시지 크기다.

2. main은 logger와 handler를 먼저 만들고 Server를 나중에 만든다. 역순 파괴 시 handler/logger가 Server보다 오래 산다. Create는 bind와 버퍼 확보를 수행하며 실패 시 Error를 확인한다.

3. handler.Attach(*server)는 callback이 Send/RequestClose를 호출할 대상을 연결한다. Start 전에 붙인다. 이 포인터의 수명은 main의 Server 수명 안이다.

4. OnData는 완성된 프레임마다 Send한다. kQueued는 복사·수락이다. kWouldBlock이면 무한 retry하지 않고 overload close를 요청한다. decoder 오류는 protocol close다. 반환값은 DecodeResult.consumed_bytes라 미완성 바이트가 transport에 남는다.

5. main은 quit·Ctrl+C·duration·stop-file을 기다린다. callback에서 Stop을 부르지 않는다. 종료 신호를 주 스레드가 받아 Stop(kGraceful)의 결과를 확인한다.

handler/logger 생성 → Create → Attach → Start
  → OnData에서 decode와 빠른 Send
  → 주 스레드 종료 신호 → Stop 결과 확인 → Server 파괴 → handler/logger 파괴

실험은 LoadClient --scenario split, coalesce, half-close 순서로 수행한다. 각 실행의 JSON에서 오류와 누락이 0인지 확인한다. frame 길이를 잘못 만들면 protocol 종료가 정상 결과다. 프레이밍은 실제 소비량을, API 계약은 실패별 동작을 설명한다.

이 예제는 최소 네트워크 사용을 보여준다. 룸·DB·파일 처리는 callback에 추가하지 않고 게임 워커로 넘긴다.

EchoServer로 바이트 왕복을 확인한다

현재 EchoServer는 4바이트 총 길이 prefix의 완성된 frame을 그대로 Send하는 최소 예제다. 게임 payload의 의미는 해석하지 않지만 길이와 경계는 검사한다. 임의 문자열을 보내는 raw echo와 구분한다. 같은 frame이 돌아오는지 비교하는 것은 접속 성공보다 강한 증거다.

Echo handler는 Server에 연결된 뒤 OnData에서 LengthPrefixedDecoder로 완성 frame을 찾고 그 span을 Send한다. Send가 반환하기 전에 복사하므로 callback 밖에 span을 보관하지 않는다. kWouldBlock과 kUnavailable은 overloaded close를 요청하며 잘못된 길이는 protocol close다.

콘솔 신호 handler는 종료 요청 flag만 바꾼다. 실제 Stop은 main의 소유 스레드가 수행한다. callback이나 signal 처리에서 직접 워커 join을 시작하면 자기 자신을 기다리거나 실행 제한을 위반할 수 있다. 종료 요청과 종료 실행을 나누는 구조를 기억한다.

load_client는 다양한 입력과 disconnect 형태로 Echo를 검사한다. 처음에는 작은 연결 수와 정확성부터 본다. throughput 수치는 검증 환경, 대기 모드와 warmup을 함께 지정해야 의미가 있으며 이 예제의 로컬 결과를 게임 전체 성능으로 확대하지 않는다.

EchoServer로 바이트 왕복을 확인한다: 적용한다

터미널 하나에서 EchoServer를 실행하고 다른 터미널에서 load_client를 실행한다. 완료된 응답 바이트를 보낸 바이트와 비교하고 서버를 정상 종료한다. 접속 실패라면 같은 PC의 주소, 포트, 이미 사용 중인 프로세스를 먼저 확인한다.

quit이나 Ctrl+C 뒤의 exit와 지표를 확인한다. 창을 강제로 닫아 테스트를 끝내면 shutdown의 자원 회수 증거가 남지 않는다. 자동 실습은 duration 또는 stop-file을 사용해 소유 스레드의 정상 종료 경로를 통과시킨다.

실습에서 관찰할 값

  • 에코 payload가 원본과 같은지 확인한다.
  • Send의 실패 결과를 숨기지 않는다.
  • 서버 정상 exit와 남은 연결 수를 확인한다.

생각하고 확인한다

Echo의 4바이트 prefix frame을 Chat에 그대로 보내도 되는가.

해설 펼치기

안 된다. Echo는 총 길이 prefix 뒤 payload를 그대로 반사하지만 Chat은 8바이트 헤더의 version과 type, 타입별 payload와 phase를 검사한다. 같은 TCP transport라도 application framing 계약이 다르다.

실제 framed EchoServer

samples/echo_server/main.cpp

현재 Echo는 4바이트 총 길이 prefix를 사용한다. decoder는 완성 frame을 찾아 그 바이트를 그대로 Send하며 LoadClient도 이 형식을 사용한다. 단순 임의 문자열 echo라고 설명하지 않는다.

handler의 Attach는 Server 생성 성공 뒤 Start 전에 수행한다. Console signal은 flag만 바꾸고 owner main이 graceful Stop을 실행한다. observability 옵션으로 로그와 지표 비용을 선택한다.

option parser와 종료 loop까지 읽어 실습 명령의 실제 인수를 확인한다. stop-file과 duration은 자동 검증에서 정상 종료 경로를 만드는 수단이다.

이 파일에서 추적할 연결

  • LoadClient의 MakeFrame과 checksum을 읽는다.
  • packet_decoder.h의 partial consume를 본다.
  • stress 도구의 stop-file과 exit 판정을 확인한다.
