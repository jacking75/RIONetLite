완료를 처리할 주체를 남기고 종료한다

종료는 자원을 역순으로 지우는 일만이 아니다. 새 작업을 차단하고, 이미 진행 중인 작업을 끝내며, 실패했을 때 해제하면 안 되는 자원을 판단하는 과정이다.

한 호출이 종료를 소유하고 나머지는 결과를 기다린다

Server::Stop은 생명주기 mutex와 ShutdownCoordinator로 첫 종료 소유자를 정한다. Stopping 상태를 본 다른 Stop 호출자는 mutex를 놓고 완료 신호를 기다린 뒤 저장한 결과를 돌려받는다. 이미 Stopped라면 같은 성공 또는 저장한 오류를 반환한다. 첫 호출 뒤에 온 호출이 graceful 예산을 새로 시작하지 않는다.

같은 서버의 이벤트·로거 콜백 안에서는 Stop을 거절한다. 그 스레드를 기다리는 join을 자기 호출 스택 안에서 시작할 수 있기 때문이다. 서버 객체를 소유한 주 스레드에 종료 플래그를 전달한다. 다른 스레드가 Send를 호출하는 동안 서버 객체를 옮기거나 파괴해도 된다는 계약은 없으므로 모든 애플리케이션 호출자를 정리한다.

공개 Stop은 transport API의 shared lock 호출이 빠져나오도록 exclusive lock을 잠시 잡고 놓는다. 이 lock을 잡은 채 콜백을 join하면 콜백의 Send와 교착할 수 있으므로 실제 End와 join 전에 해제한다. 단순히 mutex 하나를 추가하는 것보다 무엇을 기다리는 동안 그 mutex를 보유하는지 확인해야 한다.

잘못된 해제 순서를 선택해 본다

이 모델의 “새 게시 차단”은 새 애플리케이션 진입을 묶은 단계다. graceful에서 이미 접수한 송신의 내부 재게시를 일찍 막는 동작이 아니다. 실제 세부 플래그와 API lock은 원문에서 구분한다. 모델은 의존 관계를 선택하는 도구이며 모든 함수 호출의 정확한 스레드 시각을 재현하지 않는다.

워커를 먼저 없애고 outstanding이 0이 되기를 기다리면 완료를 처리할 주체가 없어질 수 있다. 등록 버퍼를 먼저 해제하면 커널 참조가 남아 use-after-free가 된다. CQ를 먼저 해제하면 완료 회수와 요청 수명 추적을 잃는다. 정상 종료에서 자원 해제 순서가 필요한 이유를 실패 선택으로 확인한다.

immediate도 안전한 회수를 생략하지 않는다

graceful은 이미 접수한 송신에 완료 기회를 준다. immediate는 이 송신 대기를 생략하고 연결을 닫는 경로로 간다. 그러나 소켓 취소 뒤 돌아오는 완료, 워커 join과 등록 버퍼 참조 정리는 여전히 필요하다. immediate를 “메모리부터 즉시 delete”라는 옵션으로 구현하지 않는다.

서버의 graceful_shutdown_timeout_ms는 Stop 진입 이후 API 배출, accept join, 송신 drain과 I/O 종료가 공유하는 예산이다. 단계마다 같은 전체 timeout을 새로 주면 전체 대기 시간이 여러 배가 될 수 있다. 현재 End는 절대 deadline과 남은 시간을 전달한다. peer FIN drain 기한과 게임 로직 배출 기한은 이 값에 자동 포함되지 않는다.

이 예산은 사용자 callback을 강제로 중단하는 wall-clock 보장이 아니다. C++ join은 콜백의 무한 대기나 deadlock을 중단하지 못한다. 네트워크 콜백을 짧고 비차단으로 유지해야 종료 예산도 의미가 있다. 바깥 watchdog의 프로세스 종료 정책이 필요하다면 라이브러리의 정상 Stop 성공과 구분해 운영 절차에 적는다.

기한 초과 뒤 추가 drain과 자원 보존을 구분한다

기한 초과나 CQ 손상이 있으면 ForceDrainAfterTimeout이 소켓부터 abort한다. 그 뒤 최대 500ms의 추가 drain에서 취소 완료를 꺼내 recv/send 참조를 retire한다. 이 경로는 또 다른 heap 할당에 의존하지 않도록 크기 4096의 결과 배열을 스택에 둔다. 이 추가 500ms 때문에 설정된 timeout을 전체 함수의 엄격한 최대 wall time으로 설명하면 안 된다.

추가 회수 뒤에도 remaining_outstanding이 남으면 등록 버퍼·매핑, notification과 CQ의 소유권을 의도적으로 포기할 수 있다. 커널이 참조하는 메모리를 해제하지 않기 위한 실패 선택이다. 프로세스 메모리가 모두 반환됐다는 뜻이 아니며 정상 서비스 상태로 재사용하지 않는다. 보존 사실과 수치를 숨기지 않는다.

공개 결과는 기한 초과라면 kShutdownTimedOut이고, CQ 손상이면 kInternalError 경로다. message에는 remaining_outstanding과 remaining_active_sessions가 포함될 수 있다. state는 Stopped가 되어도 성공적인 안전 회수와 같은 뜻은 아니다. 반복 Stop도 저장한 실패를 반환한다.

transport 뒤에 게임 처리도 배출한다

Server::Stop은 애플리케이션의 PlayerMap, DB 작업, adapter queue와 broadcast inbox를 대신 끝내지 않는다. 먼저 transport의 이벤트 생산을 중지하고, 남은 close를 포함한 큐와 실행 중 게임 작업을 배출한 뒤 로직 워커를 join한다. 빈 링만 보고 끝내면 parked close나 처리 중인 작업이 남을 수 있다.

Chat의 StopAfterDrain은 adapter depth, active_workers와 pending_broadcasts를 함께 확인한다. active_workers는 TryPop이 depth를 줄이기 전에 증가시켜 그 이벤트가 방송을 만드는 중간 순간도 포함한다. 마지막 출력 Logic drain: active_players=0 queued_events=0 pending_broadcasts=0과 프로세스 종료 코드 0을 확인한다. 이 함수 자체는 별도의 강제 timeout을 구현하지 않으므로 향후 긴 작업을 붙이면 앱의 종료 정책도 확장해야 한다.

정상 종료

주 스레드에서 Stop(kGraceful)을 호출한다. 같은 서버의 event/logger callback에서 호출하면 kInvalidState다. callback은 종료 요청 flag만 전달하고 주 스레드가 Stop한다. 객체 이동·파괴는 모든 application 호출자가 종료된 뒤 수행한다.

sequenceDiagram
  participant App
  participant Server
  participant Accept
  participant Worker
  App->>Server: Stop
  Server->>Server: Stopping, 진입 Send/Close 배출
  Server->>Accept: listen close, join
  Server->>Worker: 수락 send drain 후 close
  Worker-->>Server: 완료 정리, join
  Server->>Server: buffer/CQ/notification/Winsock 정리
  Server-->>App: 결과
  App->>App: game queue와 Player drain, logic join

graceful_shutdown_timeout_ms는 Stop 진입 이후 API 배출·accept join·송신 drain·I/O 종료가 공유하는 예산이다. immediate는 수락 송신 대기를 생략하지만 취소 완료는 정리한다. 동시·반복 Stop은 같은 결과를 받는다. 늦게 시작한 호출이 예산을 새로 늘리지 않는다.

이 값은 사용자 callback을 강제 중단하는 wall-clock 보장이 아니다. C++ join은 실행 중 callback을 중단할 수 없으므로 callback이 영구 대기하면 Stop도 기다린다. 시간 초과 뒤 안전 회수를 위한 최대 500ms 추가 drain이 있다. timeout을 정상 종료로 취급하지 않는다.

timeout에는 socket을 abort하고 취소 완료를 다시 꺼낸다. 여전히 outstanding이면 커널이 쓸 수 있는 buffer·mapping·CQ 소유권을 의도적으로 포기해 조기 해제를 막는다. 이 실패 상태에서는 프로세스를 정상 서비스로 재사용하지 않는다. Error.message의 remaining_outstanding/remaining_active_sessions와 로그를 보존한다. CQ corrupt도 실패다.

Stop은 transport만 끝낸다. adapter의 parked close를 포함한 depth, broadcast inbox, 실행 중 game task와 Player를 별도로 배출해야 한다. Chat은 마지막 Logic drain: active_players=0 queued_events=0 pending_broadcasts=0과 exit 0을 확인한다. peer_close_drain_timeout_ms는 FIN 뒤 수락 송신을 기다리는 별도 연결 예산이다.

transport와 game을 차례로 배출한다

Server::Stop은 accept와 transport I/O를 끝내지만 adapter와 게임 작업을 자동으로 모두 소비하지 않는다. Chat은 먼저 transport를 Stop하고 그 뒤 StopAfterDrain으로 game queue와 broadcast, Player를 정리한다. 생산자가 끝난 뒤 소비자를 끝내는 순서다.

depth==0만으로는 충분하지 않다. worker가 event를 꺼낸 순간 depth는 줄지만 아직 ProcessPacket을 실행하고 broadcast를 만들 수 있다. active_workers를 TryPop 전에 증가시키고 작업 뒤 감소시켜 이 실행 중 구간을 관찰한다.

pending_broadcasts는 각 inbox 항목을 포함한다. inbox를 꺼낸 뒤 peer에게 Send하는 동안에는 active_worker가 남아 있어 종료가 너무 빨리 끝나지 않는다. 모든 카운트가 배출된 뒤 running을 끄고 thread를 join한다.

마지막 active_players=0은 Closed 소비로 Player가 사라졌는지 확인하는 추가 조건이다. 큐가 비었어도 close가 유실되면 Player가 남는다. Chat은 이 상태를 실패 exit로 보고하므로 일반 출력 한 줄이 실제 종료 gate가 된다.

종료 직전에 여러 shard에서 chat을 보내고 서버 stop-file을 만든다. server Stop 뒤 더 이상 event가 생산되지 않는지, worker가 남은 close와 broadcast를 배출하는지 확인한다. 마지막 카운트와 exit를 함께 기록한다.

DB task나 timer를 추가하면 그 생산자도 종료 순서에 넣어야 한다. 현재 Chat의 카운트만 유지한 채 외부 task가 계속 event를 넣으면 empty를 확인한 직후 다시 작업이 생길 수 있다.

동시 Stop은 한 종료 결과를 공유한다

Server::Stop은 lifecycle mutex와 ShutdownCoordinator로 한 호출자가 종료를 맡게 한다. 첫 호출이 Stopping으로 바꾸고 나머지는 완료를 기다린다. Stopped 상태에서 반복 호출하면 같은 stop_error 또는 성공을 반환한다.

Send와 RequestClose는 transport_api_mutex의 shared lock 아래 Running을 확인하고 transport에 진입한다. Stop은 Stopping을 먼저 게시하고 unique lock으로 이미 진입한 호출자를 배출한다. 이 barrier를 통과해야 세션 pool을 지워도 기존 호출자가 raw pointer를 쓰지 않는다.

Stop은 이 unique lock을 worker join까지 유지하지 않는다. callback이 Send 또는 RequestClose를 호출할 수 있어 join 동안 gate를 붙잡으면 worker가 lock을 기다리고 owner는 worker를 기다리는 deadlock을 만들 수 있다.

Server 객체 자체를 다른 스레드에서 move하거나 파괴하는 작업은 이 API gate로 보호하지 않는다. 애플리케이션 호출자가 모두 빠져나와야 한다. move-only와 thread-safe member call은 같은 개념이 아니다.

동시 Stop은 한 종료 결과를 공유한다: 적용한다

sender와 closer thread가 반복 API 호출하는 중 owner에서 immediate Stop을 실행한다. Stop 후 두 application thread를 join하고 객체를 파괴한다. callback은 Closing 결과를 받아 빠져나와야 한다.

동시에 여러 Stop 호출을 만들었을 때 서로 다른 자원 해제를 중복 수행하지 않아야 한다. 실패가 있으면 재호출이 성공으로 바뀌는 것이 아니라 동일 실패를 전달해야 운영자가 실제 문제를 놓치지 않는다.

실습에서 관찰할 값

  • 이미 진입한 Send가 pool clear 전에 끝나는지 본다.
  • gate를 join 동안 유지하지 않는지 본다.
  • 반복 Stop의 error가 동일한지 확인한다.

생각하고 확인한다

같은 mutex로 모든 API와 종료 전체를 감싸면 더 안전한가.

callback에서 종료 실행을 요청하지 않는다

CallbackScope는 thread_local 연결 목록으로 현재 스레드가 어떤 Server의 callback 안에 있는지 표시한다. 중첩 callback과 같은 스레드의 서로 다른 서버를 구분한다. 자신의 callback에서 Start나 Stop을 부르면 InvalidState로 거절한다.

이 제한은 event callback뿐 아니라 Logger::IsEnabled와 Log에도 적용한다. logger는 create, start, stop과 오류 경로에서 호출되므로 logger가 Stop을 재진입하면 lifecycle mutex나 자기 thread join에 걸릴 수 있다.

Logger::Log 예외는 Emit의 catch에서 격리한다. Stop이 noexcept여도 외부 logger가 던지면 terminate가 발생할 수 있어 호출 경계에 방어가 필요하다. IsEnabled는 선언 자체가 noexcept이며 구현자는 예외를 밖으로 내보내지 않는다.

reentrancy 거절은 무한 callback을 강제로 끊는 기능은 아니다. owner flag나 유계 control queue로 종료 의사를 전달하고 callback을 빨리 반환해야 한다. 객체 파괴를 callback에 넣어도 안전하지 않다.

graceful deadline과 안전 회수를 구분한다

graceful Stop은 새 API 수락을 막고 accept를 끝내며 이미 수락한 송신을 기다린 뒤 세션을 닫고 완료를 배출한다. deadline은 Stop 시작에서 한 번 정하고 단계마다 남은 예산을 사용한다. 각 단계에 전체 timeout을 새로 주면 총 대기 상한이 여러 배로 늘어난다.

설정 graceful_shutdown_timeout_ms는 callback을 강제로 선점하는 wall-clock 보장이 아니다. accept나 I/O worker가 실행 중인 사용자 callback을 join으로 기다려야 하므로 callback이 무한 대기하면 Stop도 기다린다. callback 시간을 짧게 유지하는 계약이 먼저다.

시간 초과 또는 corrupt CQ에서는 소켓을 abort해 취소 완료를 유도하고 최대 500ms 추가 safety drain을 수행한다. 이 경로는 정상 graceful 완료가 아니므로 최종 Stop 결과는 실패로 남는다.

그래도 outstanding가 남으면 등록 버퍼·mapping·CQ와 관련 notification handle을 조기 해제하지 않고 소유권을 포기한다. 커널이 참조하는 메모리의 use-after-free를 피하기 위한 치명적 실패 정책이다. 이 서버를 정상 서비스처럼 계속 재사용하지 않는다.

송신을 읽지 않는 peer와 작은 timeout으로 종료를 시도한다. remaining_outstanding와 remaining_active_sessions를 포함한 오류를 기록한다. 안전 정리 후 프로세스가 끝났다고 graceful 성공으로 바꾸지 않는다.

강제 drain은 추가 heap allocation에 의존하지 않도록 stack 결과 배열을 사용한다. 이미 자원 부족인 실패 경로에서 또 allocation이 필요하면 원래 오류보다 더 큰 종료 실패가 생길 수 있다.

실습에서 관찰할 값

  • 모든 종료 단계가 같은 deadline을 쓰는지 본다.
  • callback join의 시간 한계를 문서화한다.
  • timeout 후 오류와 남은 자원을 기록한다.

생각하고 확인한다

해설 펼치기

미완료 커널 요청이 그 메모리를 참조한다면 즉시 해제가 use-after-free를 만든다. 정상 경로는 drain 뒤 해제해야 하고, drain 불가능의 치명적 경로에서는 조기 해제보다 소유권 포기가 안전하다. 이것은 정상 누수를 허용하는 정책이 아니다.
