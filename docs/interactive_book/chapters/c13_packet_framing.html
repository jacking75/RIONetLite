수신한 바이트에서 패킷 경계를 찾는다

TCP가 전달한 범위와 애플리케이션 메시지의 범위를 분리하면, 조각을 어디에 남기고 언제 소비해야 하는지 명확해진다.

입문큰 그림에서의 위치: P02 ③ 수신

쉽게 말하면 TCP로 받은 바이트 덩어리에서 길이 헤더로 메시지를 하나씩 잘라 내는 방법이다. 쪼개져 오면 기다리고, 붙어서 오면 여러 번 처리하고, 처리한 만큼만 소비량으로 돌려준다.

처음 읽는다면 2+3+2로 들어올 때 절의 L09 실험을 재생해 본다.

보낸 횟수는 받은 횟수가 아니다

클라이언트가 메시지 두 개를 두 번의 송신 호출로 보냈더라도 서버가 같은 횟수로 수신하지는 않는다. TCP는 순서가 있는 바이트 스트림을 제공한다. 애플리케이션이 만든 메시지의 경계는 별도 규칙으로 찾는다. “첫 네 바이트가 도착했으니 본문도 왔다”거나 “이번 수신의 끝이 패킷의 끝이다”라는 가정을 코드에 넣지 않는다.

RIONetLite의 OnData는 현재 읽을 수 있는 연속 범위를 빌려 준다. 그 안에는 이전에 남긴 조각과 새로 받은 바이트가 함께 있을 수 있다. 받은 범위를 곧바로 C++ 구조체 포인터로 캐스팅하면 길이 부족, 정렬, 바이트 순서 문제를 동시에 만들 수 있다. 디코더는 필요한 바이트가 있는지 먼저 확인하고 정수 값을 바이트 단위로 조합한다.

길이 7은 헤더와 본문을 합친 값이다

Echo의 LengthPrefixedDecoder는 4바이트 big-endian 헤더를 사용한다. 00 00 00 07은 전체 길이 7이다. 뒤의 72 69 6F는 ASCII rio다. 본문 길이가 7인 패킷이라고 읽으면 네 바이트를 더 기다리게 되고 다음 패킷의 헤더를 본문으로 오인한다.

바이트 위치값의미
0~300 00 00 07헤더를 포함한 전체 길이 7
4~672 69 6F본문 rio
7다음 패킷의 첫 바이트이번 본문에 포함하지 않는다.

최소 패킷 길이는 헤더 크기인 4다. 길이 4는 본문이 비어 있는 유효한 프레임이며 패킷 콜백을 한 번 호출한다. 길이 3은 헤더보다 작으므로 kInvalidLength다. 최대 길이는 생성자에 준 max_packet_bytes를 포함해 비교한다. 한도가 16이면 16은 허용되고 17은 kMessageTooLarge다.

서버 설정의 max_message_bytes 범위 검사와 프로토콜의 최소 길이는 같은 검사가 아니다. 설정 검증은 양수이고 양쪽 버퍼에 들어가는지를 검사한다. 길이 헤더 프로토콜을 쓰는 애플리케이션은 최소한 헤더가 들어갈 한도를 선택해야 한다. 설정값 1이 자원 예산 검사에 통과했다고 길이 4의 정상 패킷을 해석할 수 있는 것은 아니다.

2+3+2로 들어올 때 소비량을 예측한다

실험의 “누적 소비 바이트”와 “이번 소비 바이트”를 함께 본다. 실제 DecodeResult::consumed_bytes는 이번 호출이 처리한 범위의 크기다. 실험의 누적 값은 여러 호출을 비교하기 위해 추가한 관찰값이다. 라이브러리가 전역 누적 카운터를 반환하는 것으로 읽지 않는다.

이번 도착다시 해석하는 범위이번 소비량이유
2바이트처음 2바이트04바이트 헤더가 없다.
3바이트이전 2 + 새 3 = 5바이트0전체 길이 7은 알지만 본문이 덜 왔다.
2바이트이전 5 + 새 2 = 7바이트7완전한 패킷이므로 콜백을 한 번 호출한다.

첫 콜백에서 두 바이트를 소비했다고 반환하면 다음 콜백에는 헤더의 뒷부분부터 남는다. 디코더가 잘못 읽는 것이 아니라 호출자가 경계를 버린 것이다. 반대로 정상 패킷 뒤의 불완전한 꼬리까지 소비하면 이후 패킷을 복구할 수 없다. 소비량은 “본 바이트”가 아니라 다시 볼 필요가 없어진 앞부분의 길이다.

반복문은 완전한 패킷만 앞에서부터 처리한다

Decode는 먼저 남은 길이가 헤더 네 바이트 이상인지 확인한다. 충분하면 data.subspan(result.consumed_bytes, kHeaderBytes)에서 전체 길이를 읽는다. 헤더 자체보다 작으면 오류를 반환하고, 최대값보다 크면 다른 오류를 반환한다. 길이는 정상인데 전체 패킷이 아직 안 왔다면 오류 없이 현재 결과를 반환한다.

패킷 전체가 있으면 handler(data.subspan(..., packet_size))를 호출한 뒤 소비량과 패킷 수를 증가시킨다. 다음 반복은 바로 뒤 바이트부터 시작한다. 따라서 두 완전한 패킷이 함께 들어오면 같은 Decode 호출에서 두 번 처리된다. 중간에 완전하지 않은 마지막 패킷을 만나면 앞에서 처리한 패킷만 소비한 결과를 돌려준다.

디코더에는 길이 한도 외의 수신 상태가 없다. 버퍼를 보유하지 않고 호출자가 준 span만 읽는다. 패킷 콜백의 반환값으로 반복을 중단하는 API도 아니다. 콜백이 예외를 던지면 이 템플릿 함수 안에서 자동 복구하지 않는다. 서버 브리지는 애플리케이션 콜백 예외를 별도 경로로 격리하므로, 독립적으로 디코더를 쓰는 코드도 자기 오류 정책을 정해야 한다.

길이 검증은 메시지의 업무 규칙을 대신하지 않는다. 길이가 맞아도 타입, 버전, 문자열 바이트 길이, 로그인 상태 등이 잘못될 수 있다. Echo는 받은 프레임을 그대로 되돌리지만 Chat은 8바이트 헤더와 메시지별 상태 검사를 추가한다.

꼬리는 디코더가 아니라 수신 저장소에 남는다

수신 완료를 반영한 링의 읽기 범위와 다음 수신의 빈 쓰기 범위는 겹치지 않는다. 워커는 빈 공간이 있으면 다음 수신을 선게시한 뒤 읽기 span으로 콜백을 실행한다. 콜백이 반환한 소비량만큼 읽기 위치를 옮기면 미완성 꼬리는 계속 미소비 영역으로 남는다. 다음 완료 때 그 꼬리와 새 바이트가 함께 읽힌다.

이 방식은 Decode 안에서 모든 조각을 새 vector에 다시 붙이는 것과 다르다. 수신 링이 이미 조각의 수명을 관리한다. 콜백 안에서 별도 누적 버퍼를 만든다면 어느 쪽을 소비했고 어느 쪽이 보관하는지 중복 관리하지 않아야 한다. 게임 큐로 넘기는 Chat의 경우에는 큐가 raw chunk를 복사하고, 게임 워커의 Player 입력 버퍼가 그 복사본을 프레이밍한다. 그 구조에 Echo 디코더의 무상태 동작을 그대로 섞어 설명하지 않는다.

span의 유효 기간은 콜백 반환까지다.

“꼬리를 남긴다”는 말은 그 span 포인터를 저장하라는 뜻이 아니다. 소비량으로 라이브러리의 읽기 위치를 조절한다는 뜻이다. 나중에 다른 워커에서 사용할 범위는 유효한 동안 소유하는 저장소로 복사한다.

길이 오류 앞에 정상 패킷이 있을 수도 있다

입력이 정상 길이 4의 프레임과 잘못된 길이 3의 헤더로 이루어졌다면 디코더는 먼저 정상 프레임 콜백을 한 번 호출한다. 다음 헤더에서 오류를 반환할 때 consumed_bytes는 4이고 packet_count는 1이다. 오류가 생겼다고 앞에서 호출한 핸들러의 부수 효과가 자동 취소되지 않는다.

EchoHandler는 이 오류를 보고 종료를 요청한 뒤 현재 span 전체 크기를 소비량으로 반환한다. 이미 앞 프레임의 Send가 접수되었더라도 연결 종료 때문에 상대가 그 응답을 모두 받을지는 별개다. 입력 묶음 전체를 하나의 원자적 거래로 처리하려면 프레이밍과 업무 검증, 응답 접수를 따로 설계해야 한다. 현재 디코더가 그런 거래를 제공한다고 가정하지 않는다.

정상 크기의 헤더 뒤 본문이 덜 온 경우는 오류와 구분한다. 네트워크의 자연스러운 분할일 수 있다. 이때 즉시 종료하는 구현은 정상 클라이언트도 끊을 수 있다. 다만 영원히 도착하지 않는 본문 때문에 연결을 무제한 점유하게 둘 필요는 없다. 게임 프로토콜의 읽기 기한이나 서버의 idle 정책을 별도로 정한다.

정상·경계·오류를 각각 재현한다

정상 사례에는 분할 수신과 병합 수신이 모두 필요하다. 경계에는 빈 본문과 정확한 최대 길이가 필요하다. 오류에는 헤더보다 작은 길이, 최대값보다 한 바이트 큰 길이, 정상 패킷 뒤의 잘못된 헤더가 필요하다. JS 실험 검사는 이 경우들의 예상 소비량을 확인한다. 실제 C++ 단위 테스트와 RIO 통합 테스트는 별도로 실행한다.

npm.cmd --prefix tools/book run test:models
bin\tests\x64\Debug\RIONetLite.UnitTests.exe --gtest_filter=PacketDecoderTest.*
bin\tests\x64\Release\RIONetLite.IntegrationTests.exe --gtest_filter=IntegrationSmokeTest.EchoesFragmentedAndCoalescedFrames:IntegrationSmokeTest.AcceptsMaximumFrameAndRejectsOneByteOverMaximum

단위 테스트의 한도가 32 또는 8이고 실험 한도가 16인 것은 서로 다른 작은 입력으로 같은 규칙을 확인하기 위해서다. 실제 서버 기본 한도인 16KiB와도 구분한다. 테스트 이름이 존재한다는 출처 검사만으로 이번 실행이 통과했다고 기록하지 않는다.

Echo의 LengthPrefixedDecoder는 big-endian u32 **header를 포함한 전체 길이**를 읽는다. ping 4바이트의 전체 길이는 8이다.

decoder는 자체 누적 버퍼가 없다. OnData의 미소비 바이트는 transport가 다음 callback에 다시 포함한다. 애플리케이션이 또 누적하면 중복 처리된다. adapter는 raw 바이트를 모두 복사·소비하므로 게임 워커가 자기 누적 버퍼에서 framing한다. 두 누적 위치를 혼동하지 않는다.

길이 0~3은 kInvalidLength, maximum 초과는 kMessageTooLarge, 범위 안의 미완성은 정상 대기다. 오류 시 RequestClose(session, kProtocolError)를 요청한다. span보다 많은 소비량을 반환하면 연결이 닫힌다. decoder handler 예외는 전파되므로 네트워크 callback 경계에서 해당 세션을 닫는다.

Send(session, header, payload)는 두 span을 하나로 수락하고 복사한다. 전체 크기는 max_message_bytes 이하이어야 한다. header·byte order·version은 애플리케이션이 만든다. C#은 BinaryPrimitives의 BigEndian 함수를 사용한다. Chat 명세의 fixture로 양쪽을 확인한다. LoadClient의 split/coalesce 시나리오로 실제 TCP를 검사한다.

TCP는 메시지 경계를 보존하지 않는다

TCP는 순서가 있는 바이트 스트림이다. 송신자가 8바이트씩 두 번 Send해도 수신 callback은 3바이트, 13바이트로 나눠 받을 수 있다. 반대로 여러 메시지가 한 번에 합쳐질 수 있다. 한 번의 수신을 한 패킷으로 간주하면 정상 네트워크에서도 해석이 틀어진다.

애플리케이션은 길이 prefix나 구분자처럼 자체 경계를 정해야 한다. LengthPrefixedDecoder는 앞 4바이트를 big-endian 총 패킷 길이로 읽는다. 이 길이에는 prefix 자신도 포함된다. 길이가 4보다 작거나 설정 maximum보다 크면 오류로 반환한다.

불완전한 패킷은 오류가 아니다. prefix 네 바이트가 아직 없거나 전체 패킷 길이보다 현재 바이트가 적으면 Decode는 거기서 멈춘다. result.consumed_bytes는 앞에서 완성된 패킷만 포함한다. 미완성 꼬리를 지우면 다음 입력을 복원할 수 없다.

직접 decoder를 쓰는 callback은 처리한 앞부분의 크기를 반환해 transport가 나머지를 보관하도록 한다. adapter를 쓰면 raw chunk를 복사하고 전부 소비하므로 게임 워커가 별도 입력 벡터에 꼬리를 보관한다. 두 방식을 섞어 서로가 남은 바이트를 보관한다고 가정하지 않는다.

TCP는 메시지 경계를 보존하지 않는다: 적용한다

총 길이 12인 패킷과 총 길이 8인 패킷을 연속으로 보냈다. 첫 수신에 15바이트가 오면 앞의 12바이트만 처리되고 뒤의 3바이트는 다음 prefix의 일부다. 다음 입력 5바이트와 이어 붙이면 두 번째 패킷이 완성된다.

실습에서는 모든 byte 분할 위치를 검사한다. send 호출 횟수가 아닌 decoded packet 수와 정확한 payload를 비교한다. 합쳐진 16KiB heartbeat도 정상 입력인 이유는 이 경계 규칙 때문이다.

실습에서 관찰할 값

  • 1바이트씩 넣어도 같은 패킷이 나오는지 확인한다.
  • 여러 패킷을 합쳐 넣어 packet_count를 확인한다.
  • 잘못된 총 길이 0, 3, maximum+1을 거절한다.

생각하고 확인한다

패킷이 덜 왔을 때 data.size()를 반환하면 왜 잘못되는가.

해설 펼치기

반환값은 받은 크기 보고가 아니라 소비한 크기다. 미완성 prefix와 payload를 소비했다고 반환하면 transport가 그 바이트를 지운다. 다음 수신만으로 원래 패킷을 재구성할 수 없다.

슬라이더는 TCP로 앞에서부터 도착한 byte 수를 바꾼다. 두 frame은 각각 총 길이 8이며 앞 네 byte가 길이, 뒤 네 byte가 payload다. 색이 없는 칸은 아직 도착하지 않았다. 초록 칸은 이번 입력에서 완성 packet으로 소비할 수 있는 앞부분이다.

네트워크 callback의 경계는 이 slider의 위치와 관계없이 바뀔 수 있다. decoder가 prefix를 읽을 만큼의 byte를 받았어도 전체 길이가 없으면 소비하지 않는다. 이 모형은 라이브러리를 실제 실행하는 대신 동일한 길이 판정 규칙을 보여 준다.

길이 prefix decoder

include/rionetlite/packet_decoder.h

이 helper는 OS 자원 없이 byte span을 해석한다. 길이는 big-endian 4바이트이며 header 자체를 포함한다. Decoder는 입력을 소유하거나 미완성 꼬리를 내부에 저장하지 않는다.

DecodeResult의 consumed_bytes와 packet_count는 완성된 앞부분의 결과다. 길이 오류와 덜 도착한 데이터는 다르다. handler가 받은 packet span도 호출 동안만 소유하지 않는 view다.

while 조건과 subspan 위치를 직접 계산하며 읽는다. 현재 data.size()-consumed 계산이 안전한 이유는 consumed가 완성 packet 길이 합으로 유지되기 때문이다. 변형 시 이 불변 조건을 보존한다.

  • OnData 소비량과 잔여 링을 연결한다.
  • Chat의 8바이트 헤더 parser와 구분한다.

독해 포인트

충분한 header가 있을 때만 길이를 읽는다. 길이<4와 maximum 초과는 error이며, 전체 packet이 덜 온 경우는 error 없이 소비된 앞부분만 반환한다.

handler 호출 뒤 consumed와 count를 증가시킨다. callback이 packet span을 오래 저장하지 않으며 이 helper는 Chat version/type을 검사하지 않는다.
