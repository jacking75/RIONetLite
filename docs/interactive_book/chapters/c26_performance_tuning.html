비용이 이동하는 곳을 확인하며 한 조건씩 바꾼다

대기 전략, batch, affinity와 할당기는 각각 다른 비용을 바꾼다. 안전 조건을 유지하면서 실제 workload의 처리량·P99·CPU·메모리를 함께 비교한다.

polling·adaptive·notification을 구분한다

전략현재 동작평가할 비용과 가설
polling빈 CQ에서도 YieldProcessor로 짧게 반복한다.완료 반응과 idle CPU의 교환이다. 항상 빠르다고 보장하지 않는다.
adaptive정한 empty polling 예산 뒤 notification 대기로 간다.bursty 입력과 idle의 절충이며 spin 값은 실제 분포로 고른다.
notificationRIONotify와 이벤트 기반 대기를 사용한다.idle 효율과 wakeup·스케줄링 비용을 본다.

WaitForWork는 Notify가 ERROR_SUCCESS 또는 WSAEALREADY이면 armed 상태로 본다. 이벤트 대기 상한은 50ms이며 close 같은 비RIO 제어 작업도 다시 처리할 기회를 준다. 이 값이 모든 패킷에 고정 50ms 지연을 추가한다는 뜻은 아니다. 이벤트는 완료나 종료 wakeup으로 먼저 깨울 수 있다.

실제 notification 자원이 없거나 Notify가 실패한 경로도 확인한다. 공개 enum 외 cast가 Validate를 통과할 수 있다는 C21의 한계 때문에 임의 숫자를 대기 전략으로 사용하지 않는다. 처음에는 기본 adaptive 128을 기준으로 삼고 workload를 고정해 비교한다.

batch와 링 용량은 서로 다른 상한이다

completion_batch_size는 한 번에 CQ에서 꺼내는 결과 배열 크기다. 더 큰 값은 호출 수를 줄일 수 있지만 한 회차의 처리량과 제어 작업의 반응을 바꾼다. 32·64·128·256 같은 후보를 같은 입력으로 비교한다. 세션당 송신 링 용량이나 미완료 송신 수를 이 값으로 늘리는 것은 아니다.

send_buffer_bytes를 늘리면 burst 수락량은 늘지만 느린 peer에서 큐 대기와 메모리도 늘 수 있다. 큐에 들어갔다는 성공률만 보고 개선으로 판정하지 않는다. 지속 유입이 처리량보다 큰 조건은 L16처럼 다시 포화된다. 동작 한도를 무한 큐로 바꾸어 처리량 수치만 숨기지 않는다.

토폴로지를 확인한 뒤 affinity를 선택한다

enable_thread_affinity는 기본 false다. 현재 보조 함수는 processor group 좌표를 유지하면서 NUMA node의 항목을 교차로 배치한다. group 번호와 그 group 안의 processor 번호를 잃지 않아야 한다. 64개 미만의 단순한 연속 CPU 번호 가정으로 모든 시스템을 처리하지 않는다.

affinity는 앱·클라이언트·OS 작업과 CPU를 나누는 방식도 바꾼다. 컨텍스트 스위치가 줄어도 P99나 처리량이 반드시 좋아지는 것은 아니다. NUMA 메모리 접근, 같은 PC의 부하 클라이언트와 전원·스케줄링 조건을 기록한다. 코드의 토폴로지 정렬 테스트와 실제 장비 성능 승인은 별개다.

mimalloc과 RIO 등록 메모리를 구분한다

mimalloc은 vcpkg manifest로 복원하고 최종 실행 파일이 선택적으로 링크한다. UseMimalloc 옵션과 tools/test-mimalloc.ps1은 off/on 구성을 비교하는 도구다. RIO의 주소 매핑·등록 소유권을 allocator가 자동으로 해결해 주는 것은 아니다.

정상 hot path에서 불필요한 동적 할당을 줄이는 것은 유용하지만 모든 게임·로그 코드가 allocation-free라는 주장은 별도 증거가 필요하다. 예제의 Player 입력 vector·문자열과 로거, 초기화의 사전 확보를 구분한다. Debug allocation hook 검사는 지정된 core 경로를 검사하며 Release에서는 적용 범위가 달라 skip될 수 있다.

등록 전략과 준비 비용은 미시 측정으로 비교한다

run-design-benchmark.ps1은 세션별 버퍼 등록과 단일 arena 등록의 초기화 비용, 여러 descriptor 준비와 작은 바이트를 연속 영역으로 복사하는 준비 비용을 비교한다. 컴파일러가 작업을 제거하지 못하도록 결과 메모리를 외부의 volatile 간접 호출에 노출한다. 같은 도구 체인과 입력에서 반복 중앙값을 기록한다.

이 결과는 실제 네트워크 처리량 비교가 아니다. arena는 등록 수를 줄일 수 있지만 전체 arena의 수명과 slot별 범위·동시성·부분 회수 설계가 필요하다. 현재 라이브러리를 단일 arena 설계로 바꾸어 놓은 것처럼 설명하지 않는다. descriptor를 여러 개 준비하는 비용과 커널까지 zero-copy로 보내는 계약도 다른 질문이다.

과거 장비의 표를 현재 승인으로 바꾸지 않는다

기존 자료에는 i7-12700KF·20 logical processor 조건의 측정표와 당시 설정이 있다. A04에 날짜·커밋·환경·반복·한계와 함께 보존했다. 현재 독자의 CPU명으로 바꾸거나 원자료가 없는 표에 새로운 정확도를 부여하지 않는다. 이전 코드·관측 설정·컴파일러가 다르면 숫자 차이의 원인을 하나로 단정할 수 없다.

변경은 먼저 오류 0과 안전 조건을 유지해야 한다. 그 다음 하나의 옵션을 바꾸어 같은 질문을 측정한다. 실패·skip·측정 불가를 숨기지 않고, 분명한 장비별 이득이 확인된 설정만 그 환경에 적용한다.

polling과 notification을 비교한다

WorkerWaitMode는 polling, adaptive, notification 세 전략을 제공한다. polling은 empty CQ에서도 짧게 spin하고 notification은 이벤트를 기다린다. adaptive는 일정한 empty poll 후 notification으로 넘어가 CPU 사용과 지연의 타협을 시도한다.

adaptive_spin_count는 시간을 직접 지정하는 값이 아니라 빈 poll의 횟수다. CPU와 provider, 다른 작업 부하에 따라 같은 횟수의 시간이 다르다. “128이면 몇 마이크로초” 같은 고정 변환을 적용하지 않는다.

notification은 CQ notify를 arm하고 이벤트를 기다린다. 제어 mailbox나 idle sweep은 RIO 완료 없이도 처리해야 하므로 wait를 50ms로 제한한다. pure I/O 알림만 기다리면 close command가 늦게 처리되거나 종료가 멈출 수 있다.

affinity는 processor group과 NUMA 정보를 고려해 worker를 배치할 수 있지만 기본적으로 꺼져 있다. topology 정보가 없으면 fallback 순서를 사용한다. worker 수와 affinity를 늘리는 것으로 항상 throughput이 증가한다고 보장하지 않고 같은 조건에서 측정한다.

polling과 notification을 비교한다: 적용한다

동일한 정확성 workload를 세 모드에 각각 실행한다. 정상 데이터뿐 아니라 keepalive 설정, idle close와 shutdown도 확인한다. notification 이벤트가 Stop 후 해제되는지 handle 수와 반복 create-stop 테스트를 연결한다.

대기 전략 비교는 활성 연결 수, payload, metrics, affinity와 CPU 환경을 고정한다. CPU 사용이 줄어도 p99 응답이 늘 수 있으므로 하나의 숫자로 우열을 확정하지 않는다.

실습에서 관찰할 값

  • idle와 active CPU를 각각 측정한다.
  • close mailbox가 no-I/O 상태에서도 처리되는지 본다.
  • 세 모드의 실제 RIO 종료를 확인한다.

생각하고 확인한다

notification이면 worker가 영원히 기다려도 되는가.

해설 펼치기

아니다. RIO 완료 외에 close command, idle timeout과 shutdown 같은 제어 작업이 존재한다. 현재 구현은 bounded wait와 Stop의 wake를 사용해 이 작업들을 진행한다.

NUMA node별 배치 순서

src/detail/processor_topology.h

ProcessorLocation은 group, processor number와 NUMA node를 표현한다. affinity target을 만들기 전에 helper로 processor 순서를 정한다.

OrderProcessorsForAffinity는 서로 다른 node를 찾고 각 node의 같은 ordinal processor를 번갈아 배치한다. 이를 통해 첫 worker들이 한 node에만 집중되는 순서를 피하려는 구조다.

실제 NUMA query와 thread affinity 적용은 I/O worker에 있다. 이 helper의 정렬 성공은 affinity 적용 성공이나 성능 개선의 측정 증거가 아니다.

이 파일에서 추적할 연결

  • I/O worker의 PrepareAffinityTargets를 읽는다.
  • topology가 없을 때 fallback을 확인한다.
  • 설정 기본 affinity=false를 확인한다.
