RIONetLite 전체를 한 장에 놓고 본다

지도에서의 위치는 이 장의 쉽게 말하면 상자에서 설명한다.

세부 장으로 들어가기 전에 라이브러리의 바깥 모양(공개 API), 안쪽 부품, 연결 하나가 지나가는 길을 한 번에 훑는다. 이 장의 그림이 이후 모든 장의 지도 역할을 한다.

입문이 장을 읽고 나면

RIONetLite를 쓰는 프로그램의 골격을 직접 적을 수 있고, “연결 → 수신 → 송신 → 종료 → 정지”의 각 장면에서 라이브러리의 어느 부품이 일하는지 말할 수 있다. 각 장면 옆의 장 번호가 이후 세부 설명으로 가는 입구다.

라이브러리가 맡는 일과 내가 맡는 일

RIONetLite는 Windows RIO로 TCP 서버를 만드는 C++ 정적 라이브러리다. 소켓, RIO 요청, 등록 메모리, 워커 스레드처럼 실수하기 쉬운 부분은 라이브러리가 맡는다. 애플리케이션은 “연결됐다·데이터가 왔다·끊겼다”는 세 가지 알림을 받아 게임 규칙을 처리하고, 보낼 바이트가 있으면 Send를 부른다.

라이브러리가 하는 일애플리케이션이 하는 일
포트를 열고 접속을 받는다.포트 번호, 최대 접속 수, 버퍼 크기 같은 설정을 정한다.
세션 슬롯과 세션별 수신·송신 버퍼를 시작할 때 미리 준비한다.받은 바이트에서 메시지 경계를 찾는다. 길이 헤더 형식은 앱이 정한다.
RIO 수신·송신 요청을 게시하고 완료를 처리한다.메시지를 해석해 게임 상태를 바꾸고 응답을 만든다.
Send로 받은 바이트를 내부 송신 버퍼에 복사해 순서대로 보낸다.Send가 거절됐을 때 다시 보낼지, 연결을 끊을지 정한다.
연결 종료와 서버 정지 때 진행 중인 요청을 안전하게 정리한다.DB·파일처럼 오래 걸리는 일을 별도 스레드로 넘긴다.

현재 0.3.x는 Windows x64의 TCP/IPv4 서버만 다루는 preview다. TLS 암호화, 계정 인증, 데이터베이스, UDP, IPv6, 클라이언트용 API는 들어 있지 않다. 이 기능들은 애플리케이션이나 다른 라이브러리가 맡는다.

기억할 공개 API는 세 가지다

애플리케이션이 포함하는 헤더는 저장소의 include/rionetlite/에 있다. 처음에는 다음 세 가지만 알면 서버를 만들 수 있다.

이름헤더역할주로 쓰는 것
ServerConfigconfig.h서버를 만들기 전에 채우는 설정 구조체port, io_worker_count, max_sessions, max_message_bytes
EventHandlerevent_handler.h내가 상속해 구현하는 “알림 받는 쪽”OnConnected, OnData, OnClosed
Serverserver.h서버 본체Create → Start → Send·RequestClose → Stop

세 가지를 조합한 가장 작은 골격은 다음과 같다. 오류 출력과 종료 신호 처리는 줄였다. 완전한 예제는 P03의 EchoServer다.

// 공개 API의 모양을 보여 주는 최소 골격이다. 오류 출력은 줄였다.
#include "rionetlite/server.h"

class MyHandler final : public rionetlite::EventHandler {
 public:
  void OnConnected(rionetlite::SessionId session) override {
    // 새 플레이어가 들어왔다.
  }
  std::size_t OnData(rionetlite::SessionId session,
                     std::span<const std::byte> data) override {
    // data 안에서 완성된 메시지를 찾아 처리하고,
    // 처리가 끝난 앞부분의 바이트 수를 돌려준다.
    return 0;
  }
  void OnClosed(rionetlite::SessionId session,
                rionetlite::CloseReason reason) override {
    // 플레이어를 정리한다.
  }
};

int main() {
  rionetlite::ServerConfig config;
  config.port = 32452;
  MyHandler handler;  // 서버보다 오래 살아야 한다.
  auto server = rionetlite::Server::Create(config, handler);  // 설정 검사, 자원 준비
  if (!server) return 1;
  if (!server->Start()) return 1;  // accept 스레드와 I/O 워커 시작
  // ... 종료 신호를 기다린다 ...
  return server->Stop(rionetlite::StopMode::kGraceful) ? 0 : 1;  // 정리하고 멈춘다
}

처음 쓰는 사람이 가장 많이 틀리는 규칙 네 가지를 먼저 적어 둔다. 모두 뒤의 장에서 이유를 자세히 설명한다.

  1. OnData의 data는 콜백이 끝나면 사라진다. 나중에 쓰려면 복사한다. 주소만 저장하면 다른 데이터로 덮인 메모리를 읽게 된다. (C03)
  2. OnData는 처리한 바이트 수를 돌려준다. 메시지가 아직 덜 왔으면 0을 돌려주면 된다. 남은 바이트는 다음 수신 때 새 데이터와 붙어서 다시 온다. (C13)
  3. 세션은 SessionId 전체로 가리킨다. 슬롯 번호만 저장하면 끊긴 플레이어에게 보낼 응답이 같은 슬롯을 받은 새 플레이어에게 갈 수 있다. (C11)
  4. 콜백 안에서 오래 걸리는 일을 하지 않는다. 콜백을 부른 I/O 워커가 멈추면 그 워커가 맡은 다른 세션도 모두 기다린다. (C18)

공개 API 아래에는 다음 부품들이 있다. 이름을 외우기보다 “누가 무엇을 소유하고, 누가 무엇을 부르는가”를 본다.

부품하는 일자세히
① 공개 Server서버의 상태(Initialized·Running·Stopped 등)를 관리하고, Send 인자를 검사하고, 내부에서 올라온 이벤트를 EventHandler로 전달한다. 콜백에서 던진 예외도 여기서 막는다. 소스는 src/server.cpp다.C03, C06
② accept 스레드새 연결을 받고, 빈 세션 슬롯을 빌려 주고, OnConnected를 부르고, 첫 수신 요청을 게시한다. 빈 슬롯이 없으면 연결을 거절한다.C10
③ 세션 풀과 세션서버를 만들 때 max_sessions개의 세션을 미리 만든다. 연결이 오면 하나를 빌려 주고, 끊기면 진행 중인 요청이 모두 끝난 뒤 돌려받아 다음 연결에 쓴다. 연결 중에 큰 메모리를 새로 할당하지 않는다.C10, C11
④ 수신 링·송신 링세션마다 있는 원형 버퍼다. 등록 버퍼로 만들기 때문에 커널이 직접 읽고 쓴다. 같은 메모리를 가상 주소에 두 번 이어 붙이는 “이중 매핑”으로, 끝에서 처음으로 넘어가는 데이터도 한 덩어리처럼 다룬다.C08, C09
⑤ I/O 워커io_worker_count개의 스레드다. 워커마다 CQ 하나와 담당 세션 묶음이 있다. 완료를 꺼내 수신 데이터를 OnData로 넘기고, 송신 완료를 정리하고, 연결 종료를 마무리한다.C07, C12

내부 구현은 저장소의 RIONetLite/impl/에 있다. 예제와 애플리케이션은 이 내부 헤더를 직접 포함하지 않고 공개 헤더만 사용한다.

연결 하나의 일생을 여섯 장면으로 본다

그림으로 보기 · 연결 하나의 여섯 장면에서 먼저 상태를 바꾸어 본다. 아래 코드와 표는 이 그림의 조건을 세부로 읽는다.

서버가 켜지고, 플레이어가 접속해 데이터를 주고받다가 나가고, 서버가 꺼지는 과정을 여섯 장면으로 나누었다. 3부와 4부의 장들은 이 장면 하나하나를 확대해서 보는 것이다.

  1. ① 서버 준비

    Create가 설정 범위를 검사하고 세션 풀과 등록 버퍼를 미리 준비한다. Start가 워커별 CQ를 만들고 accept 스레드와 I/O 워커를 띄운다. 이 순간부터 콜백이 불릴 수 있다.

    C03 공개 API · C21 설정

  2. ② 연결

    accept 스레드가 접속을 받아 빈 슬롯을 빌리고, 그 세션을 맡을 I/O 워커를 정한다. RQ를 만들고 OnConnected를 부른 뒤 첫 수신 요청을 게시한다. 이 세션의 담당 워커는 연결이 끝날 때까지 바뀌지 않는다.

    C10 연결 수락 · C11 세션 식별

  3. ③ 수신

    커널이 수신 링의 빈 칸에 바이트를 쓰고 CQ에 완료를 남긴다. 담당 워커가 완료를 꺼내 링에 반영하고, 다음 수신을 먼저 게시한 뒤 OnData를 부른다. 앱이 돌려준 소비량만큼 링의 읽기 위치가 움직인다.

    C12 수신 경로 · C13 패킷 경계

  4. ④ 송신

    Send는 바이트를 세션의 송신 링에 복사하고 곧바로 kQueued를 돌려준다. 진행 중인 송신이 없으면 RIO 송신을 게시하고, 있으면 링에 쌓아 두었다가 완료 때 한꺼번에 보낸다. 일부만 보내졌으면 나머지를 다시 게시한다. 링이 가득 차면 kWouldBlock이다.

    C14 송신 · C15 부분 송신

  5. ⑤ 연결 종료

    상대가 연결을 끊거나(0바이트 수신), 앱이 RequestClose를 부르거나, 오류가 나면 종료가 시작된다. 소켓을 닫고 OnClosed를 한 번 부른다. 아직 끝나지 않은 요청이 있으면 슬롯을 격리해 두었다가 모두 끝난 뒤 재사용한다.

    C16 연결 종료

  6. ⑥ 서버 정지

    Stop은 새 연결과 새 요청을 막고, graceful 모드라면 이미 맡은 송신에 끝낼 기회를 준다. 남은 완료를 처리한 뒤 워커를 멈추고 자원을 해제한다. 게임 로직 큐는 앱이 따로 비운다.

    C17 서버 종료 · C18 게임 로직 큐

누가 어떤 스레드에서 일하는가

콜백이 어느 스레드에서 불리는지 알아야 공유 데이터를 안전하게 다룰 수 있다.

스레드개수하는 일이 스레드에서 불리는 콜백
주 스레드1Create·Start·Stop을 부르고 종료 신호를 기다린다.없음
accept 스레드1접속 수락과 세션 배정OnConnected
I/O 워커io_worker_count담당 세션의 수신·송신 완료와 종료 처리OnData, OnClosed
게임 로직 워커(선택)앱이 정한다큐에서 이벤트를 꺼내 게임 처리. 여기서도 Send를 부를 수 있다.없음. 라이브러리가 아니라 앱이 만든 스레드다.

한 세션의 OnData는 언제나 그 세션의 담당 워커가 순서대로 부른다. 그러나 다른 세션의 콜백은 다른 워커에서 동시에 실행될 수 있다. 여러 세션이 함께 쓰는 자료구조에는 잠금 같은 보호가 필요하다.

그래서 예제 두 개는 콜백 이후의 길이 다르다. EchoServer는 처리가 아주 짧아서 OnData 안에서 바로 응답한다. ChatServer는 QueuedEventAdapter로 받은 바이트를 복사해 게임 로직 워커에 넘기고, 로그인·룸 같은 게임 상태는 그 워커가 소유한다.
