RQ·CQ·등록 ID·컨텍스트가 맡는 일

그림으로 보기 · RQ·CQ·등록 구간·요청 컨텍스트에서 먼저 상태를 바꾸어 본다. 아래 코드와 표는 이 그림의 조건을 세부로 읽는다.

요청 큐 RQ는 한 소켓의 수신·송신 요청을 받는 연결점이다. 완료 큐 CQ는 요청 결과를 모으며 이 구현에서는 세션의 소유 I/O 워커가 자기 CQ를 처리한다. 등록 버퍼 ID는 커널에 등록한 메모리 범위를 식별한다. 요청에 들어가는 RIO_BUF는 그 ID와 Offset·Length로 구간을 지정한다.

완료 결과에는 RequestContext가 돌아온다. 이 저장소의 RioIoContext는 RIO_BUF를 기반으로 세션 index, 세대, I/O 방향, 소유 워커와 요청 번호를 함께 기록한다. 단순히 “어떤 소켓이 준비됐다”가 아니라 “이전 어떤 요청의 결과인가”를 판별하는 데 사용한다. 현재 연결로 슬롯이 재사용되었는지도 이 정보로 확인한다.

게시 성공은 완료 이벤트와 다르다

먼저 예측해 보기 · RIO 게시가 실패했다. outstanding은 어떻게 되는가?

게시 전에 늘린 참조를 롤백한다 — 실패한 요청은 완료를 만들지 않는다. L02에서 확인한다.

게시 전에 컨텍스트와 참조 카운트를 준비한다. 호출이 성공하면 나중의 완료까지 메모리를 유지한다. 호출이 실패하면 방금 준비한 참조를 롤백한다. 실패한 게시에도 완료가 올 것이라고 기다리면 카운터가 끝나지 않아 종료가 막힐 수 있다. 반대로 성공 반환을 완료라고 처리하면 커널이 쓰는 메모리를 먼저 해제할 수 있다.

이 수명 규칙은 수신과 송신에서 공통이다. 그러나 0바이트 결과의 의미는 같지 않다. 수신에서는 원격의 정상 종료를 관찰하는 경로이고 송신에서는 실패 처리로 이어진다. 방향을 잃은 공통 completion 함수 하나로 의미까지 같다고 취급하지 않는다.

함수 표를 얻지 못하면 시작하지 않는다

WindowsRioApi::Initialize는 RIO 확장 함수 표를 WSAIoctl로 요청한다. 테이블은 초기화 전에 비우며 호출 성공 여부를 반환한다. 이후 CreateCompletionQueue, RegisterBuffer, Receive와 Send는 이 표의 함수를 호출한다. 실패한 초기화를 무시하고 비어 있는 함수 포인터를 호출하지 않는다.

미지원 환경에서 일반 Winsock transport로 조용히 전환하는 fallback은 없다. 공개 생성 오류의 code와 native_code를 남기고 OS·provider·빌드 플랫폼을 확인한다. “Windows이므로 RIO가 무조건 된다”는 가정을 설정 검증으로 대신하지 않는다.

요청 수가 CQ 예산에 연결된다

현재 세션은 수신 한 개와 송신 한 개의 미완료 요청을 유지하도록 설계되었다. ValidateServerConfig는 가장 많은 세션을 맡는 워커의 수를 올림 나눗셈으로 계산하고 두 배를 CQ 용량으로 사용한다. 총 세션 수가 워커 수로 나누어떨어지지 않아도 나머지를 버리지 않는다.

애플리케이션 Send 호출을 많이 했다고 같은 수의 요청이 CQ에 쌓이는 것은 아니다. 이미 송신이 진행 중이면 새 데이터가 링에 대기한다. 메모리 예산, 게시 횟수와 앱 메시지 수를 각각 관찰해야 한다. 버퍼 용량이 큰 것과 미완료 요청이 많은 것도 다른 조건이다.

비동기 요청과 완료를 구분한다

동기 호출은 함수가 끝났을 때 작업 결과를 다룬다. 비동기 I/O는 요청이 수락된 뒤 실제 작업이 나중에 끝난다. RIOSend가 true라는 것은 요청 게시가 성공했다는 뜻이다. 상대 프로그램이 메시지를 처리했다거나 송신 완료 결과가 성공했다는 뜻은 아니다.

RIO_BUF는 등록한 BufferId, Offset, Length로 작업 구간을 지정한다. 커널은 게시된 구간을 참조하므로 해당 메모리를 이동하거나 등록 해제하지 않는다. 요청 context도 완료 결과의 RequestContext로 되돌아오므로 완료 전에 같은 context를 덮어쓰면 식별 정보가 바뀐다.

RioIoContext는 세션 인덱스, generation, owner worker와 request number를 담는다. BeginRequest는 기존 Length가 남아 있는지와 구간 범위를 확인한다. 길이 검사에서 offset+length 대신 length > registered_size-offset을 사용하면 정수 덧셈 overflow를 피한다.

요청 실패와 완료 실패는 모두 outstanding를 되돌려야 하지만 실행 시점이 다르다. 게시 실패는 CQ 결과가 안 올 수 있어 그 자리에서 정리한다. 게시가 성공했다면 정상·오류·취소 결과를 소유 워커가 꺼내 수명 카운트를 정리한다.

비동기 요청과 완료를 구분한다: 적용한다

수신 4096바이트를 게시했지만 완료 결과는 37바이트일 수 있다. 게시된 상한보다 작다는 이유로 오류가 되는 것이 아니다. 반대로 4097바이트 완료는 context가 허용한 구간 밖이므로 원문에서 방어 검사를 해야 한다.

송신은 전송된 앞부분만 읽기 위치를 옮기고 남은 부분을 다시 게시한다. 수신과 송신에서 길이 의미가 다르므로 같은 Complete 함수를 무조건 공유하지 않는다. 실제 원문에서 CompleteReceive와 CompleteSend의 상태 전이를 비교한다.

실습에서 관찰할 값

  • context와 등록 메모리의 주소가 유지되는지 본다.
  • 게시 실패와 완료 실패에서 count가 한 번만 줄어드는지 본다.
  • 세션 generation과 owner가 결과 처리 전에 검증되는지 본다.

생각하고 확인한다

Send가 kQueued를 반환했는데 실제 송신 실패가 가능한가.

해설 펼치기

가능하다. 공개 Send는 바이트를 라이브러리 링에 수락했다는 뜻이다. 이후 RIO 게시나 완료에서 실패할 수 있고 네트워크가 끊길 수도 있다. 게임 의미의 전달 확인이 필요하면 요청 번호와 애플리케이션 응답을 별도로 설계한다.

RIONetLite/impl/fast_spin_lock.h

sender와 session pool이 이 lock을 쓰지만 모든 server 객체가 같은 lock을 공유하는 것은 아니다. 잠금 범위와 서로 다른 mutex의 획득 순서를 caller 코드에서 확인한다.

  • sender의 syscall lock 밖 실행을 읽는다.
  • pool ForcedClose의 검증/전이 범위를 본다.
  • 같은 lock의 재귀 획득 경로가 없는지 확인한다.
