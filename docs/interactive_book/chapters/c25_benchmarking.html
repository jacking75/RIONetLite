6부 · C25

오류 없는 같은 조건의 반복을 비교한다

지도에서의 위치는 이 장의 쉽게 말하면 상자에서 설명한다.

처리량 숫자 하나보다 workload, 단위, 오류·반복·환경과 종료 조건이 먼저다.

심화큰 그림에서의 위치: P02 운영과 문제 해결

쉽게 말하면 처리량을 잴 때 같은 조건에서 반복하고, 오류가 난 실행은 빼고, 평균 하나 대신 중앙값과 꼬리 지연(P99)을 함께 보는 방법이다.

처음 읽는다면 무엇을 비교할지 한 문장으로 정한다 절만 읽어도 잘못된 측정을 피할 수 있다.

무엇을 비교할지 한 문장으로 정한다

“빠른가” 대신 “같은 장비·연결 수·payload에서 대기 전략을 바꾸면 처리량과 P99, CPU가 어떻게 달라지는가”처럼 질문을 좁힌다. 서버와 부하 클라이언트를 같은 PC에 두면 CPU와 메모리 대역폭을 공유하므로 서버만의 최대 용량과 같지 않다. 개발 PC에서 짧게 확인한 결과를 운영 부하 승인으로 확대하지 않는다.

워밍업, 실제 측정과 종료·drain을 나눈다. 최초 RIO 자원·캐시·할당 경로가 준비되는 시간을 측정 구간과 섞으면 반복마다 다른 시작점을 비교할 수 있다. 자원 누수를 볼 때도 같은 quiescent 상태에서 비교한다. 측정 중 최고치와 종료 뒤 안정값은 다른 질문에 답한다.

suite와 matrix는 서로 다른 질문에 쓴다

# 별도로 지정한 측정 환경에서 실행한다. 이번 책 집필에서는 실행하지 않았다.
tools\build.ps1 -Configuration Release -Rebuild
tools\run-benchmark.ps1 -Profile suite -Runs 5 -DurationSeconds 10 -Connections 32
tools\run-benchmark.ps1 -Profile matrix -Runs 5 -DurationSeconds 5 -Connections 32 -WaitModes polling,adaptive,notification -BatchSizes 64 -ObservabilityModes off -AffinityModes off

suite는 latency 32/128B, throughput 1/4/16KiB, fan-in, burst, slow consumer와 churn을 분리한다. 실제 payload 인자는 프로토콜 overhead를 고려해 case에서 정하므로 case 이름만으로 앱 본문 바이트 수를 단정하지 않는다. matrix는 wait mode·batch·observability·affinity 조합을 바꾸며 동일 case를 비교한다.

기본 워밍업은 1초이며 측정 시간과 별개다. 정상 응답 시나리오는 종료 뒤 진행 중 왕복을 추가로 drain해 경계에서 사라진 응답을 성공으로 숨기지 않는다. correctness 오류, 클라이언트 timeout, 비정상 exit와 강제 종료를 제외한 정상 반복만 성능 비교에 사용한다.

raw JSON과 집계 표의 의미를 분리한다

기본 결과 경로는 artifacts/benchmarks의 날짜·커밋별 디렉터리다. raw JSON은 실행별 correctness와 부하 클라이언트의 통계를 보존한다. summary.csv는 각 실행의 처리량·P50/P99·CPU·자원·컨텍스트 스위치 값을 기록하고 aggregate.csv는 같은 case·wait·batch·observability·affinity를 묶는다. 환경 JSON도 함께 보존한다.

하네스의 P99 단위는 microseconds이며 집계는 실행별 P99의 정렬 중앙 위치 값을 사용한다. 모든 실행의 raw 지연을 합친 뒤 계산한 P99와 같지 않다. 현재 인덱스는 floor((Runs-1)/2)이므로 짝수 Runs에서는 두 중앙값의 평균이 아니라 아래쪽 중앙 위치를 고른다. 기본 5회 반복을 바꾸면 통계 방법을 함께 기록한다.

Thread(EchoServer*)의 Context Switches/sec를 1초 간격으로 표본화해 평균·최댓값·표본 수를 남긴다. 짧은 실행의 표본 부족을 숨기지 않는다. CaptureEtw는 별도 WPR trace를 추가하는 옵션이며 권한·시스템 정책과 trace 크기를 고려한다. 과거 0xc5585011 거부 기록은 A04의 당시 환경 기록이며 현재 장비의 실행 결과가 아니다.

가상 자료로 제외·중앙값·P99를 연습한다

실행 0·2·3은 같은 환경 A의 오류 0 자료이며 처리량은 1000·1100·900 requests/s다. 중앙값은 1000이다. 실행 1은 오류가 있어 제외하고 실행 4는 환경 B라 직접 우열 판정에 섞지 않는다. 이 숫자는 학습용으로 만든 것이며 RIONetLite의 실측 성능이 아니다.

모델의 지연은 각 실행 10개짜리 가상 raw 표본을 합쳐 nearest-rank P99를 계산한다. 30개를 합친 기본 결과에서 P99는 12ms이며 단위를 us로 바꾸면 12000us다. 표본이 적어 P99가 거의 최대값이 된다는 한계도 보인다. 모델의 일반 중앙값은 짝수 개일 때 두 중앙값의 평균이며 위 하네스의 집계 방식과 구분한다.

평균이나 P99만으로 오류가 없다는 사실을 증명할 수 없다. 같은 처리량에서도 tail latency, CPU와 큐 포화가 달라질 수 있다. 표본 수와 측정 기간, 최대 지연과 오류 조건을 같이 기록한다.

승인된 기준선과 비교한다

BaselineCsv를 지정하려면 그 디렉터리에 approval.json과 environment.json이 있어야 한다. 현재 하네스는 approved 상태, 장비 식별·CPU·논리 프로세서 수, profile·반복·측정·워밍업·정리 조건을 대조한다. 임의 CSV를 가져와 현재 성능의 승인 기준선으로 취급하지 않는다.

tools\run-benchmark.ps1 -Profile suite -Runs 5 -DurationSeconds 10 -Connections 32 -BaselineCsv C:\measurement\approved\aggregate.csv

기본 회귀 한도는 처리량 중앙값 5% 초과 하락 또는 P99 중앙값 10% 초과 증가다. regression.csv를 남기고 실패한다. 저장소가 제공하던 오래된 0.2.x 기준선은 제거되었고 현행 코드의 승인된 고정 장비 기준선은 제공하지 않는다. 새 기준선은 지정 환경에서 별도로 승인하고 원자료와 함께 보관한다.

짧은 측정의 범위를 넘겨 결론내리지 않는다

한 번의 개발 PC 측정은 회귀 후보를 찾는 데 쓸 수 있지만 대규모 동접, 긴 운영 시간이나 다양한 OS/provider의 인수를 대신하지 않는다. 긴 부하와 capacity 검사는 지정 환경에서 별도로 수행한다. 이번 책 집필에서는 그런 실행을 하지 않았고 과거 자료와 가상 모델만 제공한다.

원자료에는 commit과 source hash, 컴파일러·SDK·구성·옵션, 장비·OS·관측 설정, 시나리오·연결 수·바이트 단위·기간·반복 수·오류·정리 결과를 함께 남긴다. 결과 표를 복사하면서 이 문맥을 빼면 다른 질문의 숫자를 비교하게 된다.

warmup 뒤 같은 유휴 상태를 비교한다

처음 사용하는 Echo와 abrupt-close 경로는 worker별 provider 자원을 늦게 만들 수 있다. 최초 handle 증가만 보고 누수로 확정하거나 상한을 임의로 늘리는 것 모두 부적절하다. 반복 같은 경로에서 계속 증가하는지와 Stop에서 회수되는지를 확인한다.

현재 stress 도구는 echo, split, coalesce, half-close, slow-read, abrupt-close, invalid-length와 no-read를 모두 warmup한다. warmup 결과와 측정 결과를 분리한다. 측정에 필요한 시나리오 coverage를 warmup으로 채우지 않는다.

자원 추세는 각 시나리오 뒤 연결이 빠지고 owner가 완료를 정리한 quiescent 표본을 비교한다. 활성 socket이 많은 순간과 완전 유휴 순간의 handle 수를 섞으면 부하 차이를 leak처럼 보거나 leak를 감소처럼 숨길 수 있다.

판정은 correctness, 모든 시나리오 반복 coverage, 충분한 원시·유휴 표본, 자원 상한과 server 정상 exit를 함께 요구한다. 표본 부족, exit nonzero나 강제 종료는 실패다. 600초 결과는 그 기간의 안정성 증거이며 장기 운영 보증이 아니다.

성능 측정

기본값은 logical processor에서 한 코어의 애플리케이션 여유를 남긴 worker 수, batch 64, adaptive 128 spin이다. polling은 최고 부하에서 지연을 낮출 수 있지만 idle 코어를 소비하고, notification은 idle 효율이 좋으며, adaptive는 둘의 절충이다. affinity는 NUMA와 processor group을 측정한 뒤에만 켠다.

한 번에 worker, batch(32/64/128/256), wait mode, buffer, allocator 중 하나만 바꾸고 tools\run-benchmark.ps1 결과를 비교한다. correctness error가 0이 아닌 결과를 성능 개선으로 채택하면 안 된다. mimalloc은 최종 executable이 선택적으로 링크하며 RIO 등록 메모리 소유와 무관하다.

Release를 빌드한 뒤 tools\run-benchmark.ps1 -Profile suite -Runs 5 -DurationSeconds 10 -Connections 32를 실행한다. suite는 latency 32/128 B, throughput 1/4/16 KiB, fan-in, burst, slow consumer와 churn을 실행한다. matrix는 -WaitModes, -BatchSizes, -ObservabilityModes, -AffinityModes의 조합을 비교한다. 결과는 artifacts/benchmarks/<date>-<commit>/에 raw JSON, summary.csv, 중앙값·표준편차·서버 CPU·컨텍스트 스위치·자원 최고치를 담은 aggregate.csv, 환경 JSON과 요약으로 저장된다.

Latency(32/128 B), throughput(1/4/16 KiB), fan-in, burst, slow consumer, churn을 분리한다. worker wait mode, batch, affinity, mimalloc을 한 번에 하나만 변경한다. P99, packets/bytes, CPU와 resource 추세를 함께 보고 data/connection error가 있는 실행은 무효다. 큰 ETW/WPA trace는 Git에 넣지 않고 artifact 저장소에 보관한다.

LoadClient JSON의 data_errors, dropped_packets, timeouts가 모두 0인 결과만 사용한다. 정상 응답 시나리오는 측정 종료 뒤 최대 5초 동안 진행 중 왕복을 drain하므로 종료 경계의 미수신 패킷도 성공으로 숨기지 않는다.

고정 장비의 승인된 aggregate.csv를 기준선으로 보관한 뒤 -BaselineCsv <path>를 지정하면 같은 case/wait/batch/observability를 비교한다. 기준 디렉터리에는 approval.json과 environment.json이 함께 있어야 하며 현재 컴퓨터명, CPU, 논리 코어 수와 측정 조건이 모두 일치해야 실행된다. 저장소에 보관하던 0.2.x 기준선과 로컬 결과 디렉터리는 제거했다. 현재 승인된 기준선은 제공하지 않으며 새로운 기준선은 외부 artifact 저장소에서 별도로 관리한다. 기본 실패 조건은 처리량 중앙값 5% 초과 하락 또는 P99 중앙값 10% 초과 증가이며 regression.csv를 남긴다.

하네스는 각 측정 중 \Thread(EchoServer*)\Context Switches/sec를 1초마다 표본화한다. summary.csv에는 실행별 평균·최댓값·표본 수, aggregate.csv에는 중앙값을 기록하므로 관리자 권한이 없는 장비에서도 wait mode 비교가 가능하다. -CaptureEtw는 추가로 WPR CPU file-mode trace를 cpu-context-switches.etl로 저장하며, 스레드별 스케줄링 원인 분석용이다. WPR 시스템 성능 프로파일 정책이 허용된 관리자 환경이 필요하다. 2026-08-27 로컬 실행에서는 정책 오류 0xc5585011로 ETW trace 시작이 거부됐지만 성능 카운터 계측은 정상 동작했다.

tools\run-design-benchmark.ps1은 실제 RIO 함수 테이블로 세션별 버퍼 등록과 단일 arena 등록의 초기화 시간을 비교한다. 같은 실행에서 8개 RIO_BUF descriptor 준비와 8×128바이트를 1KiB 연속 영역으로 복사하는 준비 비용도 비교한다. 컴파일러가 준비 작업을 제거하지 못하도록 결과 메모리를 volatile 간접 호출에 노출하고, 5회 중앙값과 환경을 design.json 및 environment.json에 남긴다. 이는 초기화와 CPU 준비 비용의 미시 측정이며 네트워크 처리량 비교는 공식 suite가 담당한다.

tools\test-mimalloc.ps1은 allocator off/on의 기능과 Echo 부하를 비교한다. 설계 비교·allocator 비교 결과도 기본적으로 artifacts/benchmarks/에 생성한다. 과거 수치 표와 장비 기준선은 현행 코드의 승인 결과로 사용하지 않으며, 필요한 이력은 Git에서 확인한다.
