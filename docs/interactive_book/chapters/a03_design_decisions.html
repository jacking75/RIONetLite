결정

RIONetLite 1차 릴리스는 다음 환경을 지원한다.

- Windows x64 전용이다.

- Windows 10 1803 이상, Windows 11, Windows Server 2019 이상을 대상으로 한다.

- 상태: 승인

- 날짜: 2026-08-26

과거 원문 · docs/adr/0002-threading-and-callbacks.md · 결정

당시 문장·명령·수치는 현행 실행·승인을 뜻하지 않는다. 현재 설명은 이 장의 본문을 따른다. 출처 revision: a5f29df610bdbafe68a69e0698ca71260b4c1fa7 · 항목: lines-6-18

결정

- Server::Send, Server::RequestClose, Server::state는 여러 애플리케이션 스레드에서 호출할 수 있다.

- Start와 Stop은 내부 상태 전이로 직렬화한다. 여러 스레드의 중복 Stop은 안전하고 같은 종료 결과를 관찰해야 한다.

- 직접 EventHandler는 내부 네트워크 스레드에서 호출한다.

- OnConnected는 accept 경로에서 호출하고, 동일 세션의 OnData와 OnClosed는 그 세션의 소유 I/O worker에서 호출한다.

- 사용자는 callback에서 게임 로직, DB, 파일 I/O, sleep과 blocking lock을 실행하지 않아야 한다.

- callback으로 전달한 data span은 callback이 반환될 때까지만 유효하다. 보관하려면 사용자가 복사해야 한다.

- 한 SessionId에 대해 OnConnected가 먼저 관찰되고 OnClosed는 최대 한 번 관찰되어야 한다.

- 같은 세션의 OnData와 OnClosed는 동시에 호출하지 않는다. 이 보장은 T06~T11에서 상태 머신과 event adapter로 완성한다.

- 서로 다른 세션 callback은 동시에 호출될 수 있다.

- callback 안에서 Send와 RequestClose를 호출할 수 있다. callback 재진입으로 다른 callback을 동기 호출하지 않는다.

결정

StopMode은 graceful과 immediate 두 모드를 제공한다.

- graceful은 새 accept와 외부 send를 막고 이미 수락된 send 및 close event를 설정된 timeout까지 처리한다.

- immediate는 새 I/O 게시를 막고 socket을 닫은 뒤 취소/오류 completion만 drain한다.

- timeout 뒤에는 immediate 단계로 전환하며 남은 session과 outstanding request 수를 결과와 로그에 남긴다.

- 종료 순서는 accept 중단 → session close 요청 → completion drain → worker join → CQ/registered buffer 해제 → Winsock 해제다.

- Stop은 idempotent하며 소멸자에서 예외를 던지지 않는다.

Windows x64 TCP/IPv4 서버Windows 10 1803+·11·Server 2019+가 대상이며 전체 OS 검증 완료를 뜻하지 않는다. double mapping과 RIO 의존성이 있어 x86/Win32·IPv6·TLS·UDP·클라이언트 transport·DLL ABI는 제공하지 않는다.
VS2026/v145와 정적 배포/std:c++latest·/utf-8, Release /MD·Debug /MDd다. 정적 라이브러리·공개 헤더·PDB·정확한 소스 snapshot을 함께 배포한다.
명시적 초기화 실패RIO 함수 테이블을 얻지 못하면 일반 Winsock으로 자동 fallback하지 않는다. 구체적인 library/native 오류를 반환한다.
세션별 등록 메모리double-mapped 링이 wrap 복사를 없애고 수명과 실패 rollback을 세션 단위로 격리한다. worker arena로 바꾸기 전에 시작 비용이 실제 병목인지 측정한다.
유계 저장소와 명시적 배압무제한 queue가 메모리 고갈·tail latency로 이어지지 않도록 Send 거절과 overload close를 구분한다. adapter는 짧은 mutex를 사용하므로 lock-free나 무대기 API로 소개하지 않는다.
완료를 확인하는 종료graceful/immediate를 구분하며 완료 전에 등록 메모리를 해제하지 않는다. Stop 실패를 정상 서비스 재사용의 근거로 삼지 않는다.
선택적 mimalloc최종 executable이 적용 여부를 결정하며 공개 ABI에 allocator 타입을 노출하지 않는다. 현재 기본 패키지는 사용하지 않는다.
비교 가능한 성능 증거Release x64, 같은 장비·설정, 예열·측정·후처리 분리, 최소 5회 중앙값, correctness 오류 0이 기준이다. 한 번에 한 설정만 바꾼다.
