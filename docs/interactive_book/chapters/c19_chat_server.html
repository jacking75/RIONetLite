로직 shard가 플레이어와 룸을 소유한다

네트워크 콜백은 raw 바이트를 복사하고, 게임 워커가 상태를 해석하며, 모든 shard의 같은 룸으로 메시지를 전달한다.

서버와 .NET 10 클라이언트를 실행한다

tools\build.ps1 -Configuration Release -Rebuild
bin\x64\Release\ChatServer.exe --port 32453 --logic-workers 2 --io-workers 4 --max-sessions 32
dotnet build samples\chat_client\csharp_test_client.csproj -c Release
samples\chat_client\bin\Release\net10.0-windows\ChatClient.exe

클라이언트 빌드에는 .NET 10 SDK, GUI 실행에는 .NET 10 Windows Desktop runtime이 필요하다. 현재 클라이언트는 8바이트 version 1 프로토콜이다. 옛 5바이트 패킷 클라이언트를 같은 서버에 연결해 동작할 것으로 가정하지 않는다.

서버의 listening 출력을 확인하고 클라이언트 창을 세 개 연다. 주소 127.0.0.1, 포트 32453, 서로 다른 이름과 방 1로 “연결·입장”을 선택한다. 로그인과 룸 입장 성공 뒤 채팅을 보내면 같은 방의 세 창에 각각 한 번 나타나야 한다. 한 창을 연결 종료하고 방 2로 새 연결하면 방 1의 메시지가 보이면 안 된다. 방 이동은 현재 예제에서 재접속으로 수행한다.

아래 자동 검사는 같은 C# encoder·decoder와 실제 서버를 사용한다. GUI 버튼·창 배치의 수동 검사나 별도 PC 설치를 대신하지 않는다. 이 판에서 자동 실행한 범위와 GUI 미실행 사실은 A05에 따로 기록했다.

tools\test-chat.ps1 -Configuration Release -OutputDirectory logs/chat-check

max-sessions를 작게 줄이면 기본 I/O 워커 수가 그보다 클 수 있으므로 io-workers도 함께 맞춘다. 게임 워커 수와 I/O 워커 수는 같은 값일 필요가 없다. 현재 예제는 adapter slot과 broadcast inbox를 shard당 1024개로 구성하고 max_payload_bytes는 1024다. 브라우저 모델의 작은 capacity 2는 포화를 쉽게 보기 위한 값이다.

객체 순서는 logger와 ChatApplication 생성, Server::Create, Attach, application.Start, Server::Start다. 생성자와 게임 워커가 준비되기 전 콜백을 시작하지 않는다. 시작 실패에서도 이미 만든 로직 워커를 정리한다.

8바이트 헤더와 문자열의 바이트 길이를 읽는다

모든 정수는 big-endian이고 문자열은 strict UTF-8이다. 이름 “가”는 한 글자지만 UTF-8 세 바이트다. u16 길이는 글자 수가 아니라 직렬화한 바이트 수다. 이름은 1..32바이트, 채팅은 0..256바이트다. 바이트 길이를 먼저 계산하고 해당 크기의 payload를 만든다. 잘못된 UTF-8을 자동으로 대체 문자로 바꾸어 통과시키지 않는다.

login A: 00 00 00 0B 00 01 00 01 00 01 41
join 1:  00 00 00 0C 00 01 00 02 00 00 00 01
chat hi: 00 00 00 0C 00 01 00 03 00 02 68 69
beat:    00 00 00 08 00 01 00 04

같은 연결에서 다시 login하거나 Room 상태에서 join으로 방을 바꾸는 경로는 구현되어 있지 않다. 타입·상태·길이·버전·UTF-8 오류는 protocol close다. 로그인은 이름 등록일 뿐 비밀번호 인증이나 영속 사용자 ID가 아니다. room 목록·퇴장·비밀번호·메시지 저장·여러 서버의 룸 분산도 이 예제의 구현 범위가 아니다.

세 명을 다른 shard의 같은 룸에 넣는다

기본 재생은 세 플레이어를 각각 로그인하고 같은 1번 룸에 넣은 뒤 “안녕”을 보낸다. shard가 달라도 대상은 세 명이며 발신자도 받는다. 초기화한 뒤 입장을 로그인보다 먼저 시도하거나 wire의 version을 2로 바꾸면 오류를 관찰할 수 있다. 들어온 바이트가 헤더·본문에 모자라면 무조건 종료하지 않고 입력을 남긴다.

모델은 실제 v1 바이트 규칙과 fixture를 사용하지만 네트워크 지연·mutex 경쟁·세션 종료 요청의 비동기 간격은 생략한다. 모델에서 Closed로 바뀐 것은 실제 서버에서 RequestClose와 OnClosed가 같은 함수 호출 안에서 동기 실행된다는 뜻이 아니다.

PlayerMap과 stream 입력은 로직 shard가 소유한다

RunShard는 Connected에서 Player를 만들고 Data의 소유 payload를 Player 입력 vector에 붙인다. ConsumeInput은 헤더가 모이면 길이와 버전을 검사하고 완전한 메시지마다 ProcessPacket을 호출한다. 처리한 앞부분만 지운 뒤 미완성 꼬리는 남긴다. 반환 시 남은 꼬리는 1024바이트 미만이어야 한다.

한 이벤트의 복사 chunk는 최대 1024바이트이므로 이전 꼬리와 합칠 때 일시적으로 더 긴 입력이 될 수 있다. 1024는 최대 프레임 크기와 adapter chunk 크기이지 모든 수신 span의 합계 상한이 아니다. vector의 capacity가 항상 고정 1024라고 설명하지도 않는다. 실제 코드의 입력 축적과 모델 보호용 상한 2048은 구분한다.

Closed는 Player의 SessionId 전체가 이벤트 ID와 같을 때만 지운다. index가 같아도 이전 세대의 close로 새 Player를 제거하지 않는다. game activity는 ProcessPacket이 갱신하고 주기적 scan이 오래된 플레이어를 idle 종료한다. 네트워크 수신 activity와 별도의 정책이다.

모든 목적지의 공간을 함께 확인한다

QueueBroadcast는 전역 broadcast mutex 아래 모든 shard inbox의 공간을 먼저 검사한다. 하나라도 full이면 어떤 inbox에도 추가하지 않고 발신자의 overload 종료를 요청한다. 모두 공간이 있으면 같은 메시지를 각 inbox에 넣는다. 동시에 들어온 방송도 모든 shard에서 같은 enqueue 순서를 갖도록 만든다.

각 shard는 PopBroadcast로 자기 inbox를 꺼내 자신의 PlayerMap에서 Room 상태이고 room 번호가 같은 사용자를 고른다. shard0의 맵만 순회하는 구현은 다른 shard의 같은 룸 사용자를 빠뜨린다. 현재 코드는 전체 shard fanout과 개별 shard 소유 상태의 두 단계를 분리한다.

이 선택에는 메시지 복사, 잠금과 shard별 유계 저장소 비용이 있다. 큰 MMO의 room actor나 서버 간 메시지 버스로 확장한 설계가 이미 들어 있는 것은 아니다. 현재 예제의 범위를 넘는 대안은 C20에서 제안으로 구분한다.

서버와 클라이언트의 wire를 같은 자료로 검사한다

docs/protocol/chat-fixtures.tsv는 요청·응답 8개의 고정 hex다. C++ 단위 검사와 C# encoder·decoder 검사가 같은 자료를 읽으며 브라우저 모델도 바이트를 대조한다. 다음 소스 창에는 그 파일 전체가 포함되므로 저장소가 없어도 내용을 볼 수 있다.

자동 E2E는 같은 룸의 세 명과 다른 룸, UTF-8 분할, 큰 heartbeat 병합, 최대 payload, 재접속과 잘못된 패킷 종료를 확인한다. 각 shard 구성에서 방송 수신 21건, malformed 종료 5건과 마지막 완전 배출을 요구한다. 짧은 검사이므로 대규모 접속 성능이나 다른 PC 배포 승인을 대신하지 않는다.

네트워크를 멈춘 뒤 게임 큐를 비운다

quit·Ctrl+C·duration·stop 파일로 주 루프가 끝나면 Server::Stop(kGraceful)을 먼저 호출한다. 그 뒤 StopAfterDrain이 adapter depth, 실행 중 게임 작업과 pending broadcast를 배출하고 워커를 join한다. 마지막 active_players, queued_events와 pending_broadcasts가 모두 0이고 프로세스 종료 코드도 0이어야 한다.

서버 라이브러리가 정지했다고 PlayerMap이나 방송 inbox가 자동 정리된다고 가정하지 않는다. 반대로 로직 워커를 먼저 join하면 transport가 나중에 넣은 close를 소비할 수 없다. 현재 앱의 StopAfterDrain은 사용자 업무의 무한 대기를 강제 중단하는 timeout을 구현하지 않는다.

8바이트 헤더를 바이트로 읽는다

Chat protocol v1의 헤더는 8바이트다. 앞 4바이트는 header를 포함한 총 길이, 다음 2바이트는 version 1, 마지막 2바이트는 type이다. 모든 정수는 big-endian이다. C++ 구조체를 그대로 memcpy해 보내면 padding과 endian 때문에 다른 언어와 계약이 어긋날 수 있다.

요청 type은 login 1, join 2, chat 3, heartbeat 4다. 응답은 login ok 101, join ok 102, chat message 103이다. heartbeat는 빈 payload이며 현재 응답을 보내지 않는다. heartbeat ack를 기다리는 새 클라이언트를 만들면 timeout이 발생한다.

login payload는 2바이트 이름 길이와 UTF-8 이름이며 이름은 1..32바이트다. join은 4바이트 room id다. chat은 2바이트 길이와 UTF-8 문자열이며 0..256바이트를 허용한다. 같은 방의 모든 사용자에게 103을 전달하고 송신자도 포함한다.

총 길이 maximum은 1024이며 최소는 8이다. 헤더 검사 뒤 전체 packet이 도착했는지 보고 phase에 맞는 type인지 확인한다. 현재 문서와 fixture를 C++/C# 양쪽에서 읽어 동일한 wire contract를 유지한다.

8바이트 헤더를 바이트로 읽는다: 적용한다

문자 A로 login하면 payload는 00 01 41이고 총 길이는 11이다. 전체 packet은 00 00 00 0B 00 01 00 01 00 01 41이다. 이름 길이는 문자 수가 아니라 UTF-8 byte 수다.

한글 “안녕”의 채팅 payload는 00 06 뒤 여섯 UTF-8 byte이며 총 packet은 16바이트다. fixture의 총 길이와 payload 길이를 직접 계산하면 양쪽 구현이 같은 잘못을 공유하는 것을 줄일 수 있다.

실습에서 관찰할 값

  • 길이에 헤더 8바이트가 포함되는지 본다.
  • 모든 정수가 BE로 encode/decode되는지 본다.
  • UTF-8 byte 길이를 문자열 길이와 구분한다.

생각하고 확인한다

chat text가 empty이면 항상 protocol error인가.

해설 펼치기

현재 v1 계약은 0바이트 채팅을 허용한다. payload의 길이 필드 두 바이트는 필요하고 총 길이는 10이다. 허용 여부는 상상한 정책이 아닌 실제 계약과 fixture를 따른다.

로그인과 룸 상태를 검증한다

Player.phase는 Login, Lobby, Room 세 상태다. 새 연결은 Login이고 type 1이 성공하면 Lobby, type 2가 성공하면 Room이 된다. type 3은 Room에서만 처리한다. 길이가 올바른 packet도 현재 phase에 맞지 않으면 거절한다.

예제 login은 이름을 저장하고 상태를 바꾸는 기능이다. 비밀번호, 계정 DB나 token을 검증하지 않는다. 인터넷 게임의 인증이라고 소개하면 기능 범위를 과장한다. 인증 추가 시 결과를 같은 owner worker로 돌려 phase와 request id를 확인하는 구조가 필요하다.

ValidUtf8은 MultiByteToWideChar에 MB_ERR_INVALID_CHARS를 사용한다. UTF-8 문자열을 저장하기 전에 잘못된 byte sequence를 거절한다. 길이 상한은 byte 단위이며 추후 UI 표시 이름의 금지 문자나 정규화 정책과는 다른 검사다.

room id는 unsigned 32비트 값이다. 예제는 room 생성 권한이나 입장 인원 제한을 제공하지 않는다. Room phase와 같은 room id의 peer에게 chat을 fanout하는 것까지가 현재 기능이다. 기능 추가 시 별도 authoritative room owner가 필요한지 검토한다.

로그인과 룸 상태를 검증한다: 적용한다

join을 login보다 먼저 보내면 종료해야 한다. login을 두 번 보내거나 Lobby에서 chat을 보내는 것도 동일하게 phase 위반이다. 정상 login 101과 join 102를 확인한 뒤에 chat을 보낸다.

UTF-8 byte 길이가 maximum 이내여도 encoding이 잘못될 수 있다. 길이와 UTF-8 검사, phase 검사를 독립적으로 테스트한다. 정상 한글을 거절하면서 악성 길이만 잡는 구현은 적절한 입력 검증이 아니다.

실습에서 관찰할 값

샤드 사이 broadcast를 일관되게 보낸다

PlayerMap은 worker별로 나뉘므로 chat을 송신자의 로컬 map에만 broadcast하면 다른 shard의 같은 방 사용자가 메시지를 못 받는다. 현재 Chat은 shard마다 유계 BroadcastInbox를 만들고 각 worker가 자기 PlayerMap에 전달한다.

QueueBroadcast는 하나의 mutex 아래 모든 목적 inbox의 여유를 먼저 확인한다. 한 곳이라도 full이면 아무 곳에도 넣지 않는다. 모두 가능할 때 동일한 message를 전체 inbox에 넣어 partial fanout을 피한다.

동시에 여러 shard에서 chat이 오더라도 같은 mutex로 enqueue 순서를 정해 모든 shard의 broadcast 순서가 같게 한다. 이것은 서버 내 fanout 수락 순서이며 전체 인터넷 사용자 행동의 실제 시각 순서를 보장하는 기능은 아니다.

각 worker는 자신의 inbox를 꺼내 Room phase와 같은 room id인 Player에게 103을 Send한다. 느린 peer의 송신 포화는 그 peer의 close 정책으로 처리하고 다른 peer에게 수락된 메시지는 계속 진행한다. inbox 저장량과 peer 송신 링은 다른 상한이다.

C# 클라이언트도 전체 패킷을 직렬화한다

클라이언트도 TCP의 부분 송신과 수신을 처리해야 한다. Socket.SendAsync가 buffer 전체를 보내지 못하면 남은 memory slice로 계속 보낸다. ReceiveAsync도 원하는 길이 전체를 보장하지 않으므로 ReadExactlyAsync가 header와 payload를 따로 채운다.

UI chat과 heartbeat가 동시에 송신하면 두 SendAsync loop의 바이트가 섞일 수 있다. ChatConnection은 semaphore를 전체 packet 송신 동안 유지한다. 각 syscall 한 번만 잠그면 header 일부와 다른 메시지가 섞일 가능성이 남는다.

수신은 하나의 reader가 소유한다. OpenAsync는 login 101과 join 102를 순서대로 읽고 확인한 뒤 연결을 반환한다. 이후 ReadLoopAsync가 chat 103을 읽는다. 여러 reader가 같은 socket에서 header와 payload를 나눠 가져가면 framing이 깨진다.

Dispose는 Interlocked로 한 번만 socket을 닫는다. 진행 중 Send의 continuation은 아직 semaphore를 Release할 수 있으므로 그 managed semaphore를 즉시 dispose하지 않는다. 종료 후 continuation과 객체 수명도 비동기 코드의 일부다.

게임 워커 구조

OnData의 span은 callback 동안만 유효하다. 게임 로직이 나중에 사용하려면 owned payload로 복사한다. QueuedEventAdapter는 연결·raw data·종료를 미리 확보한 shard별 저장소로 복사하며 session.index % shard_count로 라우팅한다. 세션 순서와 generation을 함께 유지한다.

ChatApplication 전체 코드를 다음 순서로 읽는다.

1. max_sessions와 일치하는 adapter session gate를 만들고 kDisconnect와 RequestClose lambda를 설정한다. 모든 차원은 양수이고 capacity는 유한하다.

2. Attach 후 게임 워커를 시작하고 Server를 Start한다. 네트워크 callback은 adapter 복사만 수행한다.

3. 각 RunShard는 재사용하는 destination 버퍼로 TryPop한다. Connected에서 Player를 만들고 Data에서 자신의 stream 누적 버퍼에 복사한다. 완성된 메시지의 login/join/chat 처리는 이 워커에서 수행한다.

4. Closed는 Player.id 전체가 이벤트의 SessionId와 같을 때만 지운다. index가 같아도 이전 generation의 이벤트는 새 Player를 지우지 못한다.

5. 방 채팅은 유계 broadcast inbox를 모든 게임 shard에 넣는다. 각 shard가 자기 PlayerMap에서 같은 room의 사용자를 골라 Send한다. 한 shard만 순회하면 다른 shard의 같은 방 사용자를 놓친다.

6. Server Stop이 모든 close를 만든 뒤 adapter depth·pending broadcast·실행 중 logic를 배출하고 게임 워커를 join한다. parked close도 depth에 포함된다. 마지막 active player 수가 0인지 확인한다.

flowchart LR
  IO[I/O callback] --> A[owned raw event queue]
  A --> L0[logic shard 0: PlayerMap]
  A --> L1[logic shard 1: PlayerMap]
  L0 --> B[bounded broadcast fanout]
  L1 --> B
  B --> L0
  B --> L1
  L0 --> S[Send: full SessionId]
  L1 --> S

TryPop의 kDestinationTooSmall은 이벤트를 제거하지 않는다. header.payload_bytes 이상 버퍼를 준비한 뒤 재시도한다. kEmpty는 현재 시점의 빈 snapshot이며 producer가 살아 있는 동안 전체 종료를 뜻하지 않는다. 어댑터는 짧은 mutex를 사용하므로 lock-free API라고 부르지 않는다. 배압에서 포화 정책을 결정한다.

잘못된 길이·version·type·상태·UTF-8은 protocol close다. 로그인은 이름 등록이며 비밀번호 인증이 아니다. room leave/list/password·메시지 저장·사용자 영속 ID는 없다. 다른 room으로 이동하려면 새 연결로 들어간다. 포화는 overload close를 사용한다.
