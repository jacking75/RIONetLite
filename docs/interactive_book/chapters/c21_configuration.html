설정값을 메모리와 요청 수로 계산한다

범위 검증은 잘못된 입력을 일찍 거절한다. 실제 주소 매핑과 메모리 확보, 모든 provider 동작의 성공까지 보장하지는 않는다.

DefaultIoWorkerCount는 모든 processor group의 활성 logical processor 수를 읽는다. 3개 이상이면 하나를 남기고 1..256으로 제한하며 조회가 0이면 1을 사용한다. 물리 코어 수나 독자의 PC에서 항상 같은 상수인 값이 아니다. 아래 계산은 워커 수를 명시한 조건으로 진행한다.

각 범위뿐 아니라 관계도 검사한다

워커 수는 세션 수보다 클 수 없고, 메시지는 수신·송신 양쪽 버퍼에 들어가야 한다. page 정렬은 4096이라고 영구 하드코딩하지 않고 Windows GetSystemInfo에서 얻는다. 세션 수가 워커 수로 나누어떨어지지 않으면 ceil(max_sessions/workers)를 최대 담당 수로 사용하고 그 두 배를 워커 CQ 용량으로 계산한다.

계산한 CQ가 RIO_MAX_CQ_SIZE인 0x8000000을 넘으면 설정 오류로 거절한다. 시작 중의 모호한 스레드 실패까지 기다리지 않는다. 예산 계산은 uint64 overflow도 확인한다. JS 실험은 큰 예산을 BigInt와 10진 문자열로 다루어 Number 정밀도로 값을 뭉개지 않는다.

max_receive_chunk_bytes는 한 수신 요청의 raw 크기이고 max_message_bytes는 메시지 크기다. 여러 프레임이 합쳐진 span은 메시지 한도보다 클 수 있다. Chat의 4096바이트 수신 요청과 1024바이트 메시지·adapter chunk는 함께 사용할 수 있다. 이 관계를 “수신 크기는 항상 메시지 이하”라는 가짜 제약으로 바꾸지 않는다.

등록·예약·backing commit·control을 분리한다

한 세션의 backing B는 receive_buffer_bytes+send_buffer_bytes다. 이중 view의 가상 주소 등록·예약 추정은 2×B이고 backing commit 추정은 B다. 기본 링 크기와 1024세션이면 commit은 320MiB, 등록·예약 범위 추정은 640MiB다. 두 view가 같은 backing을 가리키므로 이를 물리 메모리 640MiB로 단정하지 않는다.

estimated_control_bytes는 세션당 제어 512+컨텍스트 128바이트의 추정과, 워커당 batch×32+metric 256바이트의 추정을 합친다. 실제 sizeof·CQ 커널 비용·thread stack·close mailbox·allocator·adapter·broadcast inbox와 프로세스 전체 private bytes를 보장하는 값이 아니다. 게임 큐 예산도 별도로 더한다.

등록 범위와 커널의 실제 메모리 고정 비용이 항상 같은 회계 단위라고 가정하지 않는다. 예산으로 구성을 좁힌 뒤 실제 OS 지표로 commit과 kernel 자원을 측정한다. Validate가 성공해도 가상 주소 확보, 매핑·등록, CQ·스레드 생성은 실패할 수 있다. Create의 자원 오류와 Start의 오류를 계속 검사한다.

검증 함수에 없는 업무 규칙도 있다

현재 ValidateServerConfig는 WorkerWaitMode의 임의 정수 cast를 별도로 거절하지 않는다. fixture의 enum-not-validated 사례가 이를 드러낸다. 자원 범위 검사가 통과했다고 공개 enum 외의 값이 지원된다는 뜻은 아니므로 kPolling·kAdaptive·kNotification만 사용한다. 라이브러리를 임의로 수정하지 않고 이 한계를 기록했다.

길이 헤더를 쓰는 앱의 최소 메시지 크기 4 또는 8도 자원 검증만으로 정해지지 않는다. max_message_bytes=1은 자원 범위에 들어갈 수 있지만 Echo·Chat의 정상 프레임 한도로는 쓸 수 없다. 실제 프로토콜·게임 작업·DB 큐의 제약은 애플리케이션이 추가한다.

구체적인 예산 예시

기본 1024세션에서 recv 64KiB + send 256KiB backing commit 추정은 320MiB다. double mapping의 virtual reserve와 등록 범위 추정은 640MiB다. 두 view가 같은 backing을 가리키므로 등록 범위 640MiB를 물리 메모리 640MiB로 해석하지 않는다. control·close mailbox·CQ·thread stack·adapter/broadcast·allocator/kernel 추가 비용은 별도다. estimated_control_bytes는 근사치이며 실제 sizeof 또는 process 총량 보장이 아니다.

max_receive_chunk_bytes는 요청당 raw 수신 크기이고 max_message_bytes는 메시지/Send 제한이다. 여러 메시지의 합계 raw span이 message 제한보다 클 수 있다. adapter는 raw span을 조각으로 복사하고 게임 워커가 framing한다. 2 shard×1024 slot×1024 byte의 payload만 2MiB이며 gate와 parked index가 추가된다.

처음에는 기본 adaptive 정책을 사용하고 실제 workload의 P99·CPU·배압을 측정한 뒤 한 항목씩 바꾼다. keepalive 설정 실패는 접속 setup 실패 로그로 남기며 조용히 무시하지 않는다. shutdown timeout은 종료 계약의 사용자 callback·추가 drain 한계를 따른다.

설정은 메모리와 완료 큐 예산이다

ServerConfig는 편의 옵션 집합이 아니라 사전에 확보할 자원 예산이다. 기본 max_sessions는 1024, 수신 링은 64KiB, 송신 링은 256KiB다. 세션이 아직 접속하지 않았더라도 풀 준비에서 버퍼 자원이 필요하므로 큰 세션 수는 시작 비용에 직접 영향을 준다.

수신·송신 링은 Windows page 크기의 0이 아닌 배수여야 한다. max_receive_chunk_bytes는 수신 링 이하여야 하고 max_message_bytes는 양쪽 링에 들어가야 한다. io_worker_count는 1..256이며 max_sessions를 넘지 않는다. 작은 테스트 서버라면 기본 CPU 기반 worker 수를 그대로 두지 말고 같이 줄인다.

worker당 최대 세션은 ceil(max_sessions/workers)로 계산하고 CQ capacity는 그 두 배다. 현재 세션당 in-flight 수신 하나, 송신 하나라는 구현 가정이 이 식을 만든다. 향후 다중 송신 요청을 허용한다면 capacity 계산과 테스트도 같이 바뀌어야 한다.

double mapping으로 같은 저장소를 두 주소에 연결하므로 registered span과 reserved virtual bytes는 링의 논리 용량 합계의 두 배다. committed bytes 추정은 논리 저장소 합계다. 이 계산은 실제 process memory나 OS provider의 모든 부가 자원을 측정한 값이 아니다.

설정과 계산 예산

include/rionetlite/config.h

ServerConfig의 default member initializer는 실제 기본값을 보여 준다. port는 0이지만 검증에서 0을 거절하므로 사용자가 지정해야 한다. worker 기본값은 CPU topology에 따라 달라진다.

논리 메시지 크기, 수신 chunk와 링 용량은 다른 제한이다. 한 callback의 크기를 protocol maximum과 혼동하지 않는다. graceful, peer drain과 idle timer도 각각 다른 수명을 제한한다.

ValidatedServerConfig는 원래 값과 계산 결과를 함께 담는다. 이 추정값은 자원 준비 전에 사용하며 실제 process handle나 private memory를 측정한 결과와 구분한다.
