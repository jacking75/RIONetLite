EchoServer 전체를 먼저 읽는다

EchoServer는 받은 메시지를 그대로 돌려보내는 가장 작은 예제다. 코드 전체의 모양, 실행 순서, 패킷 하나가 서버를 지나가는 길을 먼저 보고 나서 세부 장으로 들어간다.

입문이 장을 읽고 나면

EchoServer의 main과 EchoHandler가 각각 무슨 일을 하는지 설명하고, 클라이언트가 보낸 7바이트가 응답으로 돌아가기까지 거치는 단계를 순서대로 말할 수 있다. 같은 흐름을 한 단계씩 실행하는 실험은 C04에 있다.

이 예제의 소유권은 main이 관리한다. 서버 설정을 채우고 포트를 연 뒤, 콜백에서 프레임을 해석하며 세션을 통해 답을 보낸다.

받은 패킷을 그대로 돌려준다

EchoServer는 네트워크 라이브러리의 “Hello, World”다. 게임 규칙은 없고, 클라이언트가 보낸 메시지를 같은 모양 그대로 돌려준다. 소스는 samples/echo_server/main.cpp 한 파일이며 공개 헤더만 사용한다.

메시지 형식은 P01에서 본 길이 헤더 방식이다. 앞의 4바이트는 헤더를 포함한 전체 길이이고, 큰 자리부터 적는다(big-endian). 길이는 최소 4(본문 없음)이고 최대는 max_message_bytes(기본 16KiB)다. 이 범위를 벗어난 길이가 오면 서버는 그 연결을 닫는다.

00길이00길이00길이07길이72r69i6Fo

클라이언트가 보낸 바이트와 서버가 돌려주는 바이트가 똑같다. 헤더까지 그대로 돌려주므로 클라이언트는 같은 규칙으로 응답을 읽을 수 있다.

전체 코드는 두 덩어리다

main.cpp는 약 220줄이지만 절반 가까이는 명령행 옵션 처리다. 뼈대는 두 덩어리뿐이다. 네트워크 알림을 받아 응답하는 EchoHandler 클래스와, 서버를 만들고 돌리고 멈추는 main 함수다. 아래는 실제 코드에서 옵션 처리, 로그 출력, Ctrl+C 처리를 뺀 축약본이다. 번호는 바로 아래 표의 설명과 짝을 이룬다.

// samples/echo_server/main.cpp의 축약본이다. 옵션 처리와 로그 출력은 뺐다.
class EchoHandler final : public rionetlite::EventHandler {
 public:
  explicit EchoHandler(std::uint32_t max_message_bytes)
      : decoder_(max_message_bytes) {}
  void Attach(rionetlite::Server& server) noexcept { server_ = &server; }  // ⑦

  void OnConnected(rionetlite::SessionId) override {}  // ①

  std::size_t OnData(rionetlite::SessionId session,
                     std::span<const std::byte> data) override {  // ②
    const rionetlite::DecodeResult decoded = decoder_.Decode(
        data, [&](std::span<const std::byte> packet) {  // ③
          const auto result = server_->Send(session, packet);  // ④
          if (result == rionetlite::SendResult::kWouldBlock ||
              result == rionetlite::SendResult::kUnavailable) {
            server_->RequestClose(session,
                                  rionetlite::CloseReason::kOverloaded);
          }
        });
    if (decoded.error != rionetlite::DecodeError::kNone) {  // ⑤
      server_->RequestClose(session, rionetlite::CloseReason::kProtocolError);
      return data.size();
    }
    return decoded.consumed_bytes;  // ⑥
  }

  void OnClosed(rionetlite::SessionId, rionetlite::CloseReason) override {}

 private:
  rionetlite::LengthPrefixedDecoder decoder_;
  rionetlite::Server* server_ = nullptr;
};

int main() {
  rionetlite::ServerConfig config;  // ⑧
  config.port = 32452;
  EchoHandler handler(config.max_message_bytes);
  auto server = rionetlite::Server::Create(config, handler);  // ⑨
  if (!server) return 3;
  handler.Attach(*server);  // ⑦
  if (auto started = server->Start(); !started) return 4;  // ⑩
  // 실제 코드는 50ms마다 quit 입력, Ctrl+C, 실행 시간, stop 파일을 확인한다.  ⑪
  if (auto stopped = server->Stop(rionetlite::StopMode::kGraceful); !stopped) {
    return 5;  // ⑫
  }
  return 0;
}
#코드하는 일
①OnConnected새 연결이 생겼다는 알림이다. Echo는 로그만 찍는다. 게임이라면 여기서 플레이어 객체를 만든다.
②OnData이 세션으로 받은 바이트 중 아직 처리하지 않은 부분 전체가 data로 들어온다. 앞에서 남겨 둔 조각과 새로 받은 바이트가 이어진 상태다.
③decoder_.Decode공개 헤더 packet_decoder.h의 길이 헤더 디코더다. data를 앞에서부터 읽어 완성된 패킷을 찾을 때마다 람다를 부른다. 두 패킷이 붙어 왔으면 두 번 부른다.
④Send패킷을 그대로 돌려보낸다. Send는 바이트를 라이브러리 내부 송신 버퍼에 복사한 뒤 바로 돌아온다. 버퍼가 가득 차서 거절되면 Echo는 연결을 닫는 정책을 쓴다.
⑤오류 처리길이가 4보다 작거나 최대값보다 크면 프로토콜 오류다. 연결 종료를 요청하고, 닫을 연결이므로 받은 바이트를 모두 소비한 것으로 돌려준다.
⑥소비량 반환“앞에서부터 이만큼은 처리했다”는 바이트 수다. 패킷이 아직 덜 왔으면 0이다. 남은 바이트는 라이브러리의 수신 링에 그대로 남아 다음 수신 때 새 데이터와 함께 다시 온다.
⑦Attach라이브러리 API가 아니라 예제의 도우미 함수다. 핸들러가 응답할 때 쓸 서버 주소를 기억한다. 콜백이 시작되는 Start보다 먼저 부른다.
⑧ServerConfig포트만 바꾸고 나머지는 기본값을 쓴다. 실제 코드는 명령행으로 워커 수, 최대 세션 수 등을 바꿀 수 있다.
⑨Server::Create설정을 검사하고 세션 풀과 버퍼를 준비한다. 실패하면 오류를 담은 std::expected가 온다. 핸들러는 서버보다 먼저 만들어 서버보다 오래 살아 있어야 한다.
⑩Startaccept 스레드와 I/O 워커를 띄운다. 이때부터 콜백이 다른 스레드에서 불린다.
⑪대기 반복주 스레드는 종료 조건만 확인하며 기다린다. 네트워크 처리는 모두 라이브러리 스레드에서 일어난다.
⑫Stop새 연결을 막고, 이미 맡은 송신을 끝낼 기회를 준 뒤 서버를 멈춘다. 콜백 안이 아니라 서버를 소유한 주 스레드에서 부른다.

코드에 소켓, 스레드 생성, RIO 함수가 하나도 없다는 점에 주목한다. 그 일은 모두 라이브러리 안에서 일어난다. 실제 원문은 아래 버튼으로 확인한다.

패킷 하나가 왕복하는 길

그림으로 보기 · 단계 버튼으로 요청과 상태가 바뀌는 순서를 확인한다. 다음 코드 설명은 이 그림의 해당 단계를 구체적으로 읽는다.

클라이언트가 rio 메시지(7바이트)를 보내고 같은 7바이트를 돌려받기까지를 네 참여자로 나누어 그렸다. 세로선은 각 참여자이고, 위에서 아래로 시간이 흐른다.

  1. 미리 게시한 수신 요청 — 연결이 생길 때 라이브러리가 “이 세션의 수신 링 빈 칸에 데이터를 받아 달라”는 요청을 이미 맡겨 두었다.
  2. 전송 — 클라이언트가 00 00 00 07 72 69 6F를 보낸다.
  3. 커널이 수신 링에 쓴다 — 등록 버퍼로 만든 수신 링에 바이트를 직접 쓰고, 이 세션 담당 워커의 CQ에 “7바이트 받음” 완료를 남긴다.
  4. 워커가 완료를 꺼낸다 — 완료가 정말 이 세션의 현재 연결 것인지 확인하고, 받은 7바이트를 링에 반영한다. 링에 빈 칸이 있으면 다음 수신 요청을 콜백보다 먼저 게시해 둔다.
  5. OnData 호출 — 워커가 아직 처리하지 않은 바이트 전체(여기서는 7바이트)를 넘긴다.
  6. Decode — 디코더가 헤더의 7을 읽고, 7바이트가 다 있으므로 패킷 하나를 람다에 넘긴다.
  7. Send — 패킷이 송신 링에 복사된다. 진행 중인 송신이 없으므로 RIO 송신 요청이 바로 게시되고, Send는 kQueued를 돌려준다. 이 시점은 “라이브러리가 맡았다”는 뜻이지 “상대가 받았다”는 뜻이 아니다.
  8. 소비량 반환 — OnData가 7을 돌려주면 수신 링의 읽기 위치가 7만큼 이동해 그 공간이 다시 빈 칸이 된다.
  9. 응답 전송 — 커널이 송신 링의 7바이트를 클라이언트로 보낸다.
  10. 송신 완료 — CQ에 송신 완료가 오면 워커가 보낸 만큼 송신 링을 비운다. 그 사이 쌓인 데이터가 있으면 다음 송신을 게시한다.

쪼개져 오면? 1번에서 2바이트만 먼저 도착했다고 하자. OnData는 2바이트를 받고, 디코더는 헤더 4바이트도 다 오지 않았으니 패킷을 찾지 못한다. OnData는 0을 돌려주고 2바이트는 수신 링에 그대로 남는다. 나머지 5바이트가 도착하면 OnData는 이어 붙은 7바이트를 받아 그때 응답한다. 앱이 조각을 모으는 버퍼를 따로 만들 필요가 없다.

정상 흐름에서 수신 요청은 항상 하나가 커널에 맡겨진 상태로 남는다. 그래서 응답 송신이 끝나도 그 세션의 메모리를 바로 해제할 수 없다. 이런 “맡긴 요청의 수명”이 3부와 4부의 핵심 주제다.

직접 실행해 본다

저장소 루트의 PowerShell에서 실행한다. 첫 명령은 Release 구성을 빌드하고 단위·통합 테스트까지 실행한다. 도구 설치와 오류 해결은 C02에서 자세히 다룬다.

tools\build.ps1 -Configuration Release
bin\x64\Release\EchoServer.exe --port 32452

# 다른 터미널에서 부하 클라이언트로 10초 동안 왕복을 확인한다.
bin\x64\Release\LoadClient.exe --port 32452 --connections 4 --duration 10 --scenario echo --json result.json

서버 창에 EchoServer listening on port 32452가 보이면 접속을 기다리는 중이다. 클라이언트가 붙을 때마다 connected: 뒤에 세션의 index와 generation이 index:generation 형태로 찍힌다. 클라이언트가 끝나면 result.json에서 받은 패킷 수가 0보다 크고 오류 카운터가 0인지 확인한다. 서버는 콘솔에 quit을 입력하거나 Ctrl+C로 멈춘다.
