# RIONetLite HTML 책 구현 상세 계획

작성일: 2026-10-27

조사 기준 커밋: `a5f29df610bdbafe68a69e0698ca71260b4c1fa7`

상태: 다음 세션 구현을 위한 계획. 본문 집필과 기존 문서 삭제는 아직 시작하지 않았다.

> main 통합 시 추가 확인: 원격 `main`의 `326c2cc`에는 이 계획의 조사 기준 이후 변경이 있다. 기존 문서 일부가 이미 `docs/operations.md`, `docs/verification.md` 등으로 통합되었고, `docs/rionetlite_book.html`도 존재한다. 아래 24개 목록은 원래 조사 시점의 목록이다. 다음 세션의 B00에서는 최신 파일과 기존 기술서 내용을 함께 대조하고 이관표를 갱신한다. 이미 삭제된 문서를 복원하거나 기존 기술서를 확인 없이 덮어쓰지 않는다. 기존 기술서의 고유한 내용도 최종 책에 통합한 뒤 독자 진입점을 하나로 정리한다. 샘플에 포함된 코드는 명시된 이전 커밋의 스냅샷이다.

## 1. 다음 세션에서 해야 할 일

이 문서에 따라 RIONetLite를 배우고 실제 서버에 사용하는 데 필요한 HTML 책을 완성한다. 현재 `docs/interactive_book/index.html`은 방향을 확인하기 위한 10개 학습 페이지 샘플이다. 샘플의 화면 구성과 실험 방식을 바탕으로 확장하되, 샘플의 짧은 설명을 완성본의 깊이 기준으로 삼지 않는다.

사용자가 확정한 요구는 다음과 같다.

1. 설명에 필요한 분량을 충분히 쓴다. 책을 작게 만드는 것을 목표로 삼지 않는다.
2. 그림, 움직이는 그림, 단계별 실행, 코드 탐색, 조건 변경 실험으로 HTML의 장점을 살린다.
3. 문장과 용어를 자연스럽고 알기 쉽게 쓴다. 한국어 평서문 `~다`체를 사용한다.
4. `docs`의 기존 내용을 책으로 통합한다. 같은 내용을 설명하는 마크다운 파일을 별도 독자 문서로 남기지 않는다.
5. 기존 문서에서 빠뜨린 내용이 없는지 확인하고, 참조 링크와 검사 도구까지 바꾼 뒤 마크다운을 삭제한다.
6. 코드의 실제 동작과 책의 설명이 일치해야 한다. 교육용 모델과 실제 실행 기록은 구분한다.

다음 세션의 시작 순서는 이 문서 읽기 → `AGENTS.md` 확인 → Git 상태 및 기준 커밋 변경 확인 → 15절의 B00부터 실행이다. 이미 완료한 단계는 검증 근거를 확인하고 이어서 진행한다. 별도의 기획서를 다시 만들거나 목차 제안만 하고 종료하지 않는다.

이번 계획은 책과 문서 체계에 관한 것이다. 책을 쓰기 위해 라이브러리 API나 네트워크 알고리즘을 임의로 바꾸지 않는다. 구현 결함이 발견되면 근거와 영향을 기록하고 책에서 정확하게 설명한다. 별도 코드 수정이 필요한 경우 작업 범위를 구분한다.

## 2. 최종 결과와 완료 기준

독자가 여는 문서는 `docs/interactive_book/index.html` 하나다. 브라우저로 파일을 직접 열어도 본문, 검색, 그림, 실험, 코드 탐험기가 작동해야 한다. 인터넷, 개발 서버, 계정, 외부 폰트나 CDN이 없어도 읽을 수 있게 만든다.

책에는 다음이 모두 포함되어야 한다.

- 6개 부, 28개 장, 5개 부록. 목차는 5절의 고정 ID를 사용한다.
- 20개 필수 실험. 학습 목적과 검증 조건은 7절에 정의한다.
- 공개 API의 사용 계약, 설정표, 오류 대응표, 실제 코드와 테스트로 연결되는 설명.
- EchoServer와 ChatServer의 실행 및 확장 과정.
- 종료·오류·포화 상황의 설명과 실험. 정상 왕복만 설명하고 끝내지 않는다.
- 기존 마크다운 24개에 대한 내용 이관 기록과 삭제 완료 여부.
- 검색, 용어 설명, 되돌아가기, 읽기 위치 저장, 자기 점검, 밝은/어두운 화면, 키보드 조작, 인쇄용 보기.
- 책 생성기, 정합성 검사, 모델 테스트, 실제 브라우저 테스트를 재현할 명령.

종이책 환산 400~600쪽 이상도 허용하지만 쪽수를 채우기 위해 내용을 늘리지 않는다. HTML의 한 장은 여러 학습 절로 나누며, 각 절은 하나의 질문에 답한다. 독자는 필요한 장으로 바로 들어갈 수 있어야 한다. 전체 본문을 강제로 순서대로 읽게 하지 않는다.

첫 판에서 실제 실행 로그의 범용 가져오기, 브라우저 내 C++ 컴파일, AI 튜터, 계정 동기화, 온라인 협업, 외부 사이트 배포는 구현 범위에 넣지 않는다. 대신 실제 테스트 실행 안내와 코드·테스트 연결은 반드시 완성한다. 이 기능들 없이도 요구한 학습 경험이 완결되어야 한다.

## 3. 문체와 용어: 원고 작성 규칙

### 3.1 설명을 쓰는 순서

원칙을 먼저 선언하고 끝내지 말고, 상황 → 코드의 동작 → 그렇게 하는 이유 → 어겼을 때의 결과 순서로 설명한다. 한 문장에는 중심 내용을 하나만 담는다. 독자가 C++과 게임 서버 개발에는 익숙하지만 RIO와 이 저장소의 세부 구조는 모른다고 가정한다.

짧은 핵심 설명 뒤에 충분한 구현 설명과 설계 판단을 붙인다. 중요한 안전 조건은 접힌 영역 안에만 넣지 않는다. 심화 영역은 대안 비교, 드문 분기, 역사적 배경에 사용한다.

다음 표현을 교정 기준으로 삼는다.

| 피할 표현 | 사용할 설명 |
|---|---|
| 결정론적 종료를 기본 계약으로 삼는다 | 서버를 종료할 때 새 연결을 막고, 진행 중인 요청을 정리한 뒤 자원을 해제한다. |
| 유계 백프레셔를 적용한다 | 송신 버퍼에는 크기 제한이 있다. 공간이 부족하면 새 데이터를 받지 않고 `kWouldBlock`을 반환한다. |
| 수명 불변 조건을 보존한다 | 요청이 끝나기 전에는 그 요청이 쓰는 버퍼를 옮기거나 해제하지 않는다. |
| generation mismatch로 stale event를 reject한다 | 작업에 기록된 세대와 현재 연결의 세대가 다르면 오래된 작업으로 보고 거절한다. |
| callback span을 저장하는 구현은 잘못이다 | 콜백이 반환된 뒤에는 이 메모리를 계속 사용할 수 없다. 나중에 처리하려면 유효한 동안 데이터를 복사해야 한다. |
| header와 payload의 임시 벡터 할당은 잘못이다 | 헤더와 본문을 따로 받는 `Send`를 쓰면 합치는 용도의 임시 버퍼를 만들지 않아도 된다. |
| 관측성을 레버리지한다 | 로그와 지표를 함께 보면 어느 세션에서 어떤 요청이 실패했는지 찾을 수 있다. |

규칙을 절대적인 선악으로 표현하지 않는다. 성능상 불리한 선택과 메모리 안전성을 깨는 오류를 구분한다. 예를 들어 임시 버퍼 사용은 비용과 설계의 문제이며, 콜백 span의 수명 위반과 같은 종류의 오류가 아니다.

### 3.2 용어 표준

첫 등장에서는 쉬운 설명과 실제 용어를 함께 적고, 이후에는 일관된 이름을 사용한다. 검색에서는 영어, 한글, 코드 식별자 모두 연결한다.

| 책에서 주로 쓸 말 | 처음 소개할 설명 / 검색 별칭 |
|---|---|
| 요청을 게시한다 | 운영체제에 비동기 작업을 요청한다. post, 게시 |
| 완료를 처리한다 | completion queue에서 결과를 꺼내 해당 요청의 상태를 갱신한다. completion |
| 아직 끝나지 않은 요청 | outstanding, in-flight. 코드에서는 각각의 카운터와 플래그 의미를 구분한다. |
| 세션 세대 | 슬롯을 다시 사용할 때 바뀌는 연결 식별값. generation, session_uid |
| 공간 부족으로 송신을 받지 못함 | 배압 또는 backpressure. 실제 반환값은 `kWouldBlock` 등이다. |
| 남은 완료를 처리한다 | drain. 무엇을 언제까지 처리하는지 함께 설명한다. |
| 한꺼번에 묶어 보낸다 | 송신 병합, coalescing. 패킷 경계를 바꾸는 것과 구분한다. |
| 로그와 지표로 상태를 확인한다 | 관측성, observability |
| 용량이 정해진 큐 | 유계 큐, bounded queue |
| 같은 메모리를 연속 주소 두 곳에 연결한다 | 이중 매핑, double mapping |
| 처리할 데이터의 범위를 빌려 본다 | span/view. 소유권 이전이나 복사와 구분한다. |

`Server::Send`, `SessionId`, `RIO_BUF` 등 실제 코드 식별자는 번역하지 않는다. `kQueued`를 ‘전송 완료’라고 바꾸지 않는다. ‘완료’는 송신 접수, 운영체제 요청 완료, 상대 애플리케이션 처리 완료 중 어느 것인지 명시한다.

화면 버튼도 자연스럽게 쓴다. ‘오류 주입 실행’보다는 ‘이번 요청을 실패시키기’, ‘상태 전이 평가’보다는 ‘이 순서로 종료해 보기’처럼 독자가 하는 행동을 적는다. 주요 제목은 한국어로 쓴다. 샘플의 영문 보조 제목은 필요한 곳에만 남긴다.

### 3.3 편집 검수

각 장은 기술 검수와 문장 검수를 따로 수행한다. 자동 검사는 용어 혼용과 반복 표현을 후보로 찾을 뿐, 자연스러움을 통과 판정하지 않는다. 실제 문장을 읽으며 다음을 확인한다.

- 누가 어떤 작업을 하는지 주어와 대상이 드러나는가?
- 코드 용어를 모르는 독자가 앞 문장으로 의미를 이해할 수 있는가?
- ‘이것’, ‘해당’, ‘계약’, ‘정합성’으로 중요한 대상을 뭉뚱그리지 않았는가?
- ‘반드시’, ‘항상’, ‘절대’의 근거를 실제 구현이나 공개 계약에서 확인했는가?
- 성능 설명에서 측정 결과와 원인에 대한 해석을 구분했는가?
- 설명을 줄이느라 실패 조건이나 제한을 생략하지 않았는가?

## 4. 독자가 책을 사용하는 방식

첫 화면에는 책의 주제, 세 가지 읽기 경로, 이어 읽기, 전체 검색을 둔다. 거대한 기능 목록이나 구현 도구 이름을 첫 화면에 나열하지 않는다.

| 읽기 경로 | 권장 장 | 도달할 결과 |
|---|---|---|
| 서버를 먼저 실행해 보기 | C01~C04 → C13 → C18~C20 | 빌드하고 예제를 실행하며 게임 로직을 어디에 붙일지 이해한다. |
| 내부 동작 이해하기 | C05~C17 | 연결, 수신, 송신, 종료의 코드와 메모리 수명을 설명한다. |
| 문제를 찾고 수정하기 | C21~C28 → 필요한 내부 장 | 로그·테스트·측정 근거로 원인을 좁히고 회귀를 확인한다. |

권장 순서는 안내일 뿐 잠금 조건이 아니다. 선수 지식이 필요한 절에는 관련 설명으로 가는 링크를 제공하고, 돌아오면 읽던 위치와 실험 상태를 복원한다.

한 절의 기본 구성은 다음과 같다. 단순 API 항목에는 모든 요소를 강제로 넣지 않는다.

1. 독자가 마주할 상황과 이번 절에서 답할 질문.
2. 실행 전 예측 질문. 맞혀야 진행할 수 있는 시험으로 만들지 않는다.
3. 그림이나 실험을 통한 관찰.
4. 실제 코드와 호출 경로를 따라가는 설명.
5. 안전 조건과 실패 사례, 가능한 대안의 비용.
6. 관련 테스트와 로컬 실행 방법.
7. 자기 말로 설명해 보는 질문, 다음에 읽을 절.

## 6. 그림과 코드 탐험기 구현

### 6.1 그림의 종류와 쓰임

- 구조도: 구성요소를 선택하면 책임, 소유 자원, 호출자를 보여준다. API 계층과 내부 구현을 구분한다.
- 시간 흐름도: accept, I/O 워커, 애플리케이션 워커, 커널을 별도 줄에 놓는다. 같은 그림에서 실제 스레드와 개념적 단계를 혼동하지 않는다.
- 메모리 그림: 주소 범위, 읽기/쓰기 범위, 게시된 요청이 사용하는 범위, 소유자를 표시한다.
- 상태도: 실제 enum 값과 전이 조건을 표시한다. 설명을 위한 단순화는 별도 표시한다.
- 비교 그림: 같은 입력으로 정상 동작과 잘못된 구현을 나란히 보여준다. 잘못된 구현은 교육용으로 명확히 표시한다.

SVG는 기본 방식으로 사용하고 CSS로 크기를 조절한다. 다이어그램만 축소해 글씨가 읽히지 않게 하지 않는다. 좁은 화면에서는 확대 버튼과 순서 목록 보기를 제공한다. 모든 그림에는 핵심 관계를 설명하는 텍스트와 접근 가능한 이름을 둔다.

색상은 역할을 일관되게 표현한다. 수신/송신/대기/완료/오류를 색상뿐 아니라 선 모양과 상태 이름으로도 구분한다. 연결선 방향과 분기 조건을 생략하지 않는다.

### 6.2 움직임의 의미

움직임은 데이터 이동, 요청 게시, 완료 처리, 상태 변경을 설명할 때만 사용한다. 자동 재생은 사용자가 시작한다. 재생/정지/이전/다음/처음/속도 조절을 제공하고 페이지 이동이나 탭 비활성화 시 정지한다. 동작 감소 설정에서는 이동 애니메이션을 없애고 상태 갱신은 유지한다.

단계 사이에 발생할 수 있는 다른 실행을 가려서는 안 된다. 교육용 직렬 경로는 ‘이번 설명에서는 다른 세션의 실행을 생략했다’고 표시한다. 단순한 프레임 속도를 실제 지연 시간으로 표시하지 않는다.

### 6.3 코드 탐험기

원문에서 함수 전체를 여는 기능과, 학습에 필요한 구간을 따라가는 기능을 함께 제공한다.

- 단계 선택 시 설명, 흐름도, 코드 강조, 상태 패널이 함께 갱신된다.
- 직접 호출, 콜백, 완료 이벤트를 서로 다른 연결로 표시한다.
- 호출 경로 이동 이력을 유지해 이전 코드와 본문으로 돌아갈 수 있게 한다.
- 기본 화면은 관련 코드 구간만 표시하고 ‘함수 전체’, ‘파일 전체’를 선택할 수 있게 한다.
- 실제 코드, 생략한 코드, 설명용 의사 코드를 구분한다. 실제 코드 안에 설명을 삽입해 원문처럼 보이게 하지 않는다.
- 원본 경로, 기준 커밋, 파일 해시, 실제 줄 번호를 표시한다.
- 전체 파일 DOM은 열 때 만든다. 책을 열자마자 모든 소스를 줄별 DOM으로 생성하지 않는다.
- 함수 이름 클릭만 지원하는 것에서 끝내지 말고 분기에서 무엇이 달라지는지 설명한다.

출처는 파일 경로+고유한 시작/끝 문자열 또는 선언 선택자로 정의한다. 줄 번호는 결과로 계산한다. 문자열이 0개 또는 여러 개면 빌드를 실패시킨다. 단순 괄호 세기로 C++ 전체 문법을 처리했다고 주장하지 않는다. 필요한 함수는 명시적 경계 선택자로 안전하게 추출한다.

| L18 / C23 | 로그·지표를 보고 진단 선택 | 증상 하나를 원인 하나로 단정하지 않음. 추가 확인 항목, 잘못된 조치의 영향, 근거 코드 연결. |
| L19 / C24 | N번째 초기화 작업 실패 | 이미 확보한 자원을 역순으로 정리, 미확보 자원 해제 없음. 실제 fake 테스트와 연결. |
| L20 / C25 | 측정 자료 선택, 오류/반복/단위 조건 변경 | 오류 있는 실행 제외, 중앙값/P99 해석, 다른 환경 비교 경고. 가상 수치를 실측 성능으로 제시하지 않음. |

L17의 설정 계산은 C++ 검증 결과와 비교하는 fixture를 만든다. 범위를 JS로 옮겨 적고 그대로 맞다고 간주하지 않는다. 모든 계산 결과에 ‘설명용 계산’ 또는 ‘검증된 설정 결과’를 표시한다. JS 정수 정밀도를 넘는 generation은 10진 문자열 또는 BigInt로 다루고 URL/JSON에는 문자열로 저장한다.

L15는 기존 ChatServer의 상태와 룸 범위를 확인한 후 모델링한다. 현재 구현에 없는 shard 간 방송을 애니메이션만으로 구현된 기능처럼 보여주지 않는다.

### 7.1 모델 구현 규약

실험은 UI 이벤트 핸들러 안에 상태 변경 코드를 흩어 놓지 않는다. 순수 상태 전이 함수로 구현한다.

```js
// 화면과 무관한 모델 인터페이스. 실제 이름도 이 형태로 통일한다.
createInitialState(config)
transition(state, action) // { state, events, explanationId }
validateState(state)     // 위반 항목 배열
serializeScenario(config, actions)
```

이전 단계는 가능한 모든 변경을 수동으로 되돌리기보다 초기 상태부터 기록한 action을 재실행해 복원한다. 같은 초기값과 action 목록은 항상 같은 결과를 내야 한다. 무작위 실험을 추가하면 seed를 저장한다.

한 모델의 상태 예시는 다음과 같다.

```json
{
  "schemaVersion": 1,
  "labId": "partial-send",
  "config": {"messageBytes": 4, "generation": "41"},
  "actions": [{"type": "complete", "bytes": 2}],
  "view": {"step": 1}
}
```

실험의 UI 설명도 현재 상태에서 계산한다. 체크박스를 바꾸었는데 이전 검증 결과가 그대로 남는 등의 모순을 없앤다. 다이어그램 노드 선택과 다음 단계 버튼은 같은 모델을 호출한다.

## 8. 실제 코드와 설명의 일치

### 8.1 근거 우선순위

현재 코드와 테스트, 공개 API 주석, 기존 문서와 설계 기록을 대조한다. 문서와 코드가 다르면 문서를 기계적으로 옮기지 않는다. 공개 계약과 구현이 어긋나면 ‘코드가 정답’으로 덮지 말고 차이를 기록한다.

조사 중 이미 확인한 주의점은 다음과 같다.

- `docs/session-lifecycle.md`의 개념 상태명·순서는 실제 `SessionState`의 Free→Accepting→Active→Draining→Closing→Quarantined와 다르다. 책에서는 실제 enum과 개념 그림을 혼용하지 않는다.
- `docs/threading-model.md`의 ‘완료를 처리하기 전에 다음 수신’이라는 문장은 모호하다. 실제 경로는 완료를 검사·반영한 뒤, 여유가 있으면 애플리케이션 콜백보다 먼저 다음 수신을 게시한다.
- EchoServer는 별도 게임 로직 큐를 통과하지 않는다. ChatServer 구조를 Echo 경로에 끼워 넣지 않는다.
- `LengthPrefixedDecoder`의 길이는 헤더 포함 전체 크기다. 디코더가 조각을 내부 보관하는 것처럼 설명하지 않는다.
- `Server::Send`는 내부 복사 계약이다. 두 span 오버로드가 커널까지 zero-copy라는 뜻이 아니다.
- generation 일치와 세션 활성 상태는 다른 조건이다. 둘을 하나의 검사처럼 표현하지 않는다.
- `send_operations`는 애플리케이션 Send 호출 수이며 RIOSend 호출 수가 아니다.
- 종료 타임아웃 후 outstanding이 남으면 현재 코드는 커널이 참조할 수 있는 등록 자원과 CQ를 의도적으로 보존할 수 있다. 성공적인 해제라고 설명하지 않는다.
- 기존 ADR에는 T03/T08/T11 등 당시 단계적 구현 계획이 남아 있다. 현재 미구현 사항이라고 그대로 옮기지 않는다.
- 기존 API 문서의 ‘0.4.0에서 호환 계층 제거 예정’은 당시 계획이다. 다음 세션의 버전·코드를 확인하고 현재 약속으로 단정하지 않는다.

### 8.2 출처 매니페스트

각 핵심 설명은 `evidence.json`의 항목으로 관리한다. 적어도 공개 계약, 상태 전이, 버퍼 수명, 큐 정책, 종료 경로, 설정 계산은 등록한다.

```json
{
  "id": "send.partial_completion",
  "chapter": "partial-send",
  "section": "repost-remainder",
  "source": "RIONetLite/impl/send_immediately.h",
  "selector": {"start": "bool Completed(", "end": "void Failed("},
  "testSource": "tests/unit/rio_request_test.cpp",
  "testName": "SendQueueTest.RepostsOnlyTheRemainderAfterPartialCompletion",
  "kind": "implementation",
  "reviewedSourceSha256": "구현 시 실제 파일 해시를 기록한다"
}
```

출처가 바뀌면 빌드가 새 코드를 넣는 것과 검토 완료를 구분한다. `--check`는 해시 변경을 발견하면 해당 설명의 재검토가 필요하다고 실패시킨다. 빌드가 검토 해시까지 자동 갱신하면 안 된다. 검토 후 명시적으로 기록을 갱신한다.

### 8.3 성능과 과거 기록

`performance-tuning.md`에는 20 논리 프로세서/i7-12700KF에서 측정한 결과가 있다. 사용자의 현재 기본 장비 정보인 i5-14400F/16스레드와 섞지 않는다. 과거 기록의 장비명을 현재 PC 사양으로 바꾸지 않는다.

과거 표에는 날짜, 커밋/버전, 장비, 측정 시간, 반복 횟수, 단위, 오류 조건, 원본 자료의 존재 여부를 함께 표시한다. 원본 자료가 없으면 ‘기존 문서의 기록이며 원자료 미확인’으로 표시한다. 과거 통과 체크는 이번 책 작업에서 테스트를 재실행한 결과가 아니다.

## 9. 화면과 공통 기능

현재 샘플의 차분한 배경, 충분한 행간, 좌측 목차, 본문과 실험을 묶는 구성을 유지한다. 단, 장 전체를 카드 목록으로 만들지 않고 설명을 연결된 문단으로 쓴다.

### 9.1 이동과 검색

- 데스크톱: 부/장/현재 절의 목차와 읽기 위치. 모바일: 열고 닫는 목차와 현재 장 표시.
- URL: `#chapter=partial-send&section=repost-remainder`를 기준으로 한다. 실험 링크에는 `lab`과 버전 있는 scenario 데이터를 추가할 수 있다.
- URL의 알 수 없는 장·절·scenario는 안내 후 안전한 기본 상태로 이동한다. 잘못된 값으로 JS가 중단되지 않게 한다.
- 샘플의 `#p1`~`#p10` 주소는 대응 장으로 보내는 별칭을 유지한다. 별도 샘플 HTML은 최종판과 병존시키지 않는다.
- 브라우저 뒤로/앞으로 이동이 장·절·실험의 이동과 일치해야 한다. 재생의 매 프레임을 방문 기록에 넣지 않는다.
- 검색 결과는 제목, 관련 문장, 장/절, 유형을 보여준다. 본문·API·용어를 검색하며 대소문자와 기본 한영 별칭을 처리한다.
- 검색 결과 선택 시 해당 절과 강조 위치로 이동한다. 검색 문자열은 HTML로 삽입하지 않고 escape한다.

### 9.2 저장과 공유

- 읽기 위치, 테마, 자기 점검은 버전 있는 localStorage 키로 저장한다.
- 실험 상태는 세션 내 이동에서 유지하고 ‘이 실험 초기화’로 지운다. 새 책 버전과 맞지 않는 저장값은 안내 후 초기화한다.
- 저장소를 사용할 수 없는 브라우저에서도 읽기와 실험은 정상 작동한다. 저장이 안 됨을 짧게 알린다.
- 실험 상태를 복사할 수 있게 한다. 로컬 파일 경로가 포함된 링크는 다른 사람의 PC에서 그대로 열리지 않는다는 점을 구분한다. 짧은 scenario JSON 내보내기/가져오기도 제공한다.
- 공유 데이터 크기와 action 개수에 상한을 두고 타입·범위를 검사한다. 외부 코드나 HTML을 실행하지 않는다.

### 9.3 접근성과 인쇄

- 모든 조작은 키보드로 가능하게 한다. 코드 패널은 Esc로 닫고 원래 버튼으로 포커스를 돌린다.
- 움직임을 멈출 수 있어야 하며 `prefers-reduced-motion`을 지원한다.
- 상태 변경은 읽을 수 있는 텍스트로도 제공한다. 자동 재생 중 불필요한 live-region 알림을 반복하지 않는다.
- 인쇄용 보기에는 모든 장을 표시하고 조작 버튼을 설명과 대표 상태로 대체한다. 펼친 심화 설명과 테스트 이름도 출력한다.
- 현재 선택한 잘못된 시나리오를 설명 없이 인쇄하지 않는다. 인쇄 스냅샷 상태를 초기 대표 상태로 고정하거나 조건을 명시한다.
- 인쇄 때문에 본래 실험 상태를 잃지 않도록 인쇄용 DOM을 따로 만들거나 전후 상태를 복원한다.
- PDF 자동 생성은 필수 산출물이 아니지만 브라우저의 인쇄/PDF 저장에서 내용이 잘리지 않아야 한다.

## 10. 파일 구조와 생성 방식

샘플 경로를 최종 경로로 계속 사용한다. `docs/book`, `docs/manual` 같은 별도 책을 추가하지 않는다.

```text
docs/
  book_implementation_plan.md       # 구현 중 작업 기준. 완료 후 핵심 유지관리 내용을 A05로 이관
  interactive_book/
    index.html                     # 독자가 여는 독립 HTML, 생성 결과
    book_template.html             # 공통 읽기 화면
    book.css
    book.js                        # 화면 연결. 실험 모델 본체는 분리
    build_book.py
    manifest.json                  # 장, 절, 읽기 경로, 실험 등록
    glossary.json
    evidence.json
    migration.json                 # 24개 문서의 내용·상태 추적
    chapters/                      # 장·부록 HTML 원고. 별도 독자 진입점 아님
    diagrams/                      # SVG와 설명 데이터
    models/                        # 순수 JS 상태 전이 모듈
    generated/
      api.json                     # 공개 API 목록 자동 생성 데이터
tools/
  book/
    package.json
    package-lock.json              # 브라우저 검사 도구 버전 고정
    verify_book.cjs
    model_tests.cjs
    content_checks.py
    fixtures/
  check-docs.ps1                   # 기존 진입점 유지, 검사 대상을 책으로 전환
  generate-api-docs.ps1            # 기존 진입점 유지, 출력은 api.json으로 변경
artifacts/book/                    # 테스트 로그, 화면 캡처, 임시 인쇄물. Git 제외
```

원고는 장별 HTML 조각으로 관리한다. 읽을 문서를 정리한다는 이유로 저작 소스까지 하나의 거대한 문자열로 만들지 않는다. 장 원고 파일에는 독립 내비게이션을 넣지 않으며 README에서 개별 원고 파일을 안내하지 않는다.

Python 표준 라이브러리로 장 원고, CSS, JS, SVG, 코드 스냅샷과 검색 데이터를 합쳐 단독 HTML을 만든다. 실행 시 `fetch()`나 ES module import로 로컬 파일을 읽지 않게 한다. 소스 단계에서 모듈을 나누더라도 생성된 HTML에는 의존 순서가 정해진 스크립트로 묶는다. 외부 번들러가 꼭 필요한 구조를 만들지 않는다.

브라우저 검사에는 저장소 안의 개발용 Node 패키지로 Playwright를 설치하고 lockfile을 유지한다. 샘플 검증에서 사용했던 다른 저장소의 `F:/github/BazookaBlast/...` 경로를 최종 명령이나 코드에 남기지 않는다. Windows 실행 예시는 실행 정책 충돌을 피하기 위해 필요하면 `npm.cmd`를 사용한다.

생성기는 현재 디렉터리와 무관하게 동작하고 UTF-8을 사용한다. 빌드 결과는 같은 입력에서 동일해야 한다. 매 실행 시각을 HTML에 넣어 불필요한 diff를 만들지 않는다. 출처 커밋, 파일 해시, 명시적인 판본 날짜를 넣고 마지막 생성 결과를 덮어쓰기 전에 임시 파일을 완성한다.

`--check`는 현재 HTML/API 데이터/출처/본문이 최신인지 읽기 전용으로 검사한다. `--output`은 검증용 임시 결과를 지정한다. 소스 목록은 명시적 allowlist로 관리해 저장소 전체나 외부 파일을 무조건 포함하지 않는다. 출력 HTML은 배포용 문서이므로 관리 대상이며, node_modules·캡처·중간 결과는 관리하지 않는다.

책이 커져도 첫 장을 빨리 표시한다. 코드 행 DOM, 다른 장의 무거운 실험, 검색 결과는 필요할 때 만든다. HTML 크기와 초기화 시간을 측정하고, 불필요한 전체 파일 중복이 있으면 제거한다. 압축을 위해 학습에 필요한 코드를 제거하지 않는다. 성능 목표는 14절에서 확인한다.

### 11.2 내용 단위 이관 추적

파일명만 대응시키고 삭제하지 않는다. 원본의 제목, 표, 명령, 주의 사항, 고유한 사실별로 `migration.json`에 기록한다.

```json
{
  "source": "docs/backpressure.md",
  "sourceSha256": "이관 시작 시 계산",
  "items": [
    {
      "id": "close-event-on-full-queue",
      "destination": "logic-queue#parked-close",
      "disposition": "merged",
      "evidence": "queue.close_order",
      "reviewed": false
    }
  ],
  "status": "inventoried"
}
```

`disposition`은 `merged`, `already_covered`, `historical`, `corrected`, `obsolete` 중 하나다. obsolete에는 제거 이유와 근거가 필요하다. 상태는 `inventoried → drafted → verified → removed` 순서로 변경한다. 다음 조건을 모두 만족해야 removed로 표시할 수 있다.

1. 모든 항목에 목적지 또는 근거 있는 제외 사유가 있다.
2. 책에 목적지 장·절이 실제 존재한다.
3. 기존 값, 명령, 표와 필요한 제한 사항이 보존되었는지 사람이 대조했다.
4. 최신 코드와 어긋난 설명은 수정 이유와 근거를 기록했다.
5. 참조 링크와 생성·검사 도구가 새 경로를 사용한다.
6. 변경 직전에 원본 해시를 다시 확인했다. 작업 중 바뀌었으면 추가 내용을 먼저 이관한다.

### 11.3 남길 문서와 최종 진입점

루트 `README.md`, `README_kr.md`는 남긴다. 프로젝트 소개, 짧은 시작 방법, 책 열기와 필요 도구만 간결하게 안내한다. 본문의 여러 `.md` 링크는 책의 장/절 주소로 바꾼다. README의 C++ 예제와 package consumer 일치 검사는 유지한다.

`AGENTS.md`, `CHANGELOG.md`, `SECURITY.md`, `LICENSE`는 목적이 다르므로 삭제하지 않는다. `benchmarks/baselines/.../README.md`와 기준선 승인·환경·원자료는 docs 밖의 측정 근거이므로 이번 통합 삭제 대상이 아니다.

이 구현 계획은 작업 중 `docs`에 남길 유일한 관리용 마크다운으로 허용한다. 책 완성 시 실제 사용된 생성·검증 방법과 이관 결과를 A05 및 JSON에 옮긴 뒤 이 계획도 삭제한다. 오래된 할 일 문서를 최종 사용 안내와 함께 남기지 않는다.

최종 독자 문서 목록은 루트 README 두 개와 HTML 책이다. 책의 여러 HTML 원고와 JSON은 저작 소스이며 독립 안내 문서로 링크하지 않는다.

## 12. 문서 생성기와 검사 도구 전환

기존 마크다운 삭제와 아래 변경은 같은 완료 단계에 묶는다. 스크립트가 오래된 파일의 존재를 요구하는 상태로 끝내지 않는다.

### `tools/check-docs.ps1`

- 현재 19개 필수 경로 배열을 새 책 진입점과 매니페스트 검사로 교체한다. 실제 항목 수는 수정 시 재확인한다.
- 기존 루트 README와 package consumer의 C++ 코드 일치 검사를 유지한다.
- 관리되는 파일만 검사한다. 저장소 전체 재귀로 node_modules, vcpkg, artifacts까지 문서 검사하지 않는다.
- HTML/Markdown 로컬 링크의 파일 경로뿐 아니라 목적지 앵커도 검사한다. 책 URL의 chapter/section 조합을 해석한다.
- `build_book.py --check`, 공개 API 갱신 검사, 출처 선택자 검사, 이관 누락 검사를 호출한다.
- 필요한 Python/Node가 없으면 설치할 도구와 다시 실행할 명령을 알려주고 실패한다. 조용히 건너뛰어 성공 처리하지 않는다.

### `tools/generate-api-docs.ps1`

- 공개 헤더의 `@api`와 선언 대조 기능을 유지한다.
- Markdown 대신 정렬이 일정한 UTF-8 `docs/interactive_book/generated/api.json`을 생성한다.
- `-Check`는 생성 결과가 최신인지 확인하고 파일을 변경하지 않는다.
- 출력 경로를 참조하는 모든 스크립트와 본문을 함께 수정한다.
- 현 생성기는 최상위 타입/함수 목록이지 모든 멤버 API 설명이 아니다. `Server::Send` 등 멤버의 계약은 A01에서 별도 작성하고 출처를 연결한다.
- 주석이나 심볼을 삭제해 검사만 통과시키지 않는다. 새 타입의 API 항목 누락은 계속 실패시킨다.

저장소에는 현재 `.github` workflow가 없으며 기존 문서에 사용자 요청으로 제거했다고 기록되어 있다. 책 작업을 이유로 CI를 새로 추가하지 않는다. 우선 로컬 검사 명령을 완성한다.

`tools/package.ps1`은 현재 headers/lib/PDB/라이선스/변경 기록/consumer sample을 묶는다. 책을 패키지에 포함하는 변경은 첫 판의 필수 조건이 아니다. 기존 배포 동작을 깨지 않고 C27에서 현재 범위를 설명한다.

### 14.2 실제 라이브러리 검증과 구분

문서 변경만으로 C++ 제품 코드에 불필요한 테스트를 추가하지 않는다. 그러나 책의 실행 안내를 검증하기 위해 최소한 최종 상태의 x64 Debug/Release 빌드와 두 테스트 실행 파일, Echo 및 Chat 기본 시나리오를 확인한다. 관련 명령은 먼저 기존 스크립트와 출력 경로를 확인한다.

```powershell
tools\build.ps1 -Configuration Debug -Rebuild
tools\build.ps1 -Configuration Release -Rebuild
bin\tests\x64\Debug\RIONetLite.UnitTests.exe
bin\tests\x64\Debug\RIONetLite.IntegrationTests.exe
bin\tests\x64\Release\RIONetLite.UnitTests.exe
bin\tests\x64\Release\RIONetLite.IntegrationTests.exe
```

메모리 검사와 긴 부하 검사는 책의 개념 모델 테스트와 별도다. 설명에 최신 실측 결과를 넣는다면 해당 검사를 실제 실행하고 근거를 남긴다. 그렇지 않다면 명령·판정 방법과 역사적 결과만 제공하며, 이번 판에서 통과했다고 쓰지 않는다. 머신 전역 설정을 변경하는 도구는 범위를 확인하고 끝나면 복구한다.

C++ 파일을 변경했다면 루트 지침의 clang-format 및 빌드 기준도 적용한다. 문서 작업 중 발생한 기존 빌드 실패를 숨기거나 책 작업의 통과로 합치지 않는다.

## 15. 구현 단계와 단계별 종료 조건

작업은 아래 순서로 진행한다. 각 단계가 끝날 때 이 문서의 상태표를 갱신하고 실제 변경 파일, 실행 명령, 결과, 미완료 항목을 짧게 기록한다. 별도의 진행 보고 마크다운을 계속 추가하지 않는다.

| 단계 | 작업과 산출물 | 선행 | 완료 판정 |
|---|---|---|---|
| B00 | 현재 코드·문서·버전 재조사, `migration.json` 내용 목록, 기존 변경 보존 | 없음 | 24개+새 문서 모두 분류, 조사 기준 갱신 |
| B01 | 원고 구조, manifest, evidence/glossary 모델, 생성기 `--check`, 개발 의존성 | B00 | 빈 장을 완성 처리하지 않는 생성·검사 기반 작동 |
| B02 | 공통 읽기 화면, 검색, 이동 이력, 저장, 소스 탐험, 접근성 | B01 | file://로 기능·키보드·저장 불가 테스트 통과 |
| B03 | C04/C13/C15를 완성본 깊이로 집필, L01/L09/L11 연결, 문체 교정 | B02 | 세 장만 읽어도 설명→실험→코드→검증이 완결됨 |
| B04 | C01~C09 나머지 집필, 구조·스레드·메모리·링 실험 | B03 | 1·2부의 원리와 코드 연결 검수 완료 |
| B05 | C10~C15 나머지 집필, 연결·식별·수신·송신 실험 | B04 | 세션 재사용과 오류·경계 모델 검증 완료 |
| B06 | C16~C20 집필, 종료·큐·Chat·게임 확장 실험 | B05 | 종료 이벤트 순서·타임아웃·실제 Chat 제한 설명 완료 |

| B08 | C25~C28 및 A01~A05 집필, 측정 실험, 과거 기록 보존 | B07 | 모든 기존 내용의 목적지와 역사 구분 확인 |
| B09 | API JSON 생성 전환, check-docs 전환, README 링크 수정 | B08 | 새 도구로 전체 문서·API 검사 통과 |
| B10 | 이관 항목 대조, 원본 해시 확인, 대상 Markdown 삭제, 빈 폴더 정리 | B09 | docs 독자 문서는 책으로 통합, 남은 링크 0 |
| B11 | 전체 문장 검수, 모델·브라우저·오프라인·인쇄 검사, 실행 안내 검증 | B10 | 14절 통과, 실패·미실행 사실 별도 기록 |
| B12 | 최종 생성·진입점 확인, 유지관리 기록 A05 이관, 계획 문서 정리 | B11 | 독자가 HTML 하나로 모든 학습 경로 사용 가능 |

B03은 또 하나의 샘플을 제출하고 끝내는 단계가 아니다. 완성본의 품질 기준을 고정한 뒤 나머지 장을 이어서 작성한다. 분량이 크면 여러 세션에 걸쳐도 되지만 매 세션 상태를 정확히 남기고 완료하지 않은 장을 숨기지 않는다.

삭제는 glob으로 모든 Markdown을 지우지 않고 `migration.json`에서 verified인 정확한 파일 목록을 사용한다. Windows에서는 절대 경로가 저장소의 docs 안에 있는지 확인한 뒤 같은 PowerShell 실행 안에서 처리한다. 사용자 작업이 섞인 파일은 최신 내용을 이관하기 전 삭제하지 않는다.

다음 세션에서는 다음 요청으로 시작할 수 있다.

> `docs/book_implementation_plan.md`를 기준으로 HTML 책을 구현한다. 문체와 용어 규칙을 지키고, 실제 코드와 테스트를 근거로 충분히 설명한다. 기존 docs의 마크다운은 내용 이관과 검증, 검사 도구 및 링크 전환을 마친 뒤 삭제한다. 현재 Git 변경을 보존하며 B00부터 완료되지 않은 단계를 진행한다.

최종 인수 시 사용자는 첫 화면에서 책의 목적과 읽기 경로를 이해하고, 한 패킷의 왕복을 코드로 따라가며, 잘못된 길이·부분 송신·오래된 세션·포화·종료 순서를 스스로 실험할 수 있어야 한다. 그리고 궁금한 API, 설정, 오류, 과거 설계 결정을 별도 마크다운을 찾아다니지 않고 같은 책 안에서 확인할 수 있어야 한다.
